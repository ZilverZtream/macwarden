# Audit of MacWarden 1.1.0

## Verdict

**11 findings: one high, four medium and six low.** The previous release's twelve reported problems have corresponding repairs and regression coverage. This audit confirms the canary-preservation and interrupted-batch recovery repairs against Polar. It also finds a live credential that scanning misses, an unsafe verification conclusion under clock skew, two file-read boundary gaps, and a recommendation safeguard bypass through invalid dates. Fix the high and medium findings before relying on these commands for incident clearance or unattended narrowing.

Candidate: `64720ee58ba3eab9feef84621abde896f482bb68`, `Merge macwarden 1.1.0`. Package and lockfile both identify version `1.1.0`. The audit ran in a separate local snapshot of the release; its tracked product tree remained unchanged. Reproducers and credential-free result records are kept with the audit material (`audit110-{root,security,online,operations}`), not in the release. This report is the only requested repository change.

This is an adversarial release audit with focused checks, not a fresh full release validation. No checkpoint approval, CI pass or full Windows/Linux suite pass is implied. Two review sessions ended before completing, after producing partial artifacts; their unfinished coverage is not counted as completed review. The LND/API review completed, and the material findings below were independently checked by the coordinating review.

### MW110-01 — Scanner drops a valid credential across its text window

Locations: `src/scan/index.ts:114`, `:188`, `:215`, `:271`. References: scan's fail-closed candidate handling and `--fail-on` contract.

Append a valid `time-before 2099-01-01T00:00:00.<50000 zero digits>Z` caveat to a real audit credential, then put the resulting bytes in the `macaroon` field of an ordinary `lndconnect` URI. The live credential is 50,257 bytes, below the 64 KiB macaroon bound; its approximately 67 KB text file is well below the 5 MiB scan limit. LND accepts the long fractional timestamp. Both `verify` and an independent `lncli getinfo` accept these final bytes.

**Actual:** `scan <connection.txt> --fail-on READ --json` exits 0 with zero findings, `dropped: 1` and fail-on count 0. Scanning the identical bytes as a binary `.macaroon` file exits 1 with one finding. The Windows and unprivileged Linux CLI reproduce the URI miss; the Linux case uses the committed ADMIN vector and also exits 0 at `--fail-on ADMIN`.

The 65,536-character detector window truncates the URI. The truncated URI suppresses its embedded base64 candidate and is then dropped when parsing fails. Increasing overlap alone does not cover the full supported credential encoding plus URI overhead.

**Fix:** retain complete candidates across windows, bounded by a documented encoded-size limit, or emit an `undecodable-candidate` finding for a truncated credential-bearing URI that participates in fail-on evaluation. Do not silently drop it. Prove detection with a credential independently accepted by LND, and include boundary lengths and offsets in regression coverage.

Evidence: `audit110-root/additional-live.mjs`, `additional-live-results.json`; `linux-native-results.json`. Independent offline ADMIN reproduction: `audit110-security/long-uri.mjs`, `long-uri-output.json`.

### MW110-02 — A local clock can produce false incident clearance

Locations: `src/commands/verify.ts:219`, `:224`; SPEC's verify classification paragraph also encodes this assumption.

Create a still-unexpired credential with an IP caveat that rejects the verification caller. With the correct clock, the real node returns a caller-dependent rejection: `rejection: "other"`, `conclusive: false`, exit 1. Call the same compiled command with its existing injected clock one day ahead while retaining the real adapter, node, files and permissions.

**Actual:** the same node response becomes `rejection: "expired"`, `conclusive: true`, exit 0. The expiry is inferred from the operator machine's clock, not established by the node. The ordinary parent remains accepted by the same LND immediately afterwards. No operating-system clock was changed.

This proof demonstrates a false expiry conclusion and unsafe exit code; it does not demonstrate that this particular IP-locked file is accepted from the tested caller. The correct result already acknowledges it could be accepted in another caller context. Clock skew must not turn that uncertainty into global clearance.

**Fix:** retain an `other` rejection as inconclusive unless expiry is established by trustworthy node-side evidence. Keep local expiry presentation separate from the incident verdict. Amend SPEC and test a context-dependent rejection with clock skew, rather than injecting a preclassified expiry outcome.

Evidence: `audit110-root/live.mjs`, `live-results.json`, rows for correct-clock IP rejection and the same bytes with an advanced local clock. The pinned [LND request definition](https://github.com/lightningnetwork/lnd/blob/v0.20.0-beta/lnrpc/lightning.proto#L4755) describes issuance, caveat and requested-permission checks; it does not return the operator machine's expiry inference.

### MW110-03 — Repository configuration can open protected files

Locations: `src/scan/git-history.ts:148`, `:154`, `:251`, `:262`. Reference: SAFE-02, including protected resolved targets and directory components.

A generated repository's `.git/config` includes `../wallet.db`. The synthetic `wallet.db` contains only harmless valid Git configuration. Both the compiled repository locator and the full `scan --git-history` CLI accept it. Preflight byte counters include its content. This reproduces on Windows and Linux.

`local()` enforces local filesystem locations but not protected names; `Preflight.small()` reads the include without `isProtectedPath`. The normal worktree walk and historical blob filters do not protect configuration preflight. Includes may also name paths outside the scanned tree or aliases to protected targets.

**Impact:** an untrusted local repository can make the scan read files it explicitly promises never to open. No real wallet/key file was read and no output exfiltration is demonstrated. Ordinary clones do not transport `.git/config`; the trigger requires scanning a locally prepared repository/configuration, not merely an ordinary tracked file.

**Fix:** apply supplied-path and resolved-target protection to all repository-location reads, including Git files, commondir, alternates and config/include targets. Refuse the history operation before content opens. Use a bounded descriptor-based reader for the preflight read itself.

Evidence: `audit110-root/feature-checks.mjs`, `feature-check-results.json`, `linux-native-results.json`; independent `audit110-security/protected-include.mjs` and `protected-include-output.json`.

### MW110-04 — An external report's lock-read concern is valid, with narrower impact

Locations: `src/bounded-file.ts:76`; `src/registry/index.ts:363`, `:384`, `:397`; `src/commands/watch.ts:277`, `:232`, `:268`.

The first lock read calls `assertPlainFile`, which uses `lstat`, then calls `readFile` by pathname. Later recovery and release reads also use whole-file pathname reads. There is no opened-handle binding between the check and content consumption.

**Confirmed:** a deterministic hook performs a real local file change after the real `lstat` returns, then lets the unchanged product code perform its real `readFile`. In both registry and watch handling, the checked file was 101 bytes; the read consumed 131,072 bytes despite `LOCK_FILE_LIMIT = 65,536`. Windows and unprivileged Linux reproduce it. The existing descriptor-based bounded reader refuses the control case before reading content.

The file swap is deliberately scheduled by the test filesystem wrapper; no concurrent attacker timing success, symlink-to-device access or OOM crash is claimed. A pathname replacement can change the object read, and the current calls do not bound content reads, so the concern is real. However, an actor must be able to modify the lock path; POSIX registry acquisition rejects group/world-writable directories. This is a medium hardening defect, not demonstrated unauthenticated remote compromise.

The unbounded reads already existed in 1.0.1. Version 1.1.0 added the incomplete `assertPlainFile` guard; the diff does not support claiming it introduced the underlying unbounded-read vulnerability.

**Fix:** validate and read through one handle, impose a limit-plus-one read bound, and check pathname/opened-file identity wherever the protocol requires a plain file. Cover recovery/quarantine and release reads too. Use nonblocking/no-follow flags where supported. The externally proposed `O_NOFOLLOW ?? 0` is not sufficient by itself on Windows: supported Windows Node here exports neither `O_NOFOLLOW` nor `O_NONBLOCK`, so identity and type checks remain necessary. An opened descriptor binds the read to a checked object; it does not make an entire pathname protocol atomic.

Evidence: `audit110-root/file-read-check.mjs`, `file-read-check/result.json`, `linux-file-read-results.json`. The test uses at most 128 KiB per changed file and removes it afterwards.

### MW110-05 — Invalid dates suppress the recommendation warning

Locations: `src/watch/usage.ts:71`, `:89`, `:115`; `src/commands/recommend.ts:214`, `:216`.

Usage timestamp validation checks their shape but not whether they are dates. `2026-99-09T12:00:00Z` is accepted. Its `Date.parse` is NaN; the observation calculation becomes NaN and `seconds < sevenDays` is false. JSON later serializes the number as null.

**Live CLI proof:** a real registered READ credential with one GetInfo observation and zero seconds of coverage yields `short: true`, a warning and no narrowing commands. Change only `lastEnd` to the invalid month. The same command against Polar returns `ok: true`, no warnings, `seconds: null`, `short: false` and two commands for baking a narrowed credential and revoking the old one, without `--accept-short-observation`.

This requires malformed or edited usage evidence; normal timestamp writes do not produce month 99. It nevertheless defeats the explicit conservative treatment of insufficient evidence at the read boundary.

**Fix:** validate actual instants and their ordering throughout the usage format. Reject invalid evidence, and independently treat non-finite observation calculations as insufficient. Regression coverage should drive the built recommendation command with malformed usage JSON and assert that advice is withheld.

Evidence: `audit110-root/feature-checks.mjs`, `feature-check-results.json`; independent draft probe `audit110-operations/repro.mjs`, `proof.json`.

### MW110-06 — ADMIN grade is not identical to baking authority

Locations: `src/commands/verify.ts:231`, `src/commands/respond.ts:187`, and SPEC's `canBake` definition.

A live credential holding only `macaroon:write` verifies accepted and produces `canBake: true`, with guidance asserting its holder can bake other credentials. An independent `lncli bakemacaroon` authenticated by that exact credential is denied. Its destructive revocation authority correctly warrants ADMIN grading; that grade does not imply every admin capability.

**Fix:** derive baking authority from `macaroon:generate` or the exact BakeMacaroon URI permission, while conservatively reporting unassessed/truncated authority. Correct verify, respond risk classification and SPEC together. Do not downgrade its general risk grade.

Evidence: `audit110-root/additional-live-results.json`; independent `audit110-online/repro.mjs`, `evidence.json`.

### MW110-07 — Usage parsing has a different root-ID boundary from writing

Location: `src/watch/usage.ts:115`. The parser accepts `99999999999999999999` as a root key ID because it matches the 20-digit regex. It exceeds `18446744073709551615`; the live record writer and registry validator correctly reject values above that limit.

**Fix:** share canonical uint64 validation across usage records, canary records and command selectors. Reject malformed imported evidence rather than propagating impossible IDs. No incorrect node mutation is demonstrated.

Evidence: `audit110-operations/proof.json`, `overflowRootAccepted`; reproduce through `UsageStore.parse` in the adjacent script.

### MW110-08 — UTF-8 redaction claim exceeds the implementation

Locations: `src/credential-recognition.ts:163`, decoded caveat presentation and output filtering. Reference: SAFE-01's explicit raw UTF-8 leak-check guarantee.

The committed binary ADMIN vector's lossy UTF-8 representation survives intact when embedded in a generated credential's caveat and rendered by `inspect --json`. The probe checks visibility in memory and stores booleans only. Recognition replaces codepoints above 255 with byte 255, which cannot reconstruct replacement-character expansion.

This is a low contract/coverage defect: the demonstrated UTF-8 representation is lossy and does not preserve a usable complete bearer credential. Ordinary hex, base64, base64url, latin1 and the exercised separated/escaped encodings were redacted correctly.

**Fix:** make the documented promise and actual recognition agree, and test UTF-8 text as input to rendering rather than merely searching for a UTF-8 needle in unrelated encoded output.

Evidence: `audit110-security/offline-surfaces.mjs`, `offline-surfaces-output.json`.

### MW110-09 — Incident planning omits snapshot drift

Locations: `src/commands/respond.ts:24`, `:161`, and its dry-run/manual-only returns. SPEC Global conventions require online commands to check ListPermissions after GetInfo, although P4's local sequence currently omits it.

With an empty registry and a drifted injected permission map, `respond --dry-run` calls only GetInfo and ListMacaroonIDs and succeeds without a drift warning. Nested rotations cannot supply that check when no rotation runs.

**Fix:** include ListPermissions in OWN requirements and perform the drift check directly in respond, with normal failure handling. Align the global and local SPEC statements. This omission predates 1.1.0.

Evidence: `audit110-online/repro.mjs`, `evidence.json`.

### MW110-10 — Help violates the JSON output promise

Location: `src/cli.ts:176`. `verify --help --json` exits 0 with plain usage text; JSON parsing fails. The same branch affects other commands. Normal command envelopes validate correctly.

**Fix:** document help as an explicit exception or define a JSON help result. Do not advertise an unconditional single-document contract while emitting plain text. This predates verify.

Evidence: `audit110-online/compatibility-evidence.json`, `jsonHelp`.

### MW110-11 — README omits inconclusive rejection

Location: `README.md:61`. It says verify exits 0 once LND rejects the file. The actual contract correctly exits 1 for a rejected but inconclusive credential, because another caller context may accept it.

**Fix:** say exit 1 for accepted or inconclusive rejection, and exit 0 only for conclusive rejection. CHANGELOG and the detailed SPEC already distinguish the cases.

Evidence: correct-clock live IP rejection in `audit110-root/live-results.json`; API compatibility output in `audit110-online/compatibility-evidence.json`.

## Remaining coverage limits

- No full Windows/Linux release suite or full Docker oracle suite was rerun for this audit. Their earlier release evidence is not substituted for these findings.
- Live interoperability was checked with the supplied Polar version; no fresh pinned 0.21.4, other LND versions, Node 22/26 or macOS run is claimed.
- The source-to-runtime bundle was examined and a relocated allowlist exercised; npm publication/provenance and external integration deployment were not independently tested.
- The two unfinished review sessions leave incomplete independent review of portions of the security and watch/resource surfaces. Existing focused tests and coordinating review reduce that gap, but do not erase it.
- The file-change proof schedules a bounded deterministic race. It does not measure the probability of a concurrent local actor winning that race.
- No complete usable credential leak, unauthenticated remote code execution or funds movement was demonstrated. The scanner miss and unsafe clearance conclusions are still concrete operational failures.

## Repair order

1. Fix long-URI fail-on behavior and verify's clock-dependent conclusion, with real-node regression evidence.
2. Bind all lock/preflight reads to checked handles and enforce protected paths consistently. Test finite file changes and both platforms; Windows needs identity checks because no-follow flags are absent.
3. Reject invalid usage instants and impossible uint64 IDs, and keep recommendations conservative when evidence is not finite or ordered.
4. Correct baking-authority guidance, snapshot checking and the output/documentation mismatches.
5. Validate the repaired exact candidate with focused affected-module checks and the required release-level runs. Do not count this audit's focused passes as a green full release.

No audit can establish that the project is “impenetrable.” An external report found a real file-read defect, but its introduction date, critical severity and unconditional Windows fix claims exceed the evidence. Its positive assessment of the linear NWC matcher and alert cleanup is consistent with the reviewed code and the focused cleanup tests.

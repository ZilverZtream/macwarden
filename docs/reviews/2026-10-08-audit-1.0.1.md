# Audit of MacWarden 1.0.1

## Result

**12 findings: 2 high, 7 medium and 3 low.** The ordinary credential lifecycle works on Polar. The failures are in canary preservation, incident recovery, recommendation safeguards, watcher shutdown and boundary handling. Fix the high findings before recommending unattended narrowing or treating registry metadata as a sufficient canary check.

Release reviewed: `952641a7d0a3920ead8f603ded9d04983f245fec` (`main`, package version `1.0.1`). Initial live probes ran on `9bda91b0e46de53443eb215fb622a8ed44e5a923` (`1.0.0`) while the release was being validated. The `respond`, `rotate`, registry and REST adapter source files are byte-identical between those commits. The changed 1.0.1 watch/inventory/recommend paths were checked after rebuilding the exact release. Findings below distinguish real-node, real-filesystem and injected-boundary proof.

The audit ran in a separate local checkout of the release. Probe paths below are relative to that checkout. It is detached at the release commit; its tracked files are clean. Reproducers and detailed observations are kept with the audit material (`audit102-{polar,online,watch}`), not in the release. No source, product tests, time limits or production configuration were changed during this audit.

### MW102-01 — Canary preservation depends on editable metadata

Locations: `src/commands/rotate.ts:329`, `:345–357`; `src/commands/respond.ts:187`. References: SPEC S3 and SECURITY's tampered-registry threat model.

1. Bake a READ canary; run watch with its guard registered.
2. Clear only that entry's registry `caveats` array. Keep its fingerprint, file path, grade, permissions and root key ID unchanged.
3. Run `rotate <label> --out <new file>`.

**Observed on Polar:** the original canary's GetInfo is denied. Rotation exits 0; the replacement has no custom caveat, and GetInfo with the replacement succeeds. The ordinary, untampered canary rotation is correctly refused. S4 already decodes the matching original file, but checks only fingerprint/permissions/grade; S3 checks custom caveats only in the registry.

This needs registry modification; it is not a remote takeover or a claim of direct spending authority. It defeats the explicit protection against turning a canary into an ordinary credential under the documented tampering model.

Fix: check the decoded original's custom caveats independently of metadata; reject disagreement before mutation. Apply the same invariant to batch classification. Regression: edit only the metadata, use the real old file, and assert no replacement is issued.

Proof: `audit102-polar/recovery-watch-results.json`, rows `ordinary canary rotation refused`, `rotate canary after registry caveats stripped`, and `replacement of stripped canary accepted`; `audit102-online/probe.mjs` also reproduces command control flow. Polar proof used the unchanged lifecycle source from 1.0.0; the online probe was repeated on 1.0.1.

### MW102-02 — Interrupted batch finish reports success without repairing

Locations: `src/commands/respond.ts:190–193`, `:217–219`; label resolution in `src/commands/revoke.ts:224`. Reference: SPEC respond promises that the same command resumes an interrupted run; rotate F6 already implements the required repair.

Stage a replacement. Delete the old root key but leave the registry with both entries active: this is the state after deletion succeeded and the process died or the registry save failed. Rerun `respond --finish --yes`.

**Observed on Polar:** exit 0, action `repair`, status `manual`, no proof and empty `unproven`. The advice is `macwarden revoke <label>`. That command exits 2/V6 because both old and replacement entries have the label. Direct `rotate <label> --finish --yes` successfully repairs the same state, exits 0 and reports `repaired:true`.

Fix: prioritize a staged replacement over the absent-original manual branch and invoke rotate's F6 repair, including replacement acceptance proof. Use numeric IDs for advice where labels can be ambiguous. Regression: deletion completed, registry unchanged, then resume through respond and prove both registry repair and accepted replacement.

Proof: `audit102-polar/recovery-watch-results.json`, rows `resume batch finish`, `run printed recovery`, `direct rotate recovery`; `audit102-online/probe.mjs` confirms on 1.0.1.

### MW102-03 — Credential-ID recommendations can widen permissions

Locations: `src/commands/recommend.ts:129–130`, `:155`, `:165–166`, `:187–195`. Reference: SPEC Commands 9, `recommendation-broader`.

A registered credential has only `info:read` and `invoices:write`. Its inconsistent usage record contains SendPaymentV2, requiring `offchain:write`, and carries the same nonzero root key ID as the registry entry. Select this evidence by label and by `id:<16 hex>`.

**Observed on 1.0.1:** the label produces `recommendation-broader` and no commands. Credential-ID selection never resolves the usage identity to the available registry entry: `current:null`, no widening warning, and a `bake --uri /routerrpc.Router/SendPaymentV2` command. The current probe supplies `--accept-short-observation` to bypass only the separate time guard; that flag does not authorize widening. With sufficient recorded coverage, that flag would not be needed.

Following the claimed narrowing command grants payment authority. The prerequisite is inconsistent or modified local evidence, exactly the situation the documented widening guard addresses; no remote write capability is claimed.

Fix: resolve unambiguous nonzero usage identities to registry permissions for every selector. When narrowing cannot be established, suppress the command. Test label, root-key-ID, credential-ID and target-file selectors against identical inconsistent evidence.

Proof: `audit102-watch/probe-current.mjs`, output retained in `probe-current-results.txt`.

### MW102-04 — Coverage before creation satisfies the seven-day guard

Locations: `src/commands/recommend.ts:172–176`; `src/watch/usage.ts:136–173`. Reference: SPEC's observation coverage and short-observation safeguard.

Use the real UsageStore API to record eight days of observation September 1–9. Create the credential October 1. Record a new one-second observation October 8, containing one allowed GetInfo call. No file poisoning or permission inconsistency is needed.

**Observed:** `observation.seconds:604801`, `short:false`, narrowing and subsequent revoke commands printed. Actual observation after credential creation was one second. Taking the minimum of all historical covered seconds and elapsed time since creation cannot locate the coverage within that elapsed interval.

Impact: a new credential can be narrowed before infrequent legitimate methods were observed, breaking its app when the original is revoked.

Fix: retain enough interval/per-credential information to prove post-creation coverage, or calculate a conservative lower bound and keep the short-observation guard when uncertain. Regression: substantial coverage before creation, a gap, then one second afterwards must remain short.

Proof: `audit102-watch/delta.mjs`; `delta-results.txt` records one second actual versus 604801 reported. Dates are synthetic; the UsageStore and recommendation implementation are real.

### MW102-05 — Pending alerts outlive the shutdown budget

Locations: `src/commands/watch.ts:675–677`; `src/watch/alert-throttle.ts:82–101`; `src/watch/alert.ts:35–37`; `src/bin.ts` exit watchdog. Reference: SPEC watch shutdown and SAFE-11.

Start one alert and queue a repeat/summary. Stop watch while the first alert is running. Let the first consume its allowed twelve seconds.

**Confirmed control-flow result on 1.0.1:** first alert starts at 667 ms, pending second at 12678 ms; watch returns success at 13678 ms with one alert still active. This uses the actual watch and runner with timed injected alert promises, not a real executable. The runner has no stop/cancel operation.

**Windows risk inferred from source:** POSIX group cleanup is a no-op on Windows. The second executable could retain almost its entire own timeout after watch returns; the CLI's three-second forced exit could terminate its supervisor before tree cleanup runs. A real orphaned process was not demonstrated. Even on POSIX, starting fresh alert work during shutdown defeats the intended global budget.

Fix: stop submissions and dispose of pending work at shutdown; give the active process/tree one global cancellation deadline. Add a real Windows current-plus-pending child lifecycle test, including readable stdout and child termination.

Proof: `audit102-watch/shutdown-current.mjs`, `shutdown-current-results.txt`.

### MW102-06 — Include validation has a depth bound but no work bound

Locations: `src/scan/git-history.ts:160–169`, `:205–206`. Entry point: `scan --git-history` on a local repository.

The preflight recursively checks every include edge without remembering files already validated, checking cancellation or enforcing a total work budget. Eight local config files, 911 bytes total, each including the same next file eight times, produce 2,396,745 validation visits despite remaining below the ten-level limit.

**Measured:** the single-edge control completes in 83 ms including process startup (8 ms in validation). The shared graph did not finish before an external 3000 ms probe deadline and was killed at 3014 ms. This is preflight, before the Git process's idle timeout is armed. The eventual runtime was deliberately not measured; this probe does not claim an observed 120-second timeout violation. Repeated I/O grows exponentially with a tiny repository.

Fix: memoize canonical validated locations, retain cycle/depth checks, and enforce cumulative file/byte/work budgets with cancellation during preflight. Apply equivalent bounds to alternates. Regression: shared graphs scale with distinct files/edges and terminate with exit 3 or cancellation within a bounded time.

Proof: `audit102-polar/resource-audit.mjs`, `resources/results.json`. The control's recorded `validationVisits:0` is a probe metadata calculation error; the actual control has eight visits. Timings and process outcomes are unaffected.

### MW102-07 — Sidecar readers bypass protected-path checks

Locations: `src/watch/usage.ts:323–331`; `src/watch/canary.ts:42–49`. Called by inventory, recommend and watch through registry-derived sidecar paths. References: SAFE-02 and protected-file handling.

Create a normal-looking usage sidecar symlink to a local synthetic `seed.json`, and a normal-looking canary sidecar symlink to a local synthetic `tls.key`. Both targets contain valid non-secret JSON solely for this probe.

**Observed on real Windows filesystem:** readUsage loads the usage record and readCanaryConfig loads the caveat configuration. Both follow the symlink and read a protected basename, without the resolution/type/identity checks used for ordinary credential input. These readers also use whole-file readFile with no input size bound; in-memory record limits are applied after the allocation/parse.

This demonstrates forbidden file access, not credential disclosure: no real seed/key was read, and no bytes were printed. It requires a modified sidecar/path in the local registry area. Ordinary private-directory access controls reduce the threat but do not enforce the advertised read boundary.

Fix: use a shared bounded regular-file reader that checks the resolved protected path and file identity before reading. Set format-derived size limits before JSON allocation. Regression: symlinks to synthetic protected filenames are refused before reading, and oversized sidecars fail predictably.

Proof: `audit102-polar/current-feature-audit.mjs`, `current-feature-results.json`, final row.

### MW102-08 — IPv6 syntax is accepted but transport TLS fails

Location: `src/lnd/index.ts:125`. Entry point: any online command with `--lnd-rest '[::1]:<port>'` and a valid IPv6 SAN certificate.

**Real local HTTPS proof:** a server bound to `::1`, with a generated `IP:::1` certificate, responds HTTP 200 to a normal Node request using hostname `::1`. Endpoint parsing accepts the bracketed URL. The production adapter passes WHATWG `URL.hostname` (`[::1]`) unchanged to HTTPS and fails with exit classification 4, underlying `ERR_TLS_CERT_ALTNAME_INVALID`, before a second HTTP request reaches the server. TLS verification stayed enabled throughout.

Fix: strip IPv6 brackets for the transport hostname; retain brackets in URLs and recovery commands. Regression: the real HTTPS IPv6 control and adapter both succeed with the same trusted certificate.

Proof: `audit102-online/ipv6.mjs`; its assertions check the 200 control, zero adapter requests and exact TLS error.

### MW102-09 — Long watch durations overflow Node's timer

Locations: `src/commands/watch.ts:107–112`, `:140–145`, `:378`. `--until` accepts durations far beyond a signed 32-bit millisecond timer.

**Observed:** compiled watch with `--until 25d` and a valid synthetic registration returns success in approximately 635 ms. Node clamps the oversized timeout to one millisecond. Installed warning suppression hides the timer warning. The documented duration is accepted but provides effectively no observation.

Fix: reject values beyond the supported timer range, or schedule long durations in bounded chunks against a monotonic deadline. Regression: the maximum accepted duration and values just above 2^31−1 milliseconds must not immediately expire.

Proof: second result in `audit102-watch/delta-results.txt`. This is a timer/control-flow probe, not a 25-day real-LND run.

### MW102-10 — An incomplete stage is presented as ready to switch

Locations: `src/commands/respond.ts:92–94`, `:193`, `:219`.

A failed/uncertain stage can leave an active pending allocation with `verified:false`, `outPath:null` and possibly no fingerprint. Rerun the staging command as recovery guidance instructs.

**Observed on compiled 1.0.1 command:** exit 0, `staged-earlier`, null output path, advice to switch the app and run finish. No file or acceptance check occurs; finish cannot use the missing file. The pending ID is preserved safely, but the recovery description is misleading.

Fix: distinguish allocated/incomplete replacements from verified completed stages; report unresolved work and actionable numeric-ID recovery. Do not blindly retry an uncertain mutation. Regression: an incomplete entry must never be described as a usable replacement.

Proof: `audit102-online/probe.mjs`.

### MW102-11 — Report formats lose review evidence

Locations: `src/report/access-review.ts:127–134`, `:152–153`, `:165–168`. Reference: SPEC N7.

The structured review carries rotation links, generated time, node/version, control observations, sign-off and compliance limitations. Markdown drops replaces/replacedBy. CSV keeps credential columns, including rotation links, but drops the report-level identity/time, controls, sign-off and limitation statement. The plain CSV also omits the new explicit canary-use details; flags can indicate triggering but not its count/timestamps.

Impact: exported artifacts do not contain all the evidence the format's documented contract promises. JSON retains the information.

Fix: define a complete, usable representation for each format, or explicitly document a credential-table-only CSV export. Preserve rotation linkage in Markdown and canary details where promised. Test required information across all formats, not only headers and CSV escaping.

Proof: `audit102-watch/probe-current.mjs` confirms missing Markdown links; serializer inspection and the actual Polar reports confirm format omissions.

### MW102-12 — Two commands have no published JSON schema

Locations: `schemas/output/`, `scripts/output-schemas.mjs:58`; packed package `files`.

The actual 1.0.1 tarball contains nine schema files: eight command schemas plus registry-entry. Watch and recommend have none, and the schema generator does not generate them. This falls short of the documented every-command output-schema claim and leaves integrations unable to validate those outputs. Watch also needs to distinguish NDJSON events from the final envelope.

Fix: add the recommendation envelope and watch event/final-result schemas, or narrow the public schema guarantee until they exist. Regression: validate real emitted outputs, including negative paths and all watch event types, against shipped schemas.

Proof: `audit102-polar/packaging-results.json`, `missingCommandSchemas:["watch","recommend"]`.

## Limits and follow-up

- No full suite was repeated; the release's Windows/Linux runs belong to its existing validation. This audit used targeted adversarial checks. Dynamic audit checks ran on Windows; Linux-specific behavior was source-reviewed but not independently executed here. Polar is 0.20.0, not the pinned 0.21.4 fixture, and no mainnet node was contacted.
- Alert shutdown uses an injected timed callback. A real Windows orphaned child/tree remains a required regression probe. No claim of measured 120-second completion is made for include fan-out.
- Two review sessions ended before completing. Their completed observations were retained, but there is no claim that the credential-focused review finished. An unfinished Git config syntax-validation lead is not counted as a confirmed finding.
- No real GitHub token or NWC secret was used, persisted in evidence, or sent to a service. The GitHub test repository, real relay/wallet integration and hosted Actions were not exercised.
- This is a finite audit, not proof that every possible edge case is covered. Follow-up should include Linux/macOS filesystem variants, real Windows alert cancellation, sustained real-node middleware/reconnect load, and matching the published npm artifact to its source commit.

## Cleanup and suggested repair order

All eight remaining audit-owned root keys, including the session, were revoked after testing. `listmacaroonids` returned only the original ID `0`; none of the audit-owned IDs remain live. Temporary credential copies inside Alice were removed. No wallet state, root key 0, channels, funds, test fixtures or source files were modified. Revoked audit outputs and evidence remain in the private audit checkout for reproduction; no new dependency tree was installed.

Suggested 1.0.2 order:

1. Enforce decoded-file canary preservation and recommendation selector consistency.
2. Fix respond finish repair and incomplete-stage recovery; prove these on real LND.
3. Correct coverage accounting and long timers; cancel pending/active alert work within one shutdown budget.
4. Bound Git location validation and sidecar reads; refuse protected symlink targets.
5. Fix IPv6 transport, report completeness and missing command schemas.
6. Run affected regressions during repair, then one complete Windows/Linux milestone validation on the exact release candidate. Preserve failing observations and verify the packed release artifact.

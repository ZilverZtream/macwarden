# macwarden — specification

Safety rules SAFE-01 … SAFE-11 are defined in [security-model.md](security-model.md); module boundaries, verified LND facts and the numbered assumptions are in [architecture.md](architecture.md). This file is the single source of behaviour: where another document disagrees, this one wins and the other is corrected.

## Purpose and audience

macwarden is a CLI for LND node operators: see what a macaroon can do, find credentials lying around, keep a record of what was issued to which app, issue least-privilege macaroons that can each be revoked, and rotate them without locking yourself out. Audience: anyone running LND behind BTCPay Server, LNbits, RTL, ThunderHub, a custom backend or an AI agent.

## Non-goals (v1)

- Rotating or deleting root key ID 0, calling `changepassword`, touching `macaroons.db`, wallet passwords, seeds, TLS keys or LND config (SAFE-02, SAFE-03).
- IP-locked macaroons from `bake`: `bake` has no `--ip` (REST clients appear to LND as the REST proxy; architecture.md assumption 5). `inspect` still decodes `ipaddr`/`iprange` caveats. The offline `attenuate` command can add an `ipaddr` or `iprange` caveat to a copy, with warning `ip-caveat-rest-proxy`.
- gRPC (except `watch`, which needs a bidirectional stream; see Commands > 8), Tor/SOCKS, online Core Lightning rune management (`inspect` and `scan` handle runes offline from 1.2.0, see Core Lightning runes), LNbits keys, Eclair, LDK. App-specific presets are deferred except the source-pinned BTCPay Server v2.4.4 preset (each preset needs an integration test; the exact supported call inventory is in [references.md](references.md#btcpay-server-preset)).
- Baking external permissions: macwarden never sends `allow_external_permissions: true`, and refuses to bake `UNASSESSED` permissions.
- Storing credentials in a keychain, telemetry (SAFE-08). See Commands > 2. scan for optional git history scanning. A watch mode was a v1 non-goal until the owner added `macwarden watch` on 2026-10-07 (Commands > 8); it records only credential identities, method names, counts and times, and, with `--payment-journal` (1.2.0), the payment hash, requested amount and fee limit of payment requests.
- Registering, rotating or revoking NWC connections (deferred, not impossible): core NIP-47 defines no call to create or revoke a connection. Some wallet services add their own; Alby Hub has a `create_connection` NWC command and an HTTP API that deletes a connection. Rotation through such a service needs a relay and wallet-API network peer, Schnorr signing and NIP-44 encryption, so it is left for a later release with its own [security model](security-model.md) review. `inspect` decodes an NWC URI offline.
- Issuing, paying for or revoking L402 tokens. `inspect` decodes an L402 (formerly LSAT) credential offline and `scan` finds them (1.2.0); only the service that issued a token can revoke it, and macwarden never contacts it.

## Global conventions

- Printed commands (recovery, suggestions and hints) quote each argument for the shell the operator pastes them into: POSIX single quotes, or on Windows PowerShell single quotes with every `'` and every U+2018–U+201B doubled, because PowerShell ends a single-quoted string at any of them. On Windows the commands are for PowerShell; cmd.exe does not treat single quotes as quotes. Control characters in a value are escaped by the text renderer, so a printed command can never carry a line break or a terminal escape.

### Inputs that are credentials

- A credential argument is a file path or `-` (stdin). A literal credential on the command line (rule 3) is refused with exit 2 and the message "pass a file path or - (stdin); literal credentials end up in shell history and process listings", unless `--unsafe-arg` is given; then it is accepted and warning `unsafe-arg` is emitted. No message ever echoes the argument (it may be a credential or a mistyped one).
- `readCredential` rules (architecture.md), in order:
  1. `-`: read non-TTY stdin to EOF, accepting at most 1,048,576 raw bytes and reading at most the first excess byte. Overflow → exit 3, stage `input-read`, before decoding and without echoing content. stdin is a TTY → exit 2 (no hang). Empty input → exit 3, stage `input-form`.
  2. First probe whether the argument names an existing path. An existing path with any protected supplied or resolved file or directory component is refused before content open with exit 3, stage `input-read`, without echoing the argument. Windows stream base names are checked too. The case-insensitive protected-name set is the union of `macaroons.db`, `wallet.db`, `*.key`, names matching `/(^|[._-])(password|passwd|seed)([._-]|$)/i`, and the legacy families `^wallet[-_.]?password(?:\..+)?$`, `^seeds?(?:\..+)?$`, and `^tls[-_.]?(?:key|privkey)(?:\..+)?$`. An existing protected path takes file-input precedence; otherwise, an existing path that is a directory or unreadable file → exit 3, stage `input-read`. Read at most 1,048,577 raw bytes; 1,048,576 bytes are accepted for parsing, and the first excess byte → exit 3, stage `input-read`, before decoding and without echoing content. This bound also applies if the file grows while read. Content whose first byte is `0x02` is binary. Otherwise it is text: strip a UTF-8 or UTF-16 (LE/BE) BOM, decode, trim, then parse as in rule 4.
  3. When no existing path is established, a recognized supported credential literal follows this rule even if its encoded text contains a protected-looking component. With `--unsafe-arg` it is parsed as a literal under rule 4 (`literal: true`); unparseable → exit 3, stage `input-form`. Without `--unsafe-arg` it is refused as a literal credential (exit 2) only if it is an `lndconnect://` URI, or it decodes under rule 4 as hex or base64/base64url to bytes whose first byte is `0x02`. A nonliteral argument with a protected component is refused at `input-read` without content open. Any other argument → exit 3, stage `input-read`, message "no such file" (so `macwarden inspect admin` with no file `admin` says "no such file").
  4. Text forms, checked in this order: an `lndconnect://` URI (scheme case-insensitive; exactly one `macaroon` query parameter, percent-decoded exactly once, then canonical base64url, unpadded or with exactly the required trailing padding; reject plus, slash, whitespace, malformed or remaining percent escapes, misplaced or excess padding, and noncanonical unused bits as `input-form`); after removing whitespace and line breaks, hex (`^(0x)?[0-9a-fA-F]+$`; odd length → `input-form`; a string of hex digits is always treated as hex, never base64); base64 or base64url, padded or unpadded. Anything else → `input-form`. `inspect` alone reads NWC URIs, L402 text and Core Lightning runes before these forms, and Aperture token store files before text (Commands > 1. `inspect`, input precedence).
- Decoding errors are exit 3 with a stage: `v2-header` (first byte not `0x02`; a v1 macaroon, binary or base64 `MDAx…`, gets the message "macaroon v1 format is not supported"), `packet` (bad or over-long varint, length past end, unknown packet type, fields out of order, header without identifier, caveat with a verification ID but no identifier, missing final end-of-section, missing or short signature; packet kinds, lengths and end-of-section markers are read as go-macaroon v2.0.0 reads them with `binary.Uvarint`: up to 10 bytes, non-minimal encodings accepted, a value above 0x7fffffff refused, and any encoding of 0 (`0x00`, `0x80 0x00`, …) is an end-of-section, because LND accepts such a re-framed copy and anyone holding the macaroon can produce one without the root key), `identifier-version` (identifier does not start with `0x03`), `identifier-proto` (the identifier is refused where LND's protobuf decoder refuses it: truncated protobuf, field number 0 or above 2²⁹−1, wire types 6 or 7, an end-group without its start, a group that is unterminated, closed with another field number, nested more than 10,001 deep or holding a member field number above 2³¹−1, an entity or action that is not valid UTF-8, or a first op with no actions, which bakery refuses as "no operations found"; wire types 0, 1 and 5 and unknown groups are skipped, varints may be non-minimal, and a field with an unexpected wire type is skipped as an unknown field), `identifier-root-key-id` (`storageId` empty, non-digits, leading zeros, or > 2⁶⁴−1); for L402 input to `inspect` also `l402-form` and `l402-preimage` (Commands > 1, L402 input). Every op after the first is expanded as bakery expands it, `entity:action` for each action in order: an op with an empty entity gives `:action` (graded unassessed), an op with no actions gives nothing. Expansion is bounded, and a bound never refuses a macaroon LND honours: an op whose entity is over 16 bytes, and an action over 256 bytes, are left out, and nothing more is kept once 1,024 permissions or 64 KiB of permission text are reached; LND v0.21.4 has 164 RPC methods across 19 entities of at most 8 bytes, so real macaroons stay far below, and these bounds keep expansion to about 6 bytes of permission text per identifier byte. When anything was left out the facts carry the warning `identifier-exceeds-bounds` and the grade fails closed (Grading). At most 4,096 caveats are kept; further caveats are parsed and checked but not reported, with the warning `caveats-exceed-bounds`. The stage `identifier-limits` is no longer produced. A text-borne candidate that fails these checks is reported as `undecodable-candidate` and counted as ADMIN.

### Online commands

- Flags: `--lnd-rest <host:port>` (an IPv6 address in brackets, `[::1]:8080`; TLS then verifies the certificate's IP address SAN for the bare address), `--tls-cert <path>`, `--macaroon <path>` (env: `MACWARDEN_LND_REST`, `MACWARDEN_TLS_CERT`, `MACWARDEN_MACAROON`; `watch` adds `--lnd-grpc`/`MACWARDEN_LND_GRPC`). The node address, its certificate and the credential macwarden presents come from one source: with no connection flag, all come from the environment; when any connection flag is given, all come from flags, and a connection variable that is set for a setting not given as a flag → exit 2 naming the variables (never their values). So a credential exported for one node is never presented to a node named on the command line, nor a credential given on the command line to a node named in the environment. `--macaroon` is macwarden's own dedicated credential (SAFE-09) and must be a path; credential text there → exit 2.
- Every online command begins with two offline checks, referred to below as **ENV** and **OWN**:
  - **ENV:** `NODE_DEBUG` naming `http`, `https`, `tls` or `net`, or any nonempty `NODE_OPTIONS` → exit 2 (these would write request headers, including macaroons, to stderr or report files). `inspect` and `scan` apply the same check (1.2.1): a heap snapshot or profile would hold every credential they decode. A diagnostic Node flag on the command line (`node --inspect …/bin.js`, a CPU or heap profile, a heap snapshot, a diagnostic report, tracing, a TLS key log; `process.execArgv`) → exit 2 before any command runs, and `watch` on a Node version outside package.json's `engines` (its HTTP/2 client depends on those releases) raises warning `unsupported-node` first.
  - **OWN:** read the TLS cert and decode macwarden's own macaroon offline; unreadable, undecodable, or missing a permission the command needs → exit 4 naming the problem, with zero LND calls. For each method a command calls, either the entity:action permission(s) the method requires or `uri:` for exactly that method satisfies the check. Own macaroon on root key ID 0 → warning `own-root-key-0` (allowed: first-time setup uses `admin.macaroon`).
- After GetInfo, every online command calls ListPermissions once; if the method set or any method's required permissions differ from the bundled snapshot it adds warning `snapshot-drift`. `respond` makes this check itself at P4, also in a dry run and when nothing is rotated; the rotations it runs repeat it for their own results. A failed call stops the command like a failed GetInfo (exit 4/5). Grading still uses the bundled snapshot in v1.
- `revoke` and `rotate` refuse (exit 2) to touch the root key ID of the macaroon macwarden itself is using.
- LND errors are classified by HTTP status and message text (architecture.md): transport, TLS or auth failure (401/403) → exit 4; LND returned an error and nothing changed → exit 5.
- **Verify accepted** means CheckMacaroonPermissions with the macaroon and its own decoded permissions as the permission list (`uri:` permissions are passed as `uri` entries; `fullMethod` and `check_default_perms_from_full_method` are never used) returns `valid: true`. **Verify rejected** means the same call fails with the root-key-missing error or the independently observed HTTP 400 target signature-mismatch response. Authentication and unknown errors are neither. A signature mismatch alone never proves a credential dead: LND gives it after a root key regeneration (which keeps every root key ID listed) and equally for any altered copy (a flipped byte, a mangled paste, a decoy) of a credential that is still accepted. `revoke`, `rotate --finish` and `respond --finish` therefore use **Verify rejected** only after ListMacaroonIDs shows the root key ID absent, on bytes LND accepted in the same run or whose fingerprint matches the registry; `verify` treats it as conclusive only when the root key ID is no longer listed or the file is the exact credential the registry recorded for that root key ID on this node (review RT-01). An empty permission list is never sent.
- After a failure, macwarden makes at most one ListMacaroonIDs call and no other LND call, except after DeleteMacaroonID errors or returns `deleted:false`: if that one reconciliation proves the target ID absent, only the prescribed V12/F11 read-only acceptance/rejection proofs may continue. The mutation is never retried; a subsequent proof failure stops and reports uncertainty. If LND's state cannot be read after a mutating call was sent → exit 7 "LND state unknown — run `macwarden inventory`".
- Revocation scope (printed at the end of every successful `revoke` and `rotate --finish`): "New requests with this macaroon are now rejected. Streams opened before the revoke stay open until they disconnect; if the credential may be compromised, restart LND."

### Registry and lock

Operator safety amendment (CP-038): existing registry parent permissions and sticky bits are preserved. Only directories created by this run are secured; an existing parent granting group/other write access is refused on POSIX. A stale lock is recovered with --break-lock only after matching verified process-domain identity, same-host dead-process proof and regular-file pathname identity checks; all cooperating acquisitions use an exclusive short-lived <registry>.lock.claim guard, then rename to a unique quarantine and verify the moved inode and owner before removing it. Changed ownership is preserved for offline recovery. A stale lock is not automatically removed when process namespace or pathname ownership cannot be established. Stop all writers, establish that the recorded process is gone in its namespace, and remove the lock offline before retrying.

Before BakeMacaroon, persist a credential-free pending allocation with `verified:false`, `outPath:null`, and `fingerprint:null`; interruption and uncertain response preserve this recovery record. A known credential always records its canonical fingerprint. An unknown-fingerprint unregistered revocation tombstone may likewise use null only with `verified:false` and `outPath:null`. Confirmed absence after a failed issue removes the pending allocation. Final issue replaces the pending record through the registry API. Signals SIGINT/SIGTERM and supported SIGHUP cancel cooperatively, release owned locks and remove unwritten reservations; possible mutation reports exit 7 and recovery. Pre-mutation interruption reports exit 6, step cancelled, message interrupted. A signal during the save of the pending allocation, or a save that fails (possibly after its rename landed), happens before BakeMacaroon: the record is removed again before exit 6 (or exit 3 "cannot record pending issued ID; nothing sent to LND"), so those exits still mean nothing changed; if the registry on disk still holds the record afterwards (or cannot be read), the exit is 7, saying nothing was sent to LND and naming the root key ID with `macwarden inventory` and `macwarden revoke <id>` (which records the absent ID through V7) (1.1.1, RL-08). Cleanup failures are visible; after possible mutation they report exit 7, while an existing primary failure retains its step and exit with cleanup diagnostics. SIGKILL cannot run cleanup.


- `--registry <path>` overrides the default registry (`$XDG_CONFIG_HOME/macwarden/registry.json`, falling back to `~/.config/…` on Linux; `~/Library/Application Support/macwarden/registry.json` on macOS; `%APPDATA%\macwarden\registry.json` on Windows). Format below.
- Mutating commands take the lock file `<registry>.lock` (created exclusively; holds pid, hostname, start time, process domain and, from 1.1.1, `token`: a random per-acquisition UUID; records without a token from earlier versions stay valid). Release removes the lock only while it is still this acquisition's file and record: same device, inode and birth time, and an owner record (read as a lock owner record, below) byte-identical to the one written, token included, because a file system may give a freed inode number to the next file at once. A lock replaced by another owner is left in place and release reports exit 3 "cannot release registry lock". A byte-identical copy of this acquisition's own record, token included, is by design indistinguishable from the lock itself and is not treated as a replacement: only a party that can already read and rewrite the lock directory can produce it, and such a party can remove or forge any lock anyway. Lock exists → exit 3 "registry locked by pid <pid> on <host> since <time>", nothing sent to LND. `--break-lock` (on `bake`, `revoke`, `rotate`) recovers a stale lock only under the proof in the Operator safety amendment above (same host, recorded pid not alive, matching recorded process domain, regular-file identity); legacy records without a process domain, and platforms without a supported domain query (currently anything but Windows and Linux), are refused; otherwise exit 3. No lock is ever held while waiting for input. Every exit releases a lock the run took, and removes an `--out` file the run reserved but did not write.

### Output

- `--json` on every command prints exactly one JSON document to stdout and nothing else: `{"schema":1,"command":"<name>"|null,"ok":<bool>,"warnings":[…],"result":{…}|null,"error":{"code":<exit>,"step":"<id>"|null,"message":"…"}|null}`. `command` is `null` for an unknown command (the argument is never echoed). `warnings` holds invocation warnings (`unsafe-arg`, `own-root-key-0`, `snapshot-drift`, `acl-best-effort`); in text mode they go to stderr as `warning: <code>: <message>`. `error.step` is the step id below where the command stopped, or for input and decoding errors the stage name; `internal` for exit 8; `null` for argument-parsing errors and for every exit-2 error of `inspect` and `scan`. Only `result` shapes are shown below. Every command's envelope is fixed by a JSON Schema (draft 2020-12) in `schemas/output/<command>.schema.json`, shipped in the npm package: `inspect` and `scan` are hand-written; `inventory`, `bake`, `revoke`, `rotate`, `attenuate`, `watch`, `recommend`, `respond`, `verify` and `reconcile` are generated by `scripts/output-schemas.mjs`, as are `macwarden.schema.json` for the documents with `command: null` and `payment-journal-record.schema.json` for one line of the payment journal (Payment journal format) (`macwarden --help --json`, and a usage error before any command is known) (`--check` fails when a file is stale), from the inspect and registry-entry schemas, so shared definitions have one source. Tests validate every command output they produce against these schemas.
- Exception: `watch --json` prints one JSON object per line while it runs (events, each with `"schema":1` and an `event` field), then the final document above as the last line. Event lines follow `schemas/output/watch-event.schema.json` (one variant per event: `call` and `error`, `canary`, and `status` with `registered` or `reconnecting`, `output-dropped`, `alert-failed`, `payment-journal-stopped`); the final document follows `watch.schema.json` and is the only line with a `command` field.
- `ok` is `false` exactly when `error` is not `null`. `scan` exiting 1 for `--fail-on` is `ok: true`, `error: null`.
- Root key IDs are uint64 and are always decimal strings in JSON. Every root key ID macwarden reads (registry `rootKeyId`, `replaces` and `replacedBy`, usage and canary records in the usage file, and the `revoke` and `recommend` selectors) must be canonical: digits only, no leading zero except `0` itself, at most 18446744073709551615. One rule, shared by every reader, so no file or selector carries an ID another part refuses.
- Fingerprint: `fp:` + first 16 lower-case hex chars of SHA-256 over the canonical binary macaroon: the bytes go-macaroon's `MarshalBinary` writes for it (minimal varints, one-byte end-of-section markers, no empty location or verification ID packets, ending with its signature packet; trailing bytes excluded). Every macaroon LND or macwarden writes is already canonical, so its fingerprint is SHA-256 over its own bytes up to the signature; a re-framed copy of the same credential gets the same fingerprint. The credential ID (`id:`, used by `watch` and `recommend`) hashes the identifier packet's contents, which re-framing never changes. Credentials appear only as fingerprints (SAFE-01). An NWC finding's fingerprint is over its 32-byte `secret`. Fingerprints are not secret but are linkable across reports, and change when a caveat is added.
- Text output escapes control characters (C0, DEL, C1) in file paths and LND-supplied strings as `\xNN`, so nothing can inject terminal escapes. It also escapes, as `\uNNNN`, the Unicode bidirectional controls and every Unicode whitespace character other than the plain space (U+00A0, U+1680, U+2000 to U+200F, U+2028 to U+202F, U+205F, U+3000, U+FEFF). So that a name cannot look like a different file, it also escapes every invisible character: each Unicode format character (general category Cf, for example U+00AD, U+200B to U+200F, U+2060 to U+206F, U+FEFF and the tag characters U+E0000 to U+E007F), the Hangul fillers (U+115F, U+1160, U+3164, U+FFA0), U+034F, U+17B4, U+17B5 and the variation selectors (U+180B to U+180F, U+FE00 to U+FE0F, U+E0100 to U+E01EF). Characters below U+0100 are written `\xNN`, characters beyond U+FFFF `\u{N}`. It writes the legacy CI marker `##[` as `##\x5b`. No text line can begin, after spaces, with `::`: a CI runner (GitHub Actions) would read it as a workflow command such as `::stop-commands::` or `::add-mask::`. A scanned path that starts that way is printed as `./path`, and any other such line start is written as `\x3a:`. `--format github` output is the exception by design: each annotation is produced by macwarden and its file name and text are escaped as workflow-command data.
- Help: `macwarden --help` prints the usage and the command list; `macwarden <command> --help` prints that command's synopsis as given in its section below (an operand `--help` after `--` is not a request for help). With `--json` (for `scan` also `--format json`), command help is the single JSON document of the Output rules: `{"schema":1,"command":"<name>","ok":true,"warnings":[],"result":{"usage":["macwarden <name> …", …]},"error":null}`, one `usage` line per synopsis line without the `Usage:` prefix; every command's schema accepts this `help` result (audit 1.1.0, MW110-10). `macwarden --help --json` is likewise one document, `{"schema":1,"command":null,"ok":true,"warnings":[],"result":{"usage":["macwarden <command> [options]","macwarden <command> --help","macwarden --help | --version"],"commands":[{"name","summary"},…]},"error":null}`, with the commands and summaries of the text help. Both exit 0. A missing command, an unknown command or an unknown leading flag exits 2 with `error: usage: missing command`, `unknown command` or `unknown flag` on stderr followed by the usage; the argument itself is never echoed.
- Caveats in output: `{"type","value"}`, plus `"expired": <bool>` only for a parseable `time-before`. `type` is `time-before`, `ipaddr`, `iprange`, `lnd-custom`, `third-party` or `unknown`. `value` is verbatim from the macaroon, never normalised: for a first-party caveat, `type === "unknown" ? value : type + " " + value` equals the caveat string. A third-party caveat's `value` is its location from the macaroon bytes (`lncli printmacaroon` prints the raw caveat id instead, so the two are not comparable). `expired` is true when now ≥ the instant. A `time-before` value is parseable exactly when bakery's check, Go's `time.Parse(time.RFC3339Nano)`, accepts it: `YYYY-MM-DDThh:mm:ss`, then optionally `.` or `,` and any number of digits (nanoseconds kept), then `Z` or `±hh:mm`; Go's general parser also accepts a one-digit hour, a zone offset hour of 24 and an offset minute of 60, and so does macwarden, with the instant LND computes. Unparseable `time-before` → no `expired`, warning `bad-time-before`. `ipaddr`/`iprange` are annotated in text output: "enforced against the address LND sees; REST clients appear as the REST proxy".

### Exit codes

| Code | Meaning |
|---|---|
| 0 | Success. |
| 1 | A finding, with `ok: true`: `scan`, at least one finding counts at or above `--fail-on`; `inventory --expiring-within`, an active credential is expired or expiring; `verify`, LND accepts the credential or its rejection is not conclusive; `reconcile`, the reconciliation is incomplete (a coverage gap, an unattributed payment, a journaled payment without a final outcome, and the other cases in Commands > 12). |
| 2 | Usage or refused request: bad or missing flags, unknown preset, invalid label, malformed root key ID, root key ID 0, literal credential without `--unsafe-arg`, `-` on a TTY, ENV check, `UNASSESSED` or unallowed `ADMIN` permissions in a bake, label conflict, unregistered ID without `--unregistered`, macwarden's own root key ID, another node's entry, pending rotation, mismatched `--target-file`, `attenuate` without a caveat flag or with an invalid `--expires`, `--ip` or `--ip-range`. |
| 3 | Input error: unreadable or undecodable input, unreadable, invalid or locked registry, `--out` already exists or is a protected path, a `scan` path argument that does not exist or cannot be read, a `scan --git-history` failure (step `git-history`: not a work tree, git unavailable, unreadable or missing objects, timeout, too large), a `scan` that would report more than 250,000 findings (step `findings-limit`), invalid ignore file, registry entry that does not match its credential file. |
| 4 | Cannot talk to LND: unreachable, TLS failure, HTTP 401/403, or the OWN check failed. |
| 5 | LND returned an error response or refused, and LND was **not** changed; any old credential is still valid. A mutating request that got no complete response (timeout, reset, cancellation) never exits 5: its outcome is unknown, so it exits 7. |
| 6 | `scan` interrupted (SIGINT, SIGTERM or SIGHUP; nothing is changed), or: operator declined, typed the wrong text, or confirmation was needed but stdin is not a TTY and `--yes` was not given. |
| 7 | LND was changed (or may have been) and a later step failed or could not be confirmed, including a mutating request whose outcome is unknown because no complete response arrived. The message states the observed LND state and the exact command to finish or undo; paths in printed commands are absolute. |
| 8 | Internal error (a bug): an unexpected exception anywhere. `error.step` is `internal`; the message contains no input and no stack, and if LND may have been changed it also says "run `macwarden inventory`". |

When several refusals apply, the lowest-numbered step wins.

## Grades

The ladder is `ADMIN` > `SPEND` > `OPERATE` > `RECEIVE` > `READ`. Each permission gets a class; the grade is the highest class among the permissions. `UNASSESSED` is not a rung: any permission the table and the bundled snapshot cannot assess makes the result `UNASSESSED`, unless the assessed permissions already give `ADMIN` (then `ADMIN`, still with the `unassessed-*` warning and the `unassessed` list). `UNASSESSED` is rendered in text as "UNASSESSED (treat as SPEND or worse)", fails every `--fail-on` threshold, and is never baked. Caveats never change the grade.

`grade(perms)` returns `{grade, reasons, warnings, unassessed}`: `reasons` = the permissions whose class equals the grade (empty for `UNASSESSED`); `unassessed` = the permissions that could not be assessed, verbatim; `warnings` from the table below. Duplicates are ignored; all three lists are sorted (UTF-8 byte order). `grade([])` → `UNASSESSED`, warning `no-permissions`. `gradeFacts(facts)` grades decoded facts: when they carry `identifier-exceeds-bounds`, the permissions left out count as unassessed, so the grade is `UNASSESSED` unless the kept permissions already give `ADMIN`, with the warning `identifier-exceeds-bounds` (instead of `no-permissions` when none were kept). `inspect`, `scan`, `attenuate` and `revoke` grade decoded macaroons this way.

| Permission | Class |
|---|---|
| `macaroon:generate`, `macaroon:write` | `ADMIN` (can mint or revoke credentials) |
| `onchain:write`, `offchain:write`, `signer:generate` | `SPEND` (can move funds) |
| `peers:write`, `info:write`, `message:write` | `OPERATE` (change node state without moving funds) |
| `invoices:write`, `address:write` | `RECEIVE` |
| any other known entity with action `write` or `generate` (e.g. `onchain:generate`, `signer:write`) | `SPEND` (not assessed individually, so it fails closed) |
| any known entity with action `read` (including `macaroon:read` and `signer:read`) | `READ` |

## Core Lightning runes (1.2.0)

`inspect` and `scan` also handle [Core Lightning](https://github.com/ElementsProject/lightning) runes. The reference is Core Lightning v26.06.8 (image `elementsproject/lightningd:v26.06.8@sha256:56f1cebe829fbb3c7d5674be8cd1212c7e02527ab32403b695033a29bcd2abce`): `ccan/ccan/rune/` (coding.c, rune.c), `ccan/ccan/base64/` and `lightningd/runes.c`. `lightning-cli decode` already decodes a rune; macwarden adds finding runes in files and history without printing them, and a conservative assessment of what their restrictions may allow. Everything here is offline: macwarden never calls `checkrune` or any other node method for a rune, and online rune management (`createrune`, `showrunes`, `blacklistrune`) is out of scope.

**Format and parser.** A rune is URL-safe base64 of a 32-byte authenticator followed by the restriction text; it does not start with a binary unique ID. macwarden decodes it exactly as Core Lightning does, not with Node's base64 decoder: only `A–Z a–z 0–9 - _`; every group of four characters but the last must be complete; the last group of one to four characters may end in any number of `=` (all dropped) and must keep at least two characters, and its unused bits are ignored; `+`, `/`, whitespace and `=` before the end are refused. Fewer than 32 bytes, or a NUL byte in the restriction text, is not a rune. The restriction text is parsed as `rune_restr_decode` parses it: restrictions are separated by `&` and all must pass (AND); alternatives within a restriction are separated by `|` and any may pass (OR). An alternative is a field name (every byte up to the first ASCII punctuation character other than `_`), one condition character and a value up to the next unescaped `|` or `&`; `\` escapes the next byte, which stays part of the value. Conditions: `!` field missing, `=` equal, `/` not equal (not a regular expression), `^` starts with, `$` ends with, `~` contains, `<` `>` integer comparison, `{` `}` lexical (byte) comparison, `#` comment. Any other condition character, an empty restriction, a trailing `|` or a dangling `\` makes the text invalid; a trailing `&` is accepted, as Core Lightning accepts it. Field names and values are kept as bytes; output shows them as UTF-8, with invalid bytes as `\xNN`.

**Unique ID and version.** An alternative with an empty field name is the unique ID: it must be the only alternative of the first restriction, with condition `=`; anywhere else the rune is invalid. Its value is the unique ID up to the first `-` and the version after it, both kept as strings. The unique ID is not the `id` field, which restricts the requesting peer's node ID. The unique ID alone is not a global identity: runes from different nodes share small IDs.

**Bounds.** At most 8,192 characters of rune text, 256 restrictions (the unique ID included) and 1,024 alternatives in all are parsed. A rune beyond a bound is not parsed in part: `inspect` refuses it as not a rune, and `scan` reports a `rune-invalid` finding with reason `exceeds-bounds`, so no assessment ever comes from a truncated policy.

**Recognition, assessment, verification.** Three things are reported separately. Recognition (`recognition: "rune-syntax"`): the text parses as a rune. Assessment: which capabilities its encoded restrictions may allow. Verification (`verification: "unchecked"`, always): whether the rune is authentic, which node issued it, whether its unique ID is blacklisted and its rate-limit state are never checked offline, so nothing macwarden reports says a node would accept the rune. Warnings predict how Core Lightning v26.06.8's `checkrune` treats a rune without consulting a node: `no-unique-id` (checkrune refuses runes without a numeric unique ID), `unique-id-not-numeric` (not a decimal of at most 2⁶³−1, read as `strtoull` reads it; an empty ID reads as 0), `unique-id-out-of-range` (100,000,000 or more: Core Lightning treats such a rune as blacklisted), `version-suffix` (Core Lightning's master rune has no version, so a versioned rune fails its derivation check), `non-canonical-encoding` (the text is not what Core Lightning writes for these bytes: missing or extra padding, unused bits set, an unnecessary escape or a trailing `&`; such a rune can still be accepted).

**Assessment.** The vocabulary is the grade ladder (Grades). Each request names a method (commando and clnrest always pass one). For every method in the pinned method table, and for a method the table does not list, each alternative is true, false or unknown for that request:

| Field | Evaluation |
|---|---|
| `method` | the condition applied to the method name; `<` `>` and `!` are false (a string field, always present) |
| `time` | unknown for capabilities (it depends on when the request is made); `!` false; `<` `>` with a value that is not a 64-bit integer (as `strtol` reads it) false; `#` true |
| `id` | unknown (the requesting peer, absent for a local call); `<` `>` false; `#` true |
| `pnum` | unknown; `!` false; `<` `>` with an invalid integer false; `#` true |
| `rate`, `per` | unknown when Core Lightning accepts the value (condition `=`, a count from 1 to 4,294,967,294 as `strtoul` reads it, so a negative count wraps modulo 2⁶⁴, for `per` a unit `sec`, `nsec`, `usec`, `msec`, `min`, `hour` or `day` without overflow); otherwise false, a comment included |
| `pinv…` | unknown when the name ends in `_amount`, `_description` or `_node`; otherwise false |
| `pname…`, `parr…`, any other field | unknown; `#` true. A field Core Lightning v26.06.8 does not know is kept as an assessment limitation (warning `unknown-field`) and never excludes anything |

A restriction rejects a request only when every alternative is false. A method may be allowed unless some restriction rejects it: **a capability is excluded only when the complete restriction structure proves that no request for it can pass**, so the assessment can overstate access and never understates it. When every alternative of a restriction is `method=<name>` or always false, the restriction pins the method to that finite set; the sets of all pinning restrictions intersect (`methods: "listed"`, `allowedMethods` lists the reviewed ones that may pass). Without a pin any method name may pass (`methods: "broad"`, warning `broad-method-access`), unless a restriction rejects every method; when no method can pass, `methods` is `"none"` (warning `no-matching-method`).

`capabilities` lists the classes of every reviewed method that may pass, highest first. The grade is the highest of them, except that it is `UNASSESSED` when any method outside the table may pass (a broad rune, or a pinned name the table does not list, warning `unreviewed-method`, listed in `unassessed`) or a method of class `UNASSESSED` may pass, unless the highest class is `ADMIN`. A rune that matches no method is reported at `READ`, the lowest grade, with `methods: "none"`: it allows nothing macwarden can find, and it is still a credential in a file. `reasons` lists the reviewed methods whose class equals the grade. Peer, parameter, rate and time restrictions are listed in `conditions` (`peer`, `parameter`, `rate`, `time`, `unknown-field`) and in `restrictions`; they never lower the grade. A spending rune stays `SPEND` when it limits amounts: a parameter condition such as `pnameamount_msat<10000` limits each call, not a cumulative budget (warning `parameter-limits-not-a-budget` when parameter conditions accompany possible spending).

| Restrictions | Result |
|---|---|
| `method=getinfo` | `READ` |
| `method=pay` | `SPEND` |
| `method^list` | `UNASSESSED`, `broad-method-access`, `sensitive-method` (`listdatastore`, `listconfigs`), capabilities `READ`, `UNASSESSED` |
| `method^list\|method=pay` | `UNASSESSED`, capabilities `SPEND`, `READ`, `UNASSESSED` |
| `method/withdraw` | `ADMIN`, `broad-method-access`: excluding one spending method does not make a rune safe |
| `method=getinfo&method=pay` | `methods: "none"`, `no-matching-method`, `READ` |
| (no restriction) | `ADMIN`, `broad-method-access` |

**Method table.** `src/grade/cln-methods.ts` gives every command `lightning-cli help` lists on the pinned v26.06.8 fixture (built-in plugins and developer commands included, 210 commands) plus `clnrest-register-path` a class; the table names its release (`methodTable: "cln-v26.06.8"`) and the comparison test checks it against the node. Classes follow the LND grades: `ADMIN` for rune administration (`createrune`, `invokerune`, `showrunes`, `blacklistrune`, `destroyrune`), secret export and derivation (`exposesecret`, `makesecret`), node control that can run code or change configuration (`plugin`, `reckless`, `setconfig`, `recover`, the `dev` commands, `datastore`, `deldatastore`, `clnrest-register-path`, `bkpr-dumpincomecsv`, which writes a file at a path the caller chooses) and `commando`, which lets a peer run commands on the node with whatever rune it presents; `SPEND` for anything that moves or commits funds (payments, channel opens, splices, closes, withdrawals, PSBT signing and funding, input reservation, `funderupdate`, `setleaserates`, `invoicerequest`); `OPERATE` for node and peer actions that move no funds (`connect`, `stop`, `setchannel`, `signmessage`, `checkrune`, which updates usage state, askrene layers); `RECEIVE` for invoices, offers and addresses; `READ` for queries. `listdatastore` has class `UNASSESSED`: the datastore can hold credentials of other plugins, and Core Lightning's own `readonly` rune preset excludes it. Sensitive methods are named in `sensitiveMethods` with warning `sensitive-method`: `listdatastore`, `listconfigs` (returns `bitcoin-rpcpassword` and `tor-service-password`), `showrunes`, `exposesecret`, `makesecret`, `getemergencyrecoverdata`, `staticbackup`, `datastore`, `deldatastore`, `clnrest-register-path`, `bkpr-dumpincomecsv`. `method^list` is never assessed as `READ`: plugin methods can use any name.

**Expiry.** `time` holds UNIX seconds. macwarden compares with its clock (injected in tests) in whole seconds, with integer-safe parsing. A restriction closes the rune at time X when each of its alternatives is `time<V` (a valid integer, X being the largest V) or false for every request. `expiry.status` is `deadline-passed` when a closing restriction's X is not after the clock (text: "deadline passed according to local clock"), `deadline-ahead` when the earliest X is later, `time-conditions` when time conditions exist but no restriction closes the rune, and `none` otherwise; `deadline` is the earliest X as a decimal string, or `null`. `time<1600000000|method=pay` is not expired: `pay` still passes after that time, subject to the other restrictions. An expired rune keeps its assessment and is still reported by `scan`; node acceptance is not checked.

**Output.** Rune facts never include the authenticator or Core Lightning's decoded string (`lightning-cli decode`'s `string`, which starts with the authenticator). Every field name, value, unique ID, version and unreviewed method name shown is converted to UTF-8 (invalid bytes as `\xNN`), has runs of 40 or more base64, base64url or hex characters replaced by `[redacted]`, counting runs joined by `.`, `:` or `~` together (a JWT, or a credential cut into shorter pieces) (a compressed public key, `02` or `03` and 64 hex digits, is shown) and recognised macaroons, `lndconnect://` and NWC URIs redacted, and is cut to 128 code points followed by `…[+N]`. At most 64 alternatives are listed; `omittedAlternatives` counts the rest. The fingerprint is `fp:` and the first 16 hex characters of SHA-256 over the complete decoded credential (authenticator and restriction text), so padded and unpadded copies share it; a `rune-invalid` finding's fingerprint is over its candidate text as UTF-8 (its first 8,193 characters). Output redaction (text, JSON, SARIF, GitHub annotations, errors, scanned paths) also replaces every value in rune key context, and every command-context value that is a checkable rune, with `[redacted]`.

`rune` facts (`inspect` `result.rune`, `scan` `finding.rune`): `{"recognition":"rune-syntax","methodTable","uniqueId"|null,"version"|null,"restrictions":[[{"field","condition","value"},…],…],"omittedAlternatives","methods","allowedMethods":[…],"capabilities":[…],"sensitiveMethods":[…],"conditions":[…],"expiry":{"status","deadline"|null},"verification":"unchecked","warnings":[…]}`; for a value that does not parse, `{"recognition":"invalid","reason","verification":"unchecked"}` with `reason` one of `exceeds-bounds`, `not-base64url`, `too-short`, `nul-byte`, `restriction-syntax`, `unique-id-placement`, and in `scan` also `no-unique-id` and `unique-id-not-numeric` (below). Both are defined once in `schemas/output/inspect.schema.json` and `scan.schema.json`; `node scripts/output-schemas.mjs --check` fails when the two copies differ.

## Commands

### 1. `inspect` (offline, SAFE-07)

`macwarden inspect <file | -> [--json]`
`macwarden inspect <hex | base64 | lndconnect://… | nostr+walletconnect://… | L402 <macaroon>:<preimage> | rune> --unsafe-arg [--json]`

1. Parse arguments: exactly one input (`--` ends flags, so `inspect -- --odd.macaroon` works); none, two, or an unknown flag → exit 2.
2. Read the input with `readCredential` (Global conventions) → exit 2 or 3 as stated there.
3. Decode → exit 3 with the stage on failure. Bytes after the signature packet are accepted (go-macaroon ignores them, so LND accepts the macaroon): warning `trailing-bytes`; the fingerprint covers only the canonical bytes, so one credential has one fingerprint.
4. Grade and describe; `warnings` is the merge of both lists, sorted (UTF-8 byte order) and de-duplicated. Text output shows `(valid)` or `(expired)` after each parseable `time-before` caveat. Print. Exit 0.

Exit-2 errors have `error.step` `null`; exit-3 errors carry the stage (`input-read`, `input-form` or a decoding stage).

```text
$ macwarden inspect ./btcpay.macaroon
fingerprint  fp:3f9a1c0e5b7d2a44
location     lnd
root key ID  4831990234117
grade        RECEIVE   (invoices:write)
permissions  info:read invoices:read invoices:write
caveats      time-before 2027-01-01T00:00:00Z (valid)
snapshot     LND 0.21.4-beta
```

`result`: `{"fingerprint","location"|null,"rootKeyId","permissions":[…],"caveats":[…],"grade","reasons":[…],"warnings":[…],"unassessed":[…],"snapshot":"0.21.4-beta"}`. `location` is `null` when the macaroon has none. `permissions` are `entity:action` for every action of every op, in the order and multiplicity `lncli printmacaroon` shows them (the duplicate-ops vector settles this).

**NWC input.** `inspect` alone also accepts a Nostr Wallet Connect URI ([NIP-47](https://github.com/nostr-protocol/nips/blob/master/47.md)) from a file, stdin, or a literal with `--unsafe-arg`; other commands keep refusing it at `input-form`. The whole trimmed text must be one URI `nostr+walletconnect://<wallet pubkey>?…` with no whitespace or fragment. The legacy schemes `nostr+walletconnect:`, `nostrwalletconnect://` and `nostrwalletconnect:` (case-insensitive, as accepted by the Alby js-sdk parser) and one `/` after the wallet public key decode identically. Checks, each failing with exit 3 and its stage: the scheme and query (`nwc-uri`), a 64-hex wallet public key (`nwc-wallet-pubkey`), exactly one `secret` of 64 hex that is a valid secp256k1 private key (`nwc-secret`), one to 64 `relay` values that are `wss://` or `ws://` URLs (`nwc-relay`), and at most one `lud16` address of at most 320 characters (`nwc-lud16`). The message is `invalid NWC URI <stage>` and never echoes the input. Relays are reported as scheme, host and path only; userinfo, query and fragment are dropped with warning `relay-details-removed`. A reported field (wallet public key, each relay, `lud16`) that carries the secret is refused, not redacted: the field is percent-decoded until stable, lower-cased and stripped to `[0-9a-z]`, and any 16-hex-character (8-byte) window of the secret, or any 11-character window of its case-folded base64 or base64url at any byte alignment, fails with exit 3 at that field's stage (`nwc-wallet-pubkey`, `nwc-relay`, `nwc-lud16`). Folding joins hostname labels, path segments and escapes within one field. Each field is checked on its own; deliberate obfuscation across fields or by transformation is not detected, since its author already holds the secret.

`result` for NWC: `{"kind":"nwc","fingerprint","walletPubkey","clientPubkey","relays":[…],"lud16"|null,"grade":"SPEND","reasons":["nwc-wallet-side-limits"],"warnings":[…]}`. The fingerprint equals `scan`'s for that connection (SHA-256 over the 32-byte secret). `clientPubkey` is the x-only secp256k1 public key of the secret; wallet services list the connection under it. The grade is always `SPEND`, because budget and permissions are set by the wallet service and are not visible. The secret never appears in any output (SAFE-01).

**L402 input (1.2.0).** An L402 credential (formerly LSAT) pays for access to an HTTP or gRPC service: a macaroon minted by the service that commits to the payment hash of a Lightning invoice, presented with the invoice's preimage as proof of payment ([L402 protocol specification](https://github.com/lightninglabs/L402/blob/592203a95ea297fad6d7e10c6de2d827bfd450b2/protocol-specification.md), sections 3, 5 and 10). `inspect` alone (and `scan`, below) reads it; `verify` refuses it at `input-form` ("an L402 token is not an LND credential"), and other commands refuse it as a macaroon they cannot decode. Accepted from a file, stdin, or a literal with `--unsafe-arg` (a literal without it is refused with exit 2, like any credential literal):

- **Authorization value**: `L402 <base64 macaroon>:<hex preimage>` or the legacy scheme `LSAT` (case-insensitive, one or more spaces or tabs), optionally preceded by the header name `Authorization:`, as one line (specification section 5.2; Aperture [`l402/header.go`](https://github.com/lightninglabs/aperture/blob/1fa4bbb0cbb911798898f0eef4d760408f3d41f9/l402/header.go)). Each macaroon is canonical base64 or base64url, padded or not; the preimage is exactly 64 hex digits, as Aperture requires (`l402-preimage` otherwise). The grammar allows several comma-separated macaroons (for example a macaroon and the discharge macaroons of its third-party caveats); macwarden reads up to 16 (more fail at `l402-form`), reports `macaroons` (their number) and warning `l402-several-macaroons`, and describes the primary one: the first with an L402 identifier, else the first. Aperture itself accepts one.
- **Challenge**: `L402 macaroon="<base64>", invoice="<bolt11>"` or `LSAT …` (specification section 5.1), optionally preceded by `WWW-Authenticate:`, its macaroon from the first `macaroon` parameter, or the first `token` parameter that some servers send instead ([getAlby/js-lightning-tools `parseL402`](https://github.com/getAlby/js-lightning-tools/blob/master/src/402/l402/utils.ts)), quoted or not, in any parameter order; a header that carries both an `LSAT` and an `L402` challenge (section 10) is read from the first. A challenge has no preimage: `form: "challenge"`, `status: "unpaid"`.
- Any other text that starts with a scheme (with or without the header name) fails at `l402-form`.
- **Pair**: `<base64 macaroon>:<hex preimage>` without a scheme.
- **Bare macaroon** in any form `readCredential` reads (binary, hex, base64) whose identifier is an L402 identifier. Its preimage, if any, is its last `preimage=<64 hex>` caveat, which Aperture's gRPC clients add (the `Macaroon` and `Grpc-Metadata-Macaroon` headers).
- **Token store file**: the binary file Aperture's client library writes ([`l402/token.go`](https://github.com/lightninglabs/aperture/blob/1fa4bbb0cbb911798898f0eef4d760408f3d41f9/l402/token.go) `serializeToken`, [`l402/store.go`](https://github.com/lightninglabs/aperture/blob/1fa4bbb0cbb911798898f0eef4d760408f3d41f9/l402/store.go)): a big-endian uint32 macaroon length (1 to 65,536), the macaroon, the 32-byte payment hash, the 32-byte preimage (all zero while the payment is pending), amount paid, routing fee and creation time (8 bytes each). Clients keep it as `l402.token` and `l402.token.pending` (legacy `lsat.token`, `lsat.token.pending`): Loop and Pool in their data directory, lnget under `~/.lnget/tokens/<domain>/` ([lnget](https://github.com/lightninglabs/lnget/blob/c855f418fc6eb872921f09f85b56d185af0e197e/l402/filestore.go)). Content is read as a token file only when it has this framing (first byte 0, the length in range, the macaroon's first byte 2, enough bytes for the rest); anything else is read as before.

The macaroon is parsed like any macaroon (stages `v2-header` and `packet`; trailing bytes give `trailing-bytes`, more than 4,096 caveats `caveats-exceed-bounds`). An L402 identifier is Aperture's version 0 `Identifier` ([`l402/identifier.go`](https://github.com/lightninglabs/aperture/blob/1fa4bbb0cbb911798898f0eef4d760408f3d41f9/l402/identifier.go)): exactly 66 bytes, a big-endian uint16 version 0, the 32-byte payment hash and a 32-byte token ID; Aperture mints it with location `lsat` ([`mint/mint.go`](https://github.com/lightninglabs/aperture/blob/1fa4bbb0cbb911798898f0eef4d760408f3d41f9/mint/mint.go)). An Authorization value, pair or token file whose macaroon carries another identifier is still reported, with `identifier: null` and warning `l402-identifier-unrecognized`; one that carries an LND macaroon is inspected as that LND macaroon (the preimage is ignored).

Caveats are read as Aperture reads them ([`l402/caveat.go`](https://github.com/lightninglabs/aperture/blob/1fa4bbb0cbb911798898f0eef4d760408f3d41f9/l402/caveat.go), [`l402/service.go`](https://github.com/lightninglabs/aperture/blob/1fa4bbb0cbb911798898f0eef4d760408f3d41f9/l402/service.go), [`l402/satisfier.go`](https://github.com/lightninglabs/aperture/blob/1fa4bbb0cbb911798898f0eef4d760408f3d41f9/l402/satisfier.go)): a first-party caveat is split at its first `=` into `condition` and `value`, each reported verbatim as `{"type","condition","value"}`. Types: `services` (`name:tier` items joined by `,`), `capabilities` (condition `<service>_capabilities`, with `service`), `valid-until` (condition `<service>_valid_until`, Unix seconds, with `service`), `preimage` (its `value` is always `null`), `constraint` (any other condition: Aperture's per-service constraints), `unknown` (no `=`, `condition: null`; Aperture ignores it) and `third-party` (`value` is its location). `services` in the result is parsed from the last `services` caveat, the one Aperture checks; an unparseable one gives `[]` and warning `l402-bad-services`. A `valid-until` value that Go's `strconv.ParseInt(value, 10, 64)` reads gets `expired` (true when now ≥ that second, as Aperture's `now().Before(expiry)` check fails then) and `until` (RFC 3339 UTC, when representable); otherwise warning `l402-bad-valid-until`. A caveat whose condition or value, or a location, contains the preimage (hex in either case, or its base64 or base64url) is reported as `{"type":"withheld","condition":null,"value":null}` (location `null`) with warning `l402-caveat-withheld`; a `preimage` caveat that is not 64 hex gives `l402-bad-preimage-caveat` and counts as no preimage.

Preimage: the one presented with the macaroon (Authorization value, pair, token file), else the last `preimage` caveat. `preimage` is `matches` when its SHA-256 equals the identifier's payment hash (the check the server makes, offline), `mismatch` when it does not, `unverifiable` when the identifier is not recognised, `absent` when there is none; `preimageSource` is `credential`, `caveat` or `null`. A macaroon without its preimage (a `WWW-Authenticate` challenge, a pending token) grants nothing on its own: the server refuses it until the invoice is paid and the preimage presented, so it is `status: "unpaid"` and not counted. A token file whose payment hash differs from the identifier's gives `l402-token-hash-differs`.

**Category, not grade.** An L402 token pays for access to a service; it gives no control of a Lightning node, so it never gets a ladder grade. `access` is always `service-access`. `status` is `live` (a usable preimage, not expired), `expired` (a usable preimage, and the last `services` caveat names at least one service while every named service's last `valid-until` caveat has passed), `preimage-mismatch` or `unpaid`. `countedAs` is `READ` when the preimage `matches` or is `unverifiable`, and `null` otherwise: a token with a usable preimage is a live bearer secret, which `scan --fail-on` counts at the lowest rung; expiry does not change it, as caveats never change a grade (the server's clock decides, and a CI result must not change with the date).

`result` for L402: `{"kind":"l402","fingerprint","macaroonFingerprint","macaroons","form":"authorization"|"challenge"|"pair"|"macaroon"|"token-file","scheme":"L402"|"LSAT"|null,"location"|null,"identifier":{"version":0,"paymentHash","tokenId"}|null,"services":[{"name","tier"}],"caveats":[…],"preimage","preimageSource","status","expired","access":"service-access","countedAs":"READ"|null,"warnings":[…]}`. `macaroonFingerprint` is SHA-256 over the primary canonical macaroon (as for any macaroon); `fingerprint` is SHA-256 over every canonical macaroon in order followed by the 32 preimage bytes when a preimage is presented with them, and equals `macaroonFingerprint` for one macaroon without a presented preimage, so one token has one fingerprint as an Authorization value, a pair and a token file. The payment hash and token ID are public (the payment hash is in the invoice). The preimage and the macaroon bytes never appear in any output, in any encoding (SAFE-01); the output choke point also redacts any text shaped like an L402 Authorization value or pair, and L402 macaroons in every encoding it recognises.

**Core Lightning rune input (1.2.0).** `inspect` alone also accepts a Core Lightning rune from a file, stdin, or a literal with `--unsafe-arg` (without it a literal rune is refused like a literal macaroon, exit 2, and never echoed). The whole trimmed text must be a rune (Core Lightning runes): URL-safe base64 of at most 8,192 characters that parses completely. Text that is also a macaroon that decodes stays a macaroon; anything else keeps the macaroon decoding rules and their errors (exit 3). `result` for a rune: `{"kind":"rune","fingerprint","grade","reasons":[…],"unassessed":[…],"rune":{…}}`, with the `rune` facts of Core Lightning runes; `unassessed` lists method names the restrictions allow by exact name that the pinned table does not list. Text output shows the kind, fingerprint, unique ID and version, grade and reasons, the methods, the possible capabilities, each restriction (`restriction` for the first, `and` for the others, alternatives joined by `OR`), the conditions, the expiry, unassessed and sensitive methods, the warnings, a `verified     no: …` line stating that authenticity, issuing node, blacklist and rate-limit state are not checked offline, and the method table's release. The authenticator never appears. The decoding stage `rune-syntax` exists for a container that holds no rune; `inspect`'s input rule never produces it.

**Input precedence (1.2.0).** `inspect` reads four credential families, and every input is read as exactly one of them, in this order. Bytes first: a binary macaroon (first byte `0x02`), then an Aperture token store file (its framing above). Otherwise the input is text (UTF-8, or UTF-16 with a byte order mark), trimmed and read as: (1) an NWC URI (one of its schemes); (2) an L402 Authorization value or challenge (a scheme, with or without the header name) or a `<base64>:<hex>` pair; (3) a Core Lightning rune (the rune input rule below); (4) an `lndconnect://` URI; (5) a hex or base64 macaroon, whose decoded macaroon is an L402 token when its identifier is an L402 identifier and an LND macaroon otherwise. NWC URIs, L402 text and `lndconnect://` URIs contain `:` or a blank, which no rune can contain, and binary input never starts with a rune character, so steps (1), (2) and (4) never compete with a rune: only hex or base64 text can be both a rune and a macaroon, and such text is a macaroon when it decodes as an LND macaroon or as a macaroon with an L402 identifier, and a rune otherwise. A form that fails its own checks fails at its own stage (`nwc-…`, `l402-…`, a macaroon stage); it is never retried as another family.

Acceptance: a file (binary, hex text, base64 text, UTF-16LE text with BOM) and stdin give identical `result` for one macaroon, and so do the literal hex, base64 and `lndconnect://` forms with `--unsafe-arg`; without `--unsafe-arg` a literal is refused with exit 2 and the leak test finds no part of it in stdout or stderr; for every vector, root key ID, permissions and caveats equal the stored `lncli printmacaroon` output under the caveat matching rule; every grade test row passes; every negative vector exits 3 at the stage listed in `test/vectors/negative/manifest.json`; `--json` with `--unsafe-arg` keeps stdout a single document; `--json` output validates against `schemas/output/inspect.schema.json`.

### 2. `scan` (offline, SAFE-07)

`macwarden scan [paths…] [--fail-on ADMIN|SPEND|OPERATE|RECEIVE|READ] [--include-dirs] [--ignore-file <path>] [--git-history [--allow-shallow]] [--agent-configs] [--format text|json|sarif|github] [--json]`

Default path: `.`. `--fail-on` takes exactly one of the five ladder grades, in any case (`spend` equals `SPEND`; reported upper-case); any other value, a missing value or a repeated flag → exit 2.

Detectors (regexes are RE2-compatible and used verbatim by `src/scan/patterns` and `rules/gitleaks.toml`):

| Kind | Match | Confirmation |

The hex and base64 patterns match only macaroons with location `lnd` written in canonical framing (one-byte packet kinds and lengths). A re-framed copy (non-minimal varints, which LND accepts) decodes as the original wherever it is decoded and is found as a `*.macaroon` file, but in text only when its framing still matches a pattern, which then decodes it fully. Text matching:

- Detectors run per line. Lines longer than 524,287 Unicode code points are scanned in windows of 524,287 code points starting every 262,144 code points; matches with the same start offset are reported once (the longest). A match of up to 262,144 code points (the candidate bound) is therefore always matched whole wherever it starts; the bound covers the largest supported encodings: hex of a 64 KiB credential (131,072), its base64 or base64url (87,382) with `lndconnect` host and certificate parameters, and NWC URIs. Longer matches are matched whole when their window has room.
- Fail closed at the bound: a match that its window cuts (the line continues it past the window end), and an `nwc` prefix whose URI runs to the window end without a boundary or a secret, are reported as `undecodable-candidate` (never decoded from a part, never dropped), whatever their detector, `lndconnect` included.
- L402: an Authorization value, challenge or pair is confirmed after `lndconnect` and before the other detectors; a confirmed one hides the matches that start inside it (its macaroon as a bare L402 or LND macaroon, a pair inside an Authorization value). One that does not decode hides nothing. The pair matcher, like the NWC matcher, is a linear-time scan (it walks each base64 run once from the `:` that ends it), so a line of open L402 shapes cannot make `scan` super-linear. JSON-escaped slashes and base64-encoded text (both below) also apply to L402 Authorization values, challenges, pairs and base64 macaroons; base64-encoded text holding `L402 `, `LSAT `, `l402 `, `lsat ` or an L402 macaroon prefix is decoded as below. Not read: an Authorization value split across lines, and an L402 macaroon with another location given without its scheme or preimage.
- Precedence: `lndconnect` matches are confirmed first; `nwc`, `macaroon-hex` and `macaroon-base64` matches that start inside a confirmed (decoded) `lndconnect` URI are not reported separately. A URI that does not parse, or is cut by a window, hides nothing: the credential it carries is still reported, decoded or as a candidate.
- Base64-encoded text (RR-02; Kubernetes Secret `data:`, Helm values): a base64 run (`[A-Za-z0-9+/]{16,}={0,2}`) holding the base64 of `0201036c6e6402` (either case), `AgEDbG5kA` or `lndconnect://` at any byte alignment is decoded once at each of its four character phases, and the decoded bytes (as latin1) are scanned as a line with the `lndconnect`, `nwc`, `macaroon-hex` and `macaroon-base64` detectors and the same confirmation, one level deep (decoded text is never decoded again). A finding is reported at the column of the encoded character where its first byte starts.
- JSON-escaped slashes: a line containing `\/` (PHP `json_encode` writes it by default) is also matched for `macaroon-base64` and `lndconnect` with every `\/` read as `/`. Such a match is reported at its column in the original line, and replaces a match of the same kind at that column only when it covers more of the line.
- NWC in escaped form: a line that mentions `walletconnect` and contains `\/`, a percent escape or `nostr walletconnect` is also matched for `nwc` after one normalisation: JSON-escaped slashes (`\/`) become `/`, percent escapes of ASCII bytes are decoded once, and `nostr walletconnect` (a `+` decoded to a space) becomes `nostr+walletconnect`. A URI matched in both forms at one column is reported once, at its column in the original line. Out of scope: double percent-encoding, `\uXXXX` escapes, HTML numeric entities and other transformations (base64 of the URI, a URI split across lines or fields).
- Fail closed: a hex or base64 prefix match that does not decode is reported as `undecodable-candidate`. This is how line-wrapped credentials (`base64` without `-w0`, `xxd -p`, YAML folded scalars) are caught: they are reported as candidates, not decoded.
- Separators and narrow wraps (RR-10, scan only; these patterns are not in `rules/gitleaks.toml`): hex with one `:`, space or `-` between every byte (`/02[: -]01[: -]03[: -]6c[: -]6e[: -]64[: -]02(?:[: -][0-9a-f]{2}){20,}/i`, colon hex, `xxd -g1`) is decoded with the separators removed and reported as `macaroon-hex`. The prefix of an `xxd` default dump (`0201 036c 6e64 02` or `02 0103 6c6e 6402`) is an `undecodable-candidate`. A hex or base64 prefix followed by fewer than 40 continuation characters that ends its line (trailing whitespace aside) may be a credential wrapped narrower than 49 columns: it is joined with the following lines that hold only the same alphabet (trimmed; base64 stops after a line ending in `=`; at most 262,144 characters), and reported as `macaroon-hex` or `macaroon-base64` at the prefix when the joined text decodes, otherwise not reported. Each line joins at most one wrap, so joining is linear. Out of scope: an `xxd` dump whose prefix is split across two lines, and hex with other separators or grouping.
- Encodings: UTF-8 with or without BOM; UTF-16 LE or BE with a BOM is decoded, then scanned. Line ends CRLF, LF and CR. `line` is 1-based; `column` is 1-based in Unicode code points from the line start, BOM excluded.

Core Lightning runes (1.2.0). A rune has no fixed prefix, and any base64 of 32 or more bytes can parse as one, so `scan` looks for runes only in explicit rune context, per line, and never context-free:

- **Key context.** A value assigned to a rune key: the word `rune` in any case, on its own or after `_`, `-`, `.`, or a lower-case letter or digit followed by a capital `R` (camelCase: `clnRune`), followed directly by a quote closing the key, a blank, `=` or `:` (so `prune`, `CLNRUNE`, `runes` and `rune_id` are not keys); then blanks, `=`, `:` or `:=` (not `==` or `=>`), blanks and at most one opening quote. Two more forms need no separator: an option token that starts with `-` followed by blanks (`--rune …`, `--cln-rune "…"`), and an XML element (`<rune>…</rune>`, `<clnRune>…`). This covers `.env` and shell assignments (`RUNE=…`, `CLN_RUNE="…"`, `export LIGHTNING_RUNE='…'`), JSON and agent configurations (`"rune": "…"`, an MCP server's `"env": {"CLN_RUNE": "…"}`), YAML and TOML, code (`{ rune: '…' }`, `rune = "…"`), Go and make assignments (`clnRune := "…"`, `CLN_RUNE := …`), XML (`<rune>…</rune>`), command-line options (`--rune=…`, `--rune …`, `lightning-cli … rune=…`) and clnrest's `Rune` HTTP header (`Rune: …`, `curl -H 'Rune: …'`, any case). The value is the run of base64 characters that follows (`A–Z a–z 0–9 - _ + / =`, so a standard-alphabet value is examined and refused rather than cut); a run shorter than 43 characters (less than a 32-byte authenticator) is not a candidate, which leaves placeholders such as `${CLN_RUNE}` and type names alone. A key-context value that is the canonical standard base64 of rune text (a Kubernetes Secret's `data`, Helm values) is decoded once and reported as that rune. A key-context value that parses but has no unique ID, or one that `checkrune`'s parameter parser does not accept as a number (`strtoull` over the whole ID, at most 2⁶³−1; an empty ID reads as 0), is reported as `rune-invalid` with reason `no-unique-id` or `unique-id-not-numeric`: `checkrune` refuses it before reading any restriction, every rune Core Lightning creates has one, and about 4 in 10 SHA-256 digests and node IDs and 1 in 8 random base64url values parse as restriction text without one.
- **Command context.** A whole argument (a base64 run with a blank, a quote or the line end on both sides) after `commando`, `checkrune`, `showrunes`, `createrune`, `invokerune` or `lightning-cli` on the same line, as in `lightning-cli commando <peer> <method> <params> <rune>`. Peer IDs, hashes and other arguments share the alphabet, so such a value is reported only when it is a checkable rune: it parses and its unique ID has the form `createrune` writes (a decimal number without a leading zero) within the range `checkrune` accepts (at most 2⁶³−1). Only the node can write the unique ID restriction, so a rune it issued has no other form, while other arguments can parse as runes: one regtest address in about a hundred (`lightning-cli withdraw bcrt1q…`) ends in the byte `=`, a rune with an empty unique ID.
- **Possibly cut values.** A quoted value not closed by its own quote, an unquoted value followed by a character that does not end values (anything but blanks, quotes, `` , ; ) ] } < > & # | ``, or a percent-encoded `=`), or a value that ends its line while the next line holds only base64 characters (a wrapped or folded scalar) may be the start of a longer rune. A cut rune has lost restrictions, and a cut value can name another method, so such a finding is graded `UNASSESSED` unless it is `ADMIN`, with warning `possibly-truncated`.
- A rune finding has `rootKeyId`, `permissions` and `caveats` `null`, `warnings` empty, `unassessed` the unreviewed method names, and `rune` with the facts of Core Lightning runes; `rune-invalid` has `grade` `UNASSESSED`. `--fail-on`, ignore entries, `byGrade` (by grade, `rune-invalid` under `UNASSESSED`), MCP tagging, `--git-history` and `--agent-configs` treat them like any other finding. Text output adds the unique ID, the possible capabilities, broad method access, a passed deadline and "not checked against the node"; SARIF adds rules `macwarden/rune/<grade>` and `macwarden/rune-invalid` and the result properties `runeUniqueId` and `verification`; GitHub annotations add the unique ID. Out of scope: a rune with no rune context (a bare value in prose or a positional argument of another program), a rune split across lines, and encodings other than one level of standard base64.

Files and directories:

- Only regular files are opened, read-only, non-blocking and with no-follow where the platform has them, and `fstat` after open: content is read only when the open descriptor is a regular file with the identity (device and inode) that `lstat` reports for its path. An entry replaced by a FIFO between the walk's `lstat` and the open therefore cannot block the scan (it is skipped as `not-regular`); the ignore file is opened the same way. At most 5,242,881 bytes are read whatever `stat` said; a file with more than 5,242,880 bytes is skipped (`size`), including one that grows during the scan.
- A file without a UTF-16 BOM that has a NUL byte in its first 8,192 bytes is binary and skipped (`binary`), except `*.macaroon`. UTF-16 text without a BOM is therefore treated as binary.
- Each path argument is resolved (realpath) once. Because the walk never follows a symlink, a walked entry's resolved path is its directory's resolved path joined with its name; it is not resolved again. Instead, after listing a directory macwarden checks that the directory's resolved path still has the identity it walked, and just before and after opening a file it checks the file's own `lstat` and its directory's identity again; an entry that changed since the walk's `lstat` is resolved and skipped (`never-open` when it now resolves to a protected name, otherwise `symlink` or `not-regular`), and one whose directory changed is `unreadable`. Each check is one `lstat` of one path, so the walk's cost grows linearly with the total length of the walked paths, never with a resolution per path component (deep directory chains cannot make it super-linear).
- Symlinks found during the walk are not followed (`symlink`); Windows reparse points other than plain files are treated the same. A path argument that is itself a symlink is followed once (the operator named it).
- FIFOs, devices and sockets → `not-regular`. `/proc`, `/sys` and `/dev` are never entered (`excluded-dir`). `.git` and `node_modules` are not entered unless `--include-dirs` (`excluded-dir`). These names, and `proc`, `sys` and `dev` in a scan of `/`, are compared as the platform's default file system compares names: case-insensitively on Windows and macOS (`.GIT` is `.git` there), exactly elsewhere (on Linux `.GIT` and `Node_Modules` are ordinary directories and are scanned); `--git-history` applies the same rule to history paths. An excluded directory is listed once.
- Never opened, per SAFE-02 (`never-open`), for explicit paths with protected supplied or resolved file or directory components (not descended), including Windows stream base names, case-insensitive: `macaroons.db`, `wallet.db`, `*.key`, names matching `/(^|[._-])(password|passwd|seed)([._-]|$)/i`, and the legacy families `^wallet[-_.]?password(?:\..+)?$`, `^seeds?(?:\..+)?$`, and `^tls[-_.]?(?:key|privkey)(?:\..+)?$`.
- A file or directory that fails during the walk is skipped (`unreadable`): only an I/O failure (it cannot be opened, stat'ed or read, or changed while being read) is a skip. An unexpected exception while analysing bytes that were read is a bug: the scan stops with exit 8 (`internal`), so a CI gate fails instead of passing a file nobody looked at. A path argument that does not exist or cannot be read → exit 3: a CI gate must not pass having scanned nothing. For the same reason a path argument that is (or, once opened, turns out to be) a FIFO, device or socket → exit 3, step `input-read`, message "scan path is not a regular file or directory"; the `not-regular` skip applies to such entries found during the walk. An argument refused by name (`never-open`) or under `/proc`, `/sys` or `/dev` (`excluded-dir`) stays a listed skip: macwarden declines it on purpose.
- A file reached through several path arguments is scanned once, reported under the first argument that reaches it.
- Within one path argument, a file with several hard-link names is scanned once and its findings are reported at the first name in walk order. Every other name is accounted for: each of those findings carries `alsoAt: {count, paths}` (how many other names, and up to five of them in walk order), so deleting or replacing one name does not leave the credential unreported under another. Text output adds "(same file also at N other paths: …)" with the names, SARIF adds `relatedLocations` and `properties.alsoAt`, GitHub annotations add the count, and the ignore rule for `alsoAt` below applies (the finding is ignored only when every name matches). A file name without findings has nothing to report and stays silent.

Ignore file: unless `--ignore-file <path>` is given (missing or unreadable → exit 3), each directory path argument may contain `.macwardenignore`. One entry per line: `fp:<16 hex>` (hex in either case, normalised to lower case) optionally followed by whitespace and a path glob (`*`, `**`, `?`). A `.macwardenignore` glob is matched against the finding's path relative to the ignore file's directory, `/`-separated; an `--ignore-file` glob is matched against the finding's `path` as reported. A glob always matches the whole path; a leading `/` anchors it as in `.gitignore` and is dropped before matching a relative path (`/top.env` matches `top.env`, not `sub/top.env`), while against an absolute reported path the glob is matched as written. The file is decoded like scanned text: UTF-8 with or without BOM, or UTF-16 LE or BE with a BOM (what Windows PowerShell 5.1 writes with `>` and `Out-File`). `#` starts a comment anywhere on a line; blank and comment-only lines are ignored; any other line → exit 3, step `ignore-file`. A matching finding is counted in `summary.ignored` and is neither reported nor counted for `--fail-on`. When at least one finding is ignored, `result.ignoredFingerprints` contains the sorted unique canonical `fp:<16 lowercase hex>` fingerprints of suppressed findings, without credential bytes or suppressed finding details; otherwise this optional field is absent. Text output shows these fingerprints on a separate `ignored-fingerprints` line only when present. Suppressed findings are excluded from `findings`, `failOn` and `byGrade`; `skipped` retains its existing reason enum and `filesSkipped` equals `skipped.length`. Parent directories are never searched for an ignore file: a suppression applies only from the argument directory's own `.macwardenignore` or a file named with `--ignore-file`, so no unnamed file can hide a finding. A pre-commit hook, which runs from the repository root and passes staged file names, therefore passes `--ignore-file .macwardenignore` explicitly (`.pre-commit-hooks.yaml`).

Redaction: a finding shows path, line, column, kind, fingerprint and the decoded facts; never the matched text or the line content (SAFE-01). Fingerprints: decoded macaroons as in Global conventions; `nwc` over the secret; `undecodable` over the file bytes; `undecodable-candidate` over the matched text as UTF-8. Text output treats scanned names and decoded values as untrusted: control characters and Unicode bidirectional controls (U+061C, U+200E, U+200F, U+202A–U+202E, U+2066–U+2069) and the invisible characters listed under Output (format characters, fillers, variation selectors) are printed as `\xNN` / `\uNNNN` / `\u{N}` escapes, and a relative path that would start a line with `:` is printed as `./path`, so no finding line can begin with a GitHub Actions workflow command (`::`). The `nwc` detector, output redaction of NWC URIs and the collection of NWC secrets for redaction all use a linear-time matcher that returns exactly the matches of the published regex.

Git history (`--git-history`; a repeated flag → exit 2): after the walk of each path argument, macwarden also scans that argument's git history. The argument must be inside a git work tree (a file argument restricts history to that file); otherwise, or when `git` cannot be run or fails, → exit 3, step `git-history`, message "path is not inside a git work tree", "git history requires git on PATH", "git history could not be read", "git history timed out", "git history is too large to scan (more than 1000000 added blobs)", "git history requires a repository on a local file system" or "git history would open a protected file".

- Shallow clones: a shallow repository (for example the default `actions/checkout` depth of 1) lacks the commits before its boundary, so history would look clean when it is not. It → exit 3, step `git-history`, with a message that says to fetch the full history (for example `fetch-depth: 0`) or pass `--allow-shallow`. With `--allow-shallow` (valid only with `--git-history`; otherwise or repeated → exit 2) the fetched commits are scanned, the top-level `warnings` contain `shallow-history` (text: on stderr) and `summary.shallowHistory` is `true`.

- Source: every blob added or modified on any ref (`git log --all --reverse --root --diff-merges=separate --no-renames --raw`, paths relative to the argument, pathspecs literal), read with `git cat-file`. Deleted, renamed and later-overwritten content is therefore found. Root commits are compared with the empty tree and merge commits with each parent, whatever the repository configures. A listed blob that is missing from the object store fails the scan (exit 3); it is never reported as skipped.
- Each distinct blob is read once and scanned exactly as a file at its path would be: the same detectors, `*.macaroon` file rule, UTF-16 and binary rules, fingerprints, grades and redaction. A blob larger than 5,242,880 bytes is not scanned as text (`size`); a larger `*.macaroon` blob is read only up to its first 65,537 bytes and reported `undecodable`, exactly like the walk. Protected names (SAFE-02) are skipped as `never-open` without reading the blob. Paths under `.git` or `node_modules` are `excluded-dir` unless `--include-dirs`. Symlink entries → `symlink`; submodules → `not-regular`.
- Each history finding has `path` (the argument joined with the path in that commit, reported like a file path) and `commit` (the full hash). `line` and `column` refer to that blob. Text output prefixes the location with the first 7 hex digits of the commit: `<commit7>:<path>:<line>:<column>`.
- Deduplication: a credential reported by the work-tree walk at the same `path` and `fingerprint` is not reported again from history. Otherwise each credential in a given file content (blob) is reported once, at the oldest commit and path that added that content in `git log --reverse` order. When the same content was also added at other paths, the finding carries `alsoAt: {count, paths}`: how many other paths, and up to five of them. Text output adds "(same content also added at N other paths)", SARIF adds `relatedLocations` and `properties.alsoAt`, and GitHub annotations add the count. One file content added at a million paths is therefore one finding per credential, not a million. A credential an older blob already reported at the same path is not reported again.
- Ignore entries and `alsoAt`: a finding that stands for several paths is ignored only when every one of its paths is listed (count at most five) and each matches an ignore entry; otherwise it is kept (fail closed).
- `.macwardenignore`, `--ignore-file` and `--fail-on` treat history findings like any other finding. `summary.blobsScanned` (present only with `--git-history`) counts the distinct blobs read; `filesScanned` still counts work-tree files.
- Offline and read-only (SAFE-07, SAFE-08): git runs with an argument array and no shell, with system and global git configuration disabled, `--no-optional-locks`, `protocol.allow=never` and `GIT_NO_LAZY_FETCH=1`, so it neither writes to the repository nor contacts a remote. `GIT_CEILING_DIRECTORIES` is honoured by the location check above. Objects missing from a partial clone make the scan fail with exit 3 rather than fetch them.
- The scanned repository is untrusted: its own `.git/config` cannot start a program or change what is listed. Command-line settings, which outrank every config file and include, pin `core.fsmonitor`, `core.hooksPath`, `log.showSignature` (with `--no-show-signature`), `gpg.program`, `gpg.ssh.program`, `gpg.x509.program`, `log.showRoot`, `log.follow`, `diff.renames` and `log.mailmap` (with empty `mailmap.file` and `mailmap.blob`); `--root`, `--diff-merges=separate`, `--no-ext-diff`, `--no-textconv`, `--no-pager`, replace refs and grafts off, and literal pathspecs fix the rest. A repository owned by another account is refused by git → exit 3.
- Repository location: before any git process starts, macwarden finds the repository as git discovery would (a `.git` directory or gitfile in the argument or a parent, stopping at `GIT_CEILING_DIRECTORIES`) and checks every location git would read: the gitfile target, `commondir`, `objects/info/alternates` (recursively, at most 5 levels) and `include.path` / `includeIf.*.path` in `config` and `config.worktree` (recursively, at most 10 levels). Each location is read at most once. git re-reads an included file every time it is named, so the check also bounds what git would traverse: more than 4,096 include and alternate entries followed in total (counting each repetition), more than 1 MiB of location-file bytes parsed in total, more than 256 distinct location files, a location file over 64 KiB, or an include or alternates cycle → exit 3 "git history could not be read", before any git process starts. An interrupt during the check is honoured. Any of them on a network or device path (on Windows a UNC path such as `\\server\share` or `//server/share`, `\\?\UNC\…`, or `\\.\…`) → exit 3 "git history requires a repository on a local file system", checked before that path is opened. Any of them (the `.git` gitfile itself included) whose supplied path or resolved target has a protected file or directory component (SAFE-02, the names listed under scan above, including one that does not exist) → exit 3 "git history would open a protected file", checked before that path is opened and before any git process starts, because git would read the same include. Location files are read through one descriptor checked to be the regular file that was resolved, and at most 64 KiB + 1 bytes of each are read. A local gitfile (linked worktrees, submodules, a moved git directory) is followed. git then runs with `GIT_DIR` and `GIT_WORK_TREE` set to the checked locations and a ceiling at the work tree's parent, so it cannot discover another repository.
- Bounds: a git process that writes nothing for 120 seconds is killed → exit 3 "git history timed out". More than 1,000,000 added-blob entries → exit 3. The listing is held column-wise (an index into de-duplicated path, blob and commit tables per entry), requests to git are streamed, blob content is streamed and only the bytes a detector needs are kept, and only outcomes with findings or a skip reason are retained; 1,000,000 entries fit in a 1 GiB heap. A failed scan waits for git to exit before reporting.
- Interrupts: SIGINT, SIGTERM and SIGHUP stop the walk and the history scan between files and blobs, abandon any file system operation still pending (an open, read or stat that does not return), kill a running git and → exit 6, step `cancelled`, message "interrupted". `scan` changes nothing, so no recovery is needed.

Output and memory: findings are kept in memory until the walk ends (they are sorted and filtered by ignore entries first). Their number is bounded by the bytes scanned, since every finding consumes at least one detector match in a file of at most 5,242,880 bytes, and the same credential found in many places shares one set of decoded facts. A scan also stops at 250,000 findings, counted before ignore entries apply: beyond it the scan fails closed with exit 3, step `findings-limit`, and reports nothing partial, so content an attacker controls cannot exhaust memory. 250,000 findings is far beyond any real repository; it bounds memory at roughly 250 MB. Output is written in chunks of about 64 KiB with stdout backpressure, so no single string holds the whole result. If the reader of stdout or stderr closes the pipe early (for example `| head`), output stops quietly and the exit status is the one computed for the scan (for example 1 when `--fail-on` tripped), never 8.

#### Output formats for CI (owner addition 2026-10-08)

`--format` takes exactly one of `text` (default), `json`, `sarif` or `github`; any other value, a missing value or a repeated flag → exit 2. `--format json` is identical to `--json`. `--json` together with `--format sarif` or `--format github` → exit 2. Exit codes, `--fail-on` and errors (text on stderr) are unchanged; only the rendering of a successful scan on stdout differs, in the same bounded chunks as text.

- **`sarif`**: one [SARIF 2.1.0](https://docs.oasis-open.org/sarif/sarif/v2.1.0/sarif-v2.1.0.html) log with one run. `tool.driver` is `macwarden` with the package version and one rule per finding kind, and per grade for decoded credentials (`macwarden/<kind>/<grade>` for `macaroon-file`, `macaroon-hex`, `macaroon-base64`, `lndconnect` and `rune`; `macwarden/nwc`, `macwarden/undecodable`, `macwarden/undecodable-candidate`, `macwarden/rune-invalid`; `macwarden/l402/paid`, `macwarden/l402/unpaid`, `macwarden/l402-file/paid` and `macwarden/l402-file/unpaid`, paid meaning `countedAs: "READ"`), because GitHub reads `security-severity` only from the rule: 9.5 ADMIN, 9.0 SPEND and nwc, 8.0 UNASSESSED, undecodable kinds and rune-invalid, 6.5 OPERATE, 4.0 RECEIVE, 3.0 READ and paid L402, 1.0 unpaid L402. L402 rules describe service access and say that only the issuing service can revoke the token; rune rules say that a rune is revoked by blacklisting its unique ID (`blacklistrune`) and that macwarden does not check it against the node. Rune rules carry `precision` `high` (`rune`) and `medium` (`rune-invalid`), every other rule `very-high`. The run declares `"columnKind":"unicodeCodePoints"` (columns count code points). Each result has `ruleId`, a `level` from the grade (`error` for ADMIN, SPEND, UNASSESSED, nwc and undecodable; `warning` for OPERATE and RECEIVE; `note` for READ and every L402 finding), a message with kind, grade, fingerprint and root key ID, a location whose URI is relative to the working directory with `uriBaseId` `%SRCROOT%`, which the run declares in `originalUriBaseIds` as the working directory's `file:` URI (an absolute `file:` URI for a path outside it, including a relative `../` path: `file:///C:/…` for a Windows drive path, `file://server/share/…` for a UNC path, `file:///…` for a POSIX path; every segment percent-encoded as UTF-8), `startLine`/`startColumn` when known, `partialFingerprints` `{"macwardenFingerprint/v1": <fp>}`, and for a history finding the commit as a logical location and property. There is never a `snippet` or any matched text (SAFE-01). The scan summary and `failOn` are in `invocations[0].properties`. At most 25,000 results are written, GitHub's limit per run; any further findings are counted in `invocations[0].properties.omittedResults` with a warning notification (`--format json` lists them all; `--fail-on` counts them all). GitHub deduplicates alerts by its own `primaryLocationLineHash`, which `upload-sarif` computes from the checked-out file; `partialFingerprints` keeps macwarden's fingerprint for other consumers, and a history finding whose file is not in the checkout gets no line hash. Upload it with `github/codeql-action/upload-sarif` ([GitHub SARIF support](https://docs.github.com/en/code-security/code-scanning/integrating-with-code-scanning/sarif-support-for-code-scanning)); code scanning of a private repository needs GitHub Code Security.
- **`github`**: one [GitHub Actions workflow command](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-commands) per finding, `::error|warning|notice file=<path>,line=<l>,col=<c>,title=macwarden <kind>::<grade> <fingerprint> …` (level as for SARIF), then the text summary line. Property values escape `%`, CR, LF, `:` and `,`; the message escapes `%`, CR and LF. `file` is the finding's path itself with only these escapes (GitHub decodes exactly them), not the text-output escaping, so the annotation names the real file even when its name holds a tab or another control character. Annotations work on private repositories without Code Security.

- `path` is the path argument (trailing separators removed; on Windows `\` written as `/`, while elsewhere `\` is an ordinary file-name character and is kept) joined with the relative path using `/`; for the path argument `.` the relative path is used alone (no `./` prefix). `findings` are sorted by path in UTF-8 byte order, then line, then column (`null` first); `skipped` by path.
- `line`/`column` are `null` for `macaroon-file`, `undecodable` and `l402-file`. `grade`, `rootKeyId`, `permissions`, `caveats` are `null` for `nwc`, `undecodable`, `undecodable-candidate`, `l402` and `l402-file`; their `warnings` and `unassessed` are `[]`. `rune` and `rune-invalid` findings always have a grade and a line, with `rootKeyId`, `permissions` and `caveats` `null` (Core Lightning runes, above).
- An `l402` or `l402-file` finding, and only such a finding, has `l402`: the L402 facts `inspect` reports without `kind` and `fingerprint` (`macaroonFingerprint`, `form`, `scheme`, `location`, `identifier`, `services`, `caveats`, `preimage`, `preimageSource`, `status`, `expired`, `access`, `countedAs`, `warnings`), expiry judged at the scan's start. Its preimage joins the secrets every reported string is redacted against. Text output shows `<status> (counted as READ)` or `<status> (not counted)` after the fingerprint.
- `skipped[].reason` is one of `symlink`, `size`, `binary`, `excluded-dir`, `never-open`, `not-regular`, `unreadable`. `filesSkipped` = number of `skipped` entries.

- `failOn` is `null` without `--fail-on`; otherwise `threshold` is the grade given and `count` the number of findings counted at or above it.

Exit: 0; 1 when `failOn.count` > 0 (`ok: true`, `error: null`); 2 on bad flags (`error.step` `null`); 3 for a missing or unreadable path argument or ignore file (`error.step` `input-read`) or an invalid ignore-file line (`ignore-file`).

### 3. `inventory` (online, read-only)

`macwarden inventory [--verify] [--expiring-within <n>(m|h|d)] [--report markdown|csv|json [--out <file>]] [--json]` + online flags — needs `info:read`, `macaroon:read`.

When `macwarden watch` has recorded usage next to the registry, each root key ID row also carries `usage: {calls, errors, lastUsed, methods}` (all credentials observed on that root key ID; root key 0 aggregates the default macaroons) and the text status adds `last used <time> (<n> calls)`. Usage covers only what a watcher observed; a missing usage file adds nothing, an unreadable one adds warning `usage-unreadable` and never fails the command.

Steps (N1–N6):

1. **N1** Parse arguments → exit 2.
2. **N2** ENV → exit 2. OWN → exit 4.
3. **N3** Open the registry read-only (no lock) → exit 3 if unreadable or invalid.
4. **N4** GetInfo; ListPermissions (`snapshot-drift`); ListMacaroonIDs → exit 4/5 on failure.
5. **N5** Join: one row per root key ID in LND, plus one per registry entry for this node's pubkey with status `active` that LND lacks. Revoked entries absent from LND are not shown.
6. **N6** `--verify`: for each `active` entry for this node whose `outPath` file exists and whose fingerprint matches, verify accepted (Global conventions). Result per row: `accepted`, `rejected` (verify rejected, e.g. after a root key regeneration), `error` (neither), or `not-checked`. The credential is never printed. A failed call does not stop the run.

Flags per row: `default-root-key` (ID 0), `own-credential` (macwarden's own root key ID), `unknown` (in LND, not in the registry, and not macwarden's own credential), `missing-in-lnd` (registry active, LND lacks it), `revoked-but-present` (registry revoked, LND still has it), `pending-replacement` (an active entry `replaces` this one: a rotation is staged), `replacement` (this entry `replaces` an active one), `invalid-replacement` (a `replaces` link macwarden could not have written: a different label, an earlier creation time, a chain, a cycle or a second claimant; the text output says to restore the registry from a trusted copy), `rejected` (`--verify` result `rejected`), `expired` (an active entry LND still holds whose earliest `time-before` caveat is not after now), `expiring` (the same, but within the `--expiring-within` window, 7 days by default), `canary-triggered` (watch's canary guard denied uses of this root key ID; the row carries `canary: {uses, firstUse, lastUse}`, its text status starts with `CANARY TRIGGERED <n> times, last <time>: assume this credential's location is compromised`, and the text output ends with a line naming every triggered canary). LND enforces every first-party caveat, so the earliest `time-before` of the recorded caveats is the effective expiry; each row's `expires` is that instant (RFC 3339 UTC, seconds) for an active entry LND holds, otherwise `null`.

Advice commands in the text status run as printed when given the same connection and `--registry` flags as the inventory (or the `MACWARDEN_*` environment) (1.1.1, RL-05). `expired` adds `revoke with: macwarden revoke <target>`, where the target is the label only when it names exactly one active entry on the node (as `revoke` V6 requires), otherwise the root key ID (for example while a rotation is staged); root key ID 0 and macwarden's own credential get no revoke command. `expiring` adds `rotate with: macwarden rotate <label> --out <file>` only for a row `rotate` accepts: labelled, not root key ID 0 or macwarden's own, not a staged replacement or an original that already has one, no invalid link, no `lnd-custom` caveat (a canary), not `UNASSESSED`; `ADMIN` adds `--allow-admin`. `--out` defaults to `<label>-<YYYY-MM-DD>.macaroon` (today's UTC date) in the directory of the recorded `outPath`, or the current directory when none is recorded; it must not exist when rotate runs. Arguments are quoted for the shell as in Global conventions.

$ macwarden inventory --verify

0               —            —        —     —            default root key: cannot be individually revoked

9001772650113   btcpay       RECEIVE  0d    —            replacement, accepted

`result`: `{"node":{"pubkey","alias","network","version"},"rootKeys":[{"rootKeyId","inLnd","flags":[…],"verify":"accepted"|"rejected"|"error"|"not-checked","expires":"<RFC 3339>"|null,"entry":{"label","grade","permissions","caveats","createdAt","status","fingerprint","outPath","replaces","replacedBy"}|null}]}`. Rows sorted by root key ID numerically. Without `--verify`, `verify` is `"not-checked"`. With `--expiring-within`, `result.expiring` is `{"within":"<n><unit>","count":<n>}`: the number of rows flagged `expired` or `expiring`, and text output ends with a line stating that count.

Exit: 0 (also when rows are flagged), 2, 3, 4 or 5; with `--expiring-within`, 1 when `expiring.count` > 0 (`ok: true`), so a scheduled job can alert before a credential stops working.

**N7** `--report markdown|csv|json [--out <file>]` adds access-review evidence built from the joined rows and every registry entry for this node, revoked entries included: generated time, node, macwarden version, and per root key ID its label, status, grade, permissions, earliest `time-before`, created, revoked and revoke-evidence fields, caveats, rotation links (`replaces`, `replacedBy`), last use and call count when usage data exists (otherwise "not observed"), denied canary uses `canary: {uses, firstUse, lastUse}` when watch's guard recorded any (otherwise `null`), and flags `default-root-key`, `own-credential`, `unknown`, `missing-in-lnd`, `revoked-but-present`, `admin-grade`, `no-expiry`, `expired`, `unlabelled`, `canary-triggered`. It closes with control observations (incident response, only when a canary was triggered; least privilege, periodic access review, prompt removal) naming the root key IDs a reviewer should decide on, and an empty reviewer sign-off; it states that it does not by itself establish compliance with any framework (`limitations` in JSON). Every format carries all of this. JSON is the structured review. Markdown has the report identity, totals and flag counts, the limitation statement, one table row per root key ID with every scalar field (including replaces, replaced by and canary uses), permissions and caveats sections, the control observations and the sign-off table. CSV is one table with exactly one header row, one row per root key ID, so any RFC 4180 reader loads it: columns `root_key_id, in_lnd, label, status, grade, permissions, expires_at, created_at, revoked_at, revoke_evidence, replaces, replaced_by, last_used, calls, flags, caveats, canary_uses, canary_first_use, canary_last_use, controls, control_observations, generated_at, macwarden_version, node_pubkey, node_alias, node_network, node_version, reviewer, review_date, review_decision, review_notes, limitations`. List cells join with a space (`permissions`, `flags`) or `; ` (`caveats`, `controls`); `controls` names the control observations that list this root key ID and `control_observations` gives each as `<control>: <observation>` joined with ` | `, so each control's ID list is the rows naming it (a control naming no ID has no row); the report-level columns from `generated_at` on repeat the same value on every row, and the sign-off columns are empty for the reviewer to fill. Totals are counts over the rows. Ordering is numeric by root key ID, so two runs with no change produce identical reports. CSV is RFC 4180 with CRLF line ends; a field starting with `=`, `+`, `-`, `@`, tab or carriage return is prefixed with `'` so spreadsheets never evaluate it. Markdown escapes `|`, `\`, `<` and `>` in cells. Every text field passes credential recognition and control characters are replaced. Without `--out` the report is the text output; with `--out` it is written through the `bake` writer (exclusive create, verified owner-only as in B7, never overwritten; an existing file, or a name refused on Windows as in B4 (checked before any request) → exit 3 at N7) and the text output adds one line naming it. `--json` keeps the inventory envelope and adds `result.report` `{"format","path"|null,"review"}`. `--report` with an unknown format, or `--out` without `--report` → exit 2.

Acceptance: [Acceptance: online commands and inventory](#acceptance-online-commands-and-inventory), plus: two runs with no changes in between produce identical `result`; the registry file's bytes and mtime are unchanged after a run; after a root key regeneration (`changepassword --new_mac_root_key` run by the test on the fixture; macwarden's own macaroon is then re-baked from the new `admin.macaroon`, since the old one is invalid too) `--verify` flags every previously accepted entry `rejected`.

### 4. `bake` (online, mutating)

`macwarden bake --label <name> (--preset <name> | --permissions <e:a,…> [--uri </pkg.Svc/Method,…>] | --uri <…>) [--expires <n>(m|h|d)] --out <file> [--allow-admin] [--break-lock] [--dry-run] [--json]` + online flags — needs `macaroon:generate`, `macaroon:read`, `info:read`.

Labels: `^[A-Za-z][A-Za-z0-9._-]{0,63}$` (so never all digits: a numeric argument is a root key ID). `--expires`: `n` an integer from 1 to 99999.

Canary: `macwarden bake --label <name> --canary [--preset … | --permissions … | --uri …] [--expires …] --out <file>` bakes a decoy. Without a permission flag it gets `info:read onchain:read offchain:read address:read invoices:read peers:read`: it looks like an ordinary read-only credential and covers the reconnaissance calls a thief makes first (node info, balances, channels, invoices, peers, addresses). A canary carries only READ or RECEIVE permissions; anything else (SPEND, OPERATE, ADMIN, UNASSESSED) is refused even with `--allow-admin` (exit 2, B3), because if the guard drops between LND's macaroon check and its middleware loop, LND runs the call with the macaroon's own permissions. The installation's canary caveat name is created once, under the registry lock, in `<registry>.canary.json` (owner-only, `{"schema":1,"caveatName":"<word>-<8 hex>"}`, never containing "canary" because `lncli printmacaroon` shows it). B14 verifies the macaroon with LND first; then the canary caveat `lnd-custom <caveatName> <16 random hex>` is appended (HMAC chain as in `attenuate`) and the result is written and recorded with that caveat. LND accepts a macaroon with a custom caveat only while a middleware registered for that name is connected, so a canary is refused by LND itself unless `macwarden watch` runs; while it runs, every **permitted** use is denied and alerted (Commands > 8). LND rejects a call the canary is not permitted to make (for example a payment with the default read permissions) and an expired or IP-mismatched canary before any middleware sees it: such attempts fail without an alert. Give a canary the permissions an attacker would try first, within READ and RECEIVE. Warning `canary-requires-watch`. `--dry-run` creates nothing.

Presets (sent to BakeMacaroon as-is):

| Preset | Permissions | Grade |
|---|---|---|
| `read-only` | `info:read onchain:read offchain:read address:read invoices:read peers:read` | `READ` |
| `invoice-only` | `info:read invoices:read invoices:write` | `RECEIVE` |
| `pay-only` | `info:read uri:/routerrpc.Router/SendPaymentV2 uri:/routerrpc.Router/TrackPaymentV2 uri:/lnrpc.Lightning/DecodePayReq` | `SPEND` |

`pay-only` uses `uri:` permissions because `offchain:write` also allows intercepting HTLCs, disabling channels and changing channel policy. The method names are checked against the committed ListPermissions snapshot when the test vectors are generated.

Steps (B1–B16):

1. **B1** Parse: `--preset` together with `--permissions`/`--uri`, unknown preset, missing `--label` or `--out`, invalid label, empty permissions, bad `--expires` → exit 2.
2. **B2** ENV → exit 2.
3. **B3** Grade the requested permissions: `UNASSESSED` or any `unassessed-*` warning → exit 2 listing them; `ADMIN` without `--allow-admin` → exit 2.
4. **B4** `--out` exists → exit 3. On Windows, a name that Windows normalises or maps to a device is refused → exit 3 ("output path refused"), because Node creates the literal name while other programs open the normalised one: any path component that ends in a dot or a space, is a reserved device name (`CON`, `PRN`, `AUX`, `NUL`, `COM0`–`COM9`, `LPT0`–`LPT9`, `CONIN$`, `CONOUT$`, with or without an extension, any case), contains `:` (an alternate data stream) or a character Windows does not allow in names, and any device-namespace path (`\\.\`). Every command that writes `--out` or `--out-dir` applies the same rule before it creates anything.
5. **B5** OWN → exit 4.
6. **B6** Open the registry → exit 3 if unreadable or invalid. Unless `--dry-run`: take the lock → exit 3 if held.
7. **B7** Unless `--dry-run`: reserve `--out` so that it is owner-only before any byte is written, and verify that; any failure → exit 3 at this step with "cannot reserve output file: <reason>" and nothing written.
   - POSIX: create it exclusively (`wx`, mode `0600`) and keep the handle, then read the mode and owner back through that handle. A group or other permission bit, or another owner, gets one `chmod 0600`; if the file is still not private (a file system that does not store modes, such as WSL drvfs `/mnt/c`, vfat, exFAT or CIFS), it is removed → exit 3. There is no best-effort mode on POSIX.
   - Windows: the fixed System32 PowerShell helper (the path is passed in its environment) creates the file (`CreateNew`) with a security descriptor that is owner-only from the first instant: owner = the current user's SID, a protected DACL with one entry granting that SID full control, nothing inherited from the folder. No other account can open any handle to it, including one that only changes its permissions, so a folder that grants others change-permissions cannot be used to reopen the file. macwarden then opens it with an exclusive share mode (fails while another handle with data access exists, and blocks new ones until the bytes are written) and, while holding that handle, reads back the owner and DACL of the object at the path. An owner other than the current user means the file is not the one created → exit 3, the file is left untouched. An entry for another account, an inherited entry or an unprotected DACL → the file is removed, exit 3. A helper that is unavailable or fails → exit 3. Only on a volume that stores no Windows permissions (FAT, exFAT) is the file created without an ACL, with warning `acl-best-effort` ("the volume stores no Windows permissions (FAT or exFAT): anyone with access to the volume can read the file").
   - From here until B15, any failure removes the empty file. The text output names the verified protection: `(0600, verified)`, `(owner-only Windows ACL, verified)`, or `(no Windows permissions on this volume)` with the warning.
8. **B8** GetInfo → exit 4/5. ListPermissions (`snapshot-drift`). An active entry with this label for this node's pubkey → exit 2.
9. **B9** `--dry-run`: print label, permissions, grade, caveats and "root key ID: allocated at bake time"; exit 0. Only read-only calls were made; nothing was locked or created.
10. **B10** ListMacaroonIDs → exit 4/5. Draw a fresh root key ID (architecture.md); after 16 colliding draws → exit 5.
11. **B11** BakeMacaroon (`allow_external_permissions` never `true`). The pending entry for the chosen ID is already saved (Registry and lock). On failure, one ListMacaroonIDs: ID present (the call succeeded but the response was lost) → exit 7, pending entry kept, follow-up `macwarden revoke <id>`; ID absent after a definite LND error response or a refused connection → exit 4 (transport) or 5 (LND error), pending entry removed, nothing changed; ID absent after a request that reached LND but got no complete response (timeout, reset, cancellation) → exit 7, because LND may still apply it: pending entry kept, follow-up `macwarden revoke <id>` (it deletes the key if it appears, or closes the pending entry by ID if it never does); list fails → exit 7 "LND state unknown — run `macwarden inventory`", pending entry kept.
12. **B12** Decode the response; root key ID and permissions must equal the request, and the macaroon must carry no caveat (BakeMacaroon never adds one; a custom caveat would make the credential depend on a middleware; 1.2.1). Mismatch → exit 7. `rotate` applies the same at S11.
13. **B13** With `--expires`, add `time-before <now + duration>` offline, the instant written as RFC 3339 UTC with seconds precision (fraction dropped) and `Z` (e.g. `2026-12-31T09:00:00Z`).
14. **B14** Verify accepted on these final bytes. Not accepted (rejected, error or timeout) → exit 7. This catches a broken caveat before anything is written.
15. **B15** Write the bytes to the reserved handle, flush, close. Failure → exit 7, file removed.
16. **B16** Append the registry entry (`status:"active"`, `verified:true`), save atomically, release the lock. Failure → exit 7; the message prints the entry (no credential) and says the file is valid.

For every exit 7 in B12–B15, macwarden first updates the pending entry (`status:"active"`, `verified:false`, `outPath:null`) if the registry is writable, and the follow-up is `macwarden revoke <id>`. If that update fails, the pending entry saved before B11 still exists, so the follow-up is the same; `--unregistered` is never needed.

```text
$ macwarden bake --label btcpay --preset invoice-only --expires 90d --out ./btcpay.macaroon
baked  btcpay  root key ID 4831990234117  RECEIVE  fp:3f9a1c0e5b7d2a44
caveats  time-before 2027-01-01T00:00:00Z
wrote ./btcpay.macaroon (0600, verified); registry updated
```

`result`: the registry entry (below); with `--dry-run`: `{"dryRun":true,"label","permissions","grade","caveats"}`.

Acceptance: [Acceptance: bake](#acceptance-bake), plus: `ADMIN` without `--allow-admin` and `UNASSESSED` requests exit 2 with zero LND calls; the written file's fingerprint equals the registry's; a lock held → exit 3 with zero LND calls; two concurrent bakes on one registry → one succeeds, the other exits 3.

### 5. `revoke` (online, mutating)

`macwarden revoke <label | root-key-id> [--target-file <file>] [--unregistered] [--yes] [--break-lock] [--dry-run] [--json]` + online flags — needs `macaroon:write`, `macaroon:read`, `info:read`.

The target file is the macaroon being revoked (default: the entry's `outPath`, used only if its fingerprint matches the entry and its `time-before`, if any, has not passed). With a usable target file macwarden proves LND rejects it; otherwise it confirms the root key ID is absent from ListMacaroonIDs and reports "by ID only". (`--macaroon` stays macwarden's own credential.)

Steps (V1–V13):

1. **V1** Parse. An argument of digits only must be a canonical decimal uint64 (no leading zeros, ≤ 18446744073709551615); otherwise it must be a valid label. Anything else (`-1`, `+5`, `0x10`, `007`, `18446744073709551616`) → exit 2. ID 0 → exit 2 (SAFE-03).
2. **V2** ENV → exit 2.
3. **V3** `--target-file` given: read and decode offline → exit 3 on failure. Decoded root key ID 0 → exit 2; numeric target and a different decoded ID → exit 2.
4. **V4** OWN → exit 4. Numeric target equal to the own macaroon's root key ID → exit 2.
5. **V5** GetInfo → exit 4/5. ListPermissions (`snapshot-drift`).
6. **V6** Open the registry (no lock) → exit 3. Resolve among entries for this node's pubkey only: a label must match exactly one `active` entry (else exit 2, listing candidates); a numeric target uses the entry with that ID for this node; an entry with that ID only for another node → exit 2 without `--unregistered` (the operator may have meant that node; the message names `--unregistered`), while with `--unregistered` it is this node's unregistered ID, revoked and recorded under this node's pubkey (1.1.1, RL-04: root key IDs are per node, and small IDs from `lncli bakemacaroon --root_key_id` exist on every node); no entry → exit 2 unless `--unregistered` (message: other tools and other operators store root keys in the same LND store — Lightning Terminal is reported to). Resolved ID equal to the own macaroon's → exit 2. `--target-file` decoded ID differs from the resolved ID → exit 2. Default target file (1.1.1, RL-01): when `outPath` decodes to the entry's fingerprint on another root key ID, the entry's root key ID or fingerprint was edited (a fingerprint covers the identifier, which carries the root key ID) → exit 3, restore the registry from a trusted copy. A file there on another root key ID with another fingerprint is another credential at a reused path (typically a replacement baked or staged where the app reads its file), and a file on the entry's root key ID with another fingerprint is another macaroon on that key; neither is the target, so the revocation is proven by ID only. Before 1.1.1 a reused path refused every revoke, rotate and finish of the old credential.
7. **V7** ListMacaroonIDs → exit 4/5. ID absent and no active entry → exit 5 "nothing to revoke". ID absent with an active entry (an earlier run was killed after deleting) → repair: plan, `--dry-run` exit 0, confirmation as in V9, lock, mark revoked with `revokeEvidence:"by-id-only"`, exit 0 saying it was already absent; LND is not called again.
8. **V8** With a usable target file: verify accepted as a baseline; record the outcome. Transport/authentication errors stop with exit 4 and protocol errors stop with exit 5 at V8, before mutation; unexpected errors remain internal failures. Only a completed normalized negative acceptance result means not accepted. Not accepted → proof will be by ID only.
9. **V9** Print the plan (label, root key ID, grade, proof method). `--dry-run` stops here (exit 0). Unless `--yes`, ask the operator to type the label (the root key ID for an unregistered target); wrong text or EOF → exit 6; stdin not a TTY → exit 6 (SAFE-05).
10. **V10** Take the lock → exit 3 if held, nothing sent. Re-read the registry; the entry changed since V6 → exit 3, nothing sent.
11. **V11** DeleteMacaroonID. Error or `deleted:false` → one ListMacaroonIDs: ID present after a definite LND error response, a refused connection or `deleted:false` → exit 5 (still valid), registry unchanged; ID present after a request that reached LND but got no complete response (timeout, reset, cancellation) → exit 7, registry unchanged, because LND may still delete it: the message prints the exact rerun, which deletes the key if it is still present or repairs the record through V7 if it is gone; absent → continue only with V12's prescribed read-only proof, without repeating the list or retrying deletion; list fails → exit 7 "LND state unknown — run `macwarden inventory`". A subsequent proof failure stops and reports uncertainty.
12. **V12** Verify: the ID is absent from ListMacaroonIDs (unless V11's list already showed it) and, if V8 was accepted, verify rejected. Either fails → exit 7; registry not marked revoked.
13. **V13** Registry: `status:"revoked"`, `revokedAt`, `revokeEvidence:"rejected"|"by-id-only"` (no other value is accepted when the registry is read); an unregistered ID gets a new entry with `label:null`. Save, release the lock. Write failure → exit 7 (a rerun repairs it via V7). An unregistered ID had no entry, so V7 refuses a rerun with exit 5; the exit-7 message says the ID was deleted from LND, the record could not be saved, and no further action is needed, and prints no rerun command. Print the revocation-scope sentence.

```text
$ macwarden revoke btcpay --yes
revoked  btcpay  root key ID 4831990234117  fp:3f9a1c0e5b7d2a44
proof    ID absent from LND; macaroon rejected (root key missing)
New requests with this macaroon are now rejected. Streams opened before the revoke stay open until they disconnect; if the credential may be compromised, restart LND.
```

Without a usable target file the proof line reads `ID absent from LND (verified by ID only)`.

`result`: `{"rootKeyId","label"|null,"evidence":"rejected"|"by-id-only","repaired":<bool>,"entry"}`; with `--dry-run`: `{"dryRun":true,"rootKeyId","label"|null,"grade"|null,"proof":"rejected"|"by-id-only"}`.

Acceptance: [Acceptance: revoke](#acceptance-revoke), plus: after a revoke, a macaroon on another root key ID is still accepted; every refusal in V1–V6 makes zero mutating calls, and V1–V4 refusals make zero LND calls.

Rotation S4 amendment (CP-038): independently recompute the grade of recorded permissions and refuse grade inconsistency with exit 3. If a readable old credential exists, refuse its fingerprint mismatch with exit 3; missing or unusable old files require explicit informed approval to use recorded permissions. Show the exact grade and permissions and explain that the old credential cannot prove them; require the typed label before taking a lock, reserving output or issuing a replacement. Decline, wrong text, EOF or non-TTY exits 6 at S4; stage --yes remains invalid. Dry-run shows this unproven authority and existing expiry value/requested duration without confirmation or changes.

### 6. `rotate` (online, mutating)

Two invocations (SAFE-04):

`macwarden rotate <label> --out <file> [--allow-admin] [--break-lock] [--dry-run] [--json]` — **stage**: bake and verify a replacement; the old credential is untouched.
`macwarden rotate <label> --finish [--yes] [--break-lock] [--dry-run] [--json]` — **finish**: revoke the old credential after the operator has switched the app.

Stage needs `macaroon:generate`, `macaroon:read`, `info:read`; finish needs `macaroon:write`, `macaroon:read`, `info:read`. `--out` or `--allow-admin` with `--finish`, or `--yes` without `--finish` → exit 2 (step `S1`/`F1`).

A **pending replacement** for entry O is an `active` entry N for the same node with `replaces: O.rootKeyId`, where O is `active`. An entry whose `replaces` names a revoked entry (a finished rotation) or an entry no longer in the registry (the revoked original was pruned) is not a pending replacement: `rotate`, `respond` and `inventory` all treat it as an original that can be rotated again (1.1.1, RL-07; before, `respond` planned `stage` for it and `rotate` refused it at S3). To abandon a staged rotation: `macwarden revoke <new root key ID>`.

Stage steps (S1–S13):

1. **S1** Parse; invalid label or missing `--out` → exit 2.
2. **S2** ENV → exit 2.
3. **S3** Open the registry → exit 3. Resolve offline: exactly one `active` entry O with this label that is not itself a pending replacement (none → exit 2). One registry may hold several nodes and `bake` allows a label on each (1.1.1, RL-04): when the label is active on several nodes, S3 reads the TLS certificate and own macaroon and calls GetInfo (read-only; failures exit 4/5 at S3) and only the connected node's entry counts (none → exit 2). Before 1.1.1 this exited 2 "label is active on several nodes", which also failed the credential in `respond`. An active entry on this node naming O in `replaces` that macwarden could not have written (a different label, the same root key ID, or created before O) → exit 3 "registry tampering", restore the registry from a trusted copy; the message for "created before O" also names the abandon command `macwarden revoke <N id>`. Exception (1.1.1, RL-02): a link recorded up to 24 hours before O is accepted when it has exactly the shape a 1.1.0 stage wrote under a clock behind O's recorded creation time: O's permissions (as a set) and grade, at most one caveat and only `time-before`, no `replacedBy`, and `createdAt` in `Date.toISOString()` form (milliseconds and `Z`). The time order is a plausibility check, not a boundary (whoever can edit the registry can edit `createdAt` too), and such a link grants no more than O; an older, broader or otherwise different backwards link stays tampering. O carries an `lnd-custom` caveat (a canary or another custom caveat) → exit 2: a rotation would replace it with an ordinary credential; revoke it and bake a new canary instead. O already has a pending replacement N → exit 2 listing both IDs: "finish with `macwarden rotate <label> --finish` only after confirming the app uses <N.outPath>, or abandon with `macwarden revoke <N id>`".
4. **S4** Permissions to bake: a file at `O.outPath` on another root key ID is not O's credential: with another fingerprint (a reused path) it is handled as a missing file, so O's recorded permissions need the informed approval below; with O's fingerprint the entry was edited → exit 3 (as V6). If `O.outPath` exists and its fingerprint matches O, decode it; its permissions differ from O's → exit 3 "registry entry does not match the credential"; it carries an `lnd-custom` caveat that O does not record → exit 3 (the registry caveat list is editable metadata, so the decoded file decides whether O is a canary; restore the registry from a trusted copy), before any lock or LND call. Otherwise propose O's permissions with the informed approval required by the Rotation S4 amendment.
5. **S5** Every `bake` offline refusal on those permissions: re-grade; `UNASSESSED` → exit 2; `ADMIN` without `--allow-admin` → exit 2; O's recorded `requested` duration (reused at S11) cannot produce a `time-before` instant from now → exit 3, before any lock or LND call (1.1.1, RL-03); `--out` exists or is a name refused on Windows (B4) → exit 3.
6. **S6** OWN → exit 4. O's root key ID equal to the own macaroon's → exit 2.
7. **S7** Unless `--dry-run`: take the lock (exit 3); re-read the registry, and if O changed or a pending replacement appeared since S3 → exit 3; reserve `--out` (as B7).
8. **S8** GetInfo → exit 4/5; O's `nodePubkey` differs → exit 2. ListPermissions (`snapshot-drift`). ListMacaroonIDs → exit 4/5; O's ID absent → exit 5 "old root key ID is not in LND". If S4 proved permissions from O's credential file, verify it accepted with its own permissions (read-only; also in `--dry-run`): not accepted → exit 5 "old credential cannot prove the recorded authority; nothing changed"; transport or authentication failure → exit 4.
9. **S9** `--dry-run`: print old ID, grade, permissions, caveat kinds and the stage and finish plans; exit 0.
10. **S10** Draw a fresh ID (B10) and bake (B11) with O's permissions.
11. **S11** Decode and compare (B12); add `time-before` with the same duration as O's `requested` value, if O had one (B13).
12. **S12** Verify accepted on the final bytes (B14); write `--out` (B15).
13. **S13** Record N: same label, `replaces: O.rootKeyId`, `status:"active"` (B16). N's `createdAt` (also in the pending record saved at S10) is the later of now and O's `createdAt` (1.1.1, RL-02), so a clock behind O's recorded creation time never makes macwarden's own link look created before O. Print "staged", the new path, the grade and permissions, and the next steps: switch every replica and config copy of the app to the new file, then `macwarden rotate <label> --finish`; to abandon, `macwarden revoke <N id>`. Exit 0.

Failures in S10–S13 behave as the matching `bake` step, except that the follow-up always names the new root key ID — `macwarden revoke <new id>`, plus `--unregistered` when no entry could be recorded — because the label also names O; the pending entry saved before S10 keeps `replaces`, so it counts as a pending replacement until revoked, and `--unregistered` is never needed. A BakeMacaroon request with no complete response is handled as in B11: exit 7 with the pending entry kept, never "nothing changed". O stays valid and unchanged in every case.

Finish steps (F1–F12):

1. **F1** Parse → exit 2.
2. **F2** ENV → exit 2.
3. **F3** Open the registry → exit 3. Resolve O as in S3 (a tampered replacement link → exit 3) and its pending replacement N; none → exit 2 "nothing staged; run `macwarden rotate <label> --out <file>` first".
4. **F4** OWN → exit 4. O's root key ID equal to the own macaroon's → exit 2.
5. **F5** GetInfo → exit 4/5; O's `nodePubkey` differs → exit 2. ListPermissions (`snapshot-drift`).
6. **F6** ListMacaroonIDs → exit 4/5. N's ID absent → exit 5 "staged replacement is not in LND; clear it with `macwarden revoke <N id>`". O's ID absent (an earlier finish was killed after deleting) → first pass the F7 replacement file, fingerprint and acceptance proof (missing/mismatched file → exit 3; not accepted → exit 5; registry unchanged), then repair: plan, `--dry-run` exit 0, confirmation as in F8, lock and re-read both entries as in F9, mark O revoked (`by-id-only`, `replacedBy`), exit 0; no second delete is sent.
7. **F7** `N.outPath` must exist with a matching fingerprint (else exit 3) and verify accepted (else exit 5 "new credential is not accepted; nothing changed"), including before the F6 absent-old-ID repair. When O is present, baseline for O as V8 (O's `outPath`, if usable as defined for `revoke`). A file there that is not O's (another credential at a reused path, such as the replacement staged where the app reads its file) leaves the proof by ID only; O's fingerprint on another root key ID → exit 3 as in V6.
8. **F8** Show old and new root key ID, grade, permissions and the new path. `--dry-run` stops here (exit 0). Unless `--yes`, the prompt reads: "Finishing revokes root key ID <O id>. Continue only if every replica and config copy of <label> now uses <N.outPath>. Type <label> to continue:"; wrong text or EOF → exit 6; stdin not a TTY → exit 6.
9. **F9** Take the lock → exit 3. Re-read the registry; O or N changed since F3 → exit 3, nothing sent.
10. **F10** DeleteMacaroonID(O) with V11 semantics → exit 5 (old still valid) or 7; a request with no complete response while O is still listed exits 7 with the exact `rotate <label> --finish` rerun, never "still valid".
11. **F11** Verify O rejected (V12) and N still accepted. Either fails → exit 7; registry not changed.
12. **F12** Registry: O `revoked` with `revokedAt`, `revokeEvidence`, `replacedBy: N.rootKeyId`. Save, release the lock. Failure → exit 7 (a rerun repairs it via F6). Print the revocation-scope sentence.

macwarden never retries a mutating call blindly. A killed process leaves LND in the state of the last completed call; `inventory` shows it. The old credential stays valid at every failure point before F10 completes.

On failure `error.step` names the step (`S11`, `F10`, …).

Acceptance: [Acceptance: rotate](#acceptance-rotate) and [rotation failure injection](#rotation-failure-injection) cases 1–8; every failure case asserts with the `lncli` acceptance probe that the old macaroon is still accepted unless F10 completed.

### 7. `attenuate` (offline, writes one file)

`macwarden attenuate <file | -> --out <file> [--expires <n>(m|h|d)] [--ip <address> | --ip-range <cidr>] [--dry-run] [--unsafe-arg] [--json]`

Adds first-party caveats to a copy of an existing macaroon, offline, the way `lncli constrainmacaroon` does: for each caveat the new signature is HMAC-SHA256 keyed with the previous signature over the caveat text. It never contacts LND (SAFE-07, SAFE-08) and never changes the input.

1. **A1** Parse arguments: exactly one input; `--out` required; at least one of `--expires`, `--ip`, `--ip-range`; `--ip` and `--ip-range` together, a repeated flag, a missing value or an unknown flag → exit 2. `--expires` as in `bake` (`n` from 1 to 99999). `--ip` takes one IPv4 or IPv6 address (no zone, no leading zeros in IPv4 octets, no IPv4-mapped IPv6 form); `--ip-range` takes a CIDR. Values are written in Go's canonical text, as LND writes them: IPv6 in RFC 5952 form, and a range with its host bits cleared (`10.1.2.3/8` → `iprange 10.0.0.0/8`). Invalid → exit 2.
2. **A2** Unsafe Node diagnostic settings, as in `bake` B2 → exit 2.
3. **A3** `--out` as in `bake` B4: protected path or an existing file → exit 3; never overwritten.
4. **A4** Read the input with `readCredential` and decode it → exit 2 or 3 as in `inspect`. An undecodable input is never attenuated.
5. **A5** Append, in this order, `time-before <now + n>` (RFC 3339 UTC, seconds, `Z`, as B13), then `ipaddr <address>` or `iprange <cidr>`. Decode the child and confirm it equals the input's root key ID, location and permissions with exactly the appended caveats after the original ones; otherwise exit 8.
6. **A6** `--dry-run`: print the plan and child facts; write nothing; exit 0. Otherwise write the child to `--out` through the `bake` writer (exclusive create, verified `0600` or verified Windows owner-only ACL as in B7, warning `acl-best-effort` only on a FAT or exFAT volume) → exit 3 on failure ("cannot create output file: <reason>"), removing an unwritten file. Print. Exit 0.

Warnings: `shared-root-key` always (the copy shares the input's root key ID, so revoking that ID revokes both; the registry does not track the copy); `ip-caveat-rest-proxy` with `--ip`/`--ip-range` (LND checks the peer address: REST clients appear as the REST proxy, Tor clients as the local Tor daemon, and clients behind Lightning Terminal, LNC or a reverse proxy as that proxy); `expiry-clock` with `--expires` (the expiry comes from this machine's clock and LND checks it against the node's clock); `earlier-expiry-kept` when the input already has an earlier `time-before` (caveats only narrow); `existing-ip-caveat` when the input already has an IP caveat (LND requires each to match); `unsafe-arg` and `acl-best-effort` as elsewhere.

`result`: the `inspect` result of the child plus `{"dryRun","out"|null,"parentFingerprint","added":[…]}`. Only the `--out` file contains credential bytes (SAFE-01).

Acceptance: the appended bytes and signature equal an independent go-macaroon v2 construction from a known root key; for every caveat-bearing vector the child decodes to the input plus the appended caveats; refusals create no file; the leak test covers the command; against the pinned regtest LND, `--ip` output is byte-identical to `lncli constrainmacaroon --ip_address`, matching IP and future expiry are accepted, a non-matching IP is rejected, and `deletemacaroonid` of the shared ID rejects both the input and the copy.


### 8. `watch` (online, read-only middleware)

`macwarden watch [--lnd-grpc <host:port>] [--middleware-name <name>] [--until <n>(s|m|h|d)] [--alert-command <path>] [--alerts-only] [--payment-journal <path>] [--json]` + online flags (`--registry` as usual) — needs `macaroon:write` (RegisterRPCMiddleware) and `info:read`. LND must run with `rpcmiddleware.enable=true`. **Do not set `rpcmiddleware.addmandatory`**: it blocks every RPC whenever no watcher is connected.

Registers with LND's RegisterRPCMiddleware over gRPC (LND's REST WebSocket proxy limits each message to 4 MiB, which would break the stream on large RPC responses and fail them; gRPC carries up to LND's 200 MiB limit). `--lnd-grpc` defaults to the `--lnd-rest` host with port 10009 (env `MACWARDEN_LND_GRPC`). An explicit port 443 (`--lnd-grpc host:443`) is kept as 443 (1.2.1). The same pinned TLS certificate and own macaroon are used.

Steps (W1–W7):

1. **W1** Flags → exit 2 naming the flag and rule. `--middleware-name` 5–48 of `[A-Za-z0-9._-]` (default `macwarden-watch`); `--alert-command` an absolute path to an existing regular executable file (POSIX: an execute bit and `access(X_OK)`; Windows: an `.exe` or `.com` file, since a `.cmd`, `.bat` or `.ps1` script cannot run without a shell); `--until` 1–999999 with unit s/m/h/d; the whole range is honoured (a duration beyond the 2^31−1 ms of one timer, about 24.8 days, is waited for in chunks against one monotonic deadline); `--payment-journal` a nonempty path.
2. **W2** ENV check → exit 2.
3. **W3** OWN check: TLS cert and own macaroon readable and decodable, holding `macaroon:write` and `info:read` (or the method URIs) → exit 4.
4. **W4** Registry and `<registry>.canary.json` readable → exit 3.
5. **W5** GetInfo (node identity) → exit 4/5. An interrupt before W6 (nothing registered or locked) → exit 6, step `cancelled`, message "interrupted"; one after W6 but before the first session registered → exit 6 naming the endpoint it was waiting for (1.2.1). LND's registration confirmation counts once: a repeated `reg_complete` does not start another session (1.2.1).
6. **W6** One watcher per registry: exclusive `<registry>.watch.lock` holding `{pid, hostname, domain}` (`domain` is the process domain: boot ID plus PID namespace on Linux, or silo on Windows), replaced only when its owner provably no longer runs → otherwise exit 3. On the same host an owner is gone when its record is from another boot, when its PID is this process's own (a restarted container running watch as PID 1 again), or when the PID no longer exists; an owner in another PID namespace or silo on the same boot cannot be probed and keeps the lock. Two containers that share a registry volume must not share a hostname. A lock whose owner record cannot be read (an earlier watch interrupted while creating it) is never removed automatically: exit 3 naming the file, to be deleted by the operator when no watch runs. A failed lock write removes the file it created, and on exit a watcher removes the lock only while it is still the file it created (same device and inode). A `<registry>.usage.json` that cannot be read → exit 3; one that is not valid is renamed to `<registry>.usage.json.corrupt-<time>` (never deleted) with warning `usage-file-quarantined`, and recording starts empty, so a damaged file cannot keep the watcher (and every canary) down. Otherwise exit 3. A stale lock is taken over atomically: it is renamed to a unique quarantine name, which only one process can do for a given file, and removed only if it is still the stale record that was read; otherwise it is put back without overwriting anything and the lock counts as held, so two watches starting at once never both run. With `--payment-journal`, the journal is then opened, locked and started (Payment journal below); any failure → exit 3, the watch lock released, nothing registered.
7. **W7** Register a **read-only** middleware (`<name>`); when the registry holds active canaries for this node, also register a middleware for the installation's canary caveat name (`<name>-guard`). LND without `rpcmiddleware.enable` → exit 4 with that fix (no retry); a refused registration (authentication, name already registered) → exit 4/3 (no retry). A stream lost after registration is re-registered with backoff 1 s doubling to 30 s. After any session of this run registered, "already registered" is LND still holding the lost stream (it notices only at its keepalive), so it is retried with the same backoff instead of ending the run. The connection is checked with an HTTP/2 PING every 30 s (20 s to answer) and TCP keepalive, so a peer that vanishes without closing (crashed host, dropped NAT entry) is detected and re-registered. Request IDs are forgotten at every new session, because LND restarts them.

Every intercepted message is answered immediately, before any other work: the read-only middleware always accepts; the canary guard always denies (`permission denied`). An intercept type this version does not know is answered the same way (accept for the observer, deny for the guard), and an internal error while deciding denies for the guard. Then, for each call (a stream counts once, however many messages it carries, and its final error is recorded once): the caller's macaroon is decoded in memory to its **credential ID** — `id:` + the first 16 hex of SHA-256 over the macaroon's identifier packet (version, nonce, root key ID, operations) — and its root key ID, and the bytes are dropped. Clients that append caveats per call (lncli adds a timeout caveat) keep one credential ID; fingerprints would differ. Request and response payloads and gRPC metadata are never read or recorded, except the request payloads `--payment-journal` reads (Payment journal below). An event is emitted: `<time>  <method>  root key <id>  <credential id>  <label|unregistered>` (label from the registry by non-zero root key ID; root key 0 is shared by LND's default macaroons and never labelled); `error <method> …` when the response is an error; for a canary `ALERT canary <label> used: <method> … request denied`. `--alerts-only` prints only canary and status events. Event output never waits on its reader: lines are queued (at most 1 MiB) and written off the event loop, because a reader that stops (a paused pager, a backed-up log shipper) would otherwise stall every intercept answer and so every node RPC. Lines that do not fit are dropped and reported by a status event `output fell behind: <n> event lines dropped` (counts and usage are unaffected); canary alerts and status events are never dropped. If nothing reads stdout at all, the final summary waits until it can be written. `--alert-command` runs the executable (no shell, no arguments, minimal environment, 10 s timeout) with the canary event JSON on stdin. A failed alert (non-zero exit, timeout, missing executable) raises warning `alert-failed`, a status event `ALERT COMMAND FAILED for canary <label>` and the `alertFailures` count. Event lines are written by a bounded queue off the event loop: a reader that falls behind loses ordinary lines (counted and reported in an `output-dropped` status line), and a full pipe that answers EAGAIN is retried with backoff rather than treated as closed, so canary alerts still reach a slow reader. Only a closed reader (EPIPE, EBADF) stops output. Attribution (decoding the caller's macaroon, recording usage, emitting the event) runs behind a bounded queue (20,000 calls or 16 MiB of macaroon bytes) and gets at most 20% of wall time (a token bucket with at most 5 ms banked), never before the next intercept's feedback: when callers outpace it, further attribution is dropped and counted in `droppedAttributions` (in the summary and in the usage file), so the node's RPC latency does not grow with the call rate. A dropped call costs a counter only: the caller's macaroon is copied out of the received frame only when attribution accepts the call. Canary uses never go through this queue: the guard denies at once and keeps one pending slot per registered canary plus one shared slot for unregistered conditions (bounded by the registry, not by the caller), handled on the next event-loop turn with the number of uses it collected, so a burst of ordinary calls can never hide a canary alert. Feedback for every message read in one event-loop turn is sent in one HTTP/2 write. **Capacity** (measured over a real local TLS HTTP/2 connection, 10,000 distinct macaroons, one Windows 11 desktop, Node 24): p99 feedback latency 77 ms at 100,000 calls per second sustained for 10 s, 233 ms at 160,000; at 200,000 calls per second the watcher saturates and latency grows (1.5 s after 5 s), approaching LND's 2 s intercept timeout. Above about 160,000 intercepted calls per second per node, run watch only for short observations. Fields from the stream are bounded before they are copied or decoded: a macaroon above 64 KiB is attributed `id:undecodable` without being copied, a method name above 256 bytes is recorded as `/unknown/Unknown`, and a custom caveat condition above 256 bytes is ignored. A session ends, and watch reconnects, when LND does not confirm the registration within 30 s, when a message stops arriving midway for 60 s, or when more than 16 MiB of feedback is waiting to be read, counting each unsent write as its bytes plus 1 KiB (an unsent HTTP/2 write holds about 200 to 400 bytes besides its data, so bytes alone let a million unread accepts hold over 600 MiB). A message split across chunks is collected in 64 KiB blocks as it arrives, so a message announced at up to 190 MiB costs what actually arrived, never the announced length. On reconnect the registry is re-read at most every 5 s (the periodic re-read every 60 s still runs, so a canary baked while sessions flap is guarded within 60 s), and every pass of the reconnect loop yields one event-loop turn. The reconnect backoff (1 s doubling to 30 s) starts again at 1 s only after a session stayed registered for 60 s.

Canary alerting is bounded because whoever holds a canary controls how often it is used: every use is denied at once, but per canary only the first use in a 10-second window raises an alert; further uses in that window are counted and reported in one summary alert (`repeats`) when it ends. A registered canary is tracked by its root key ID; every condition that is not a registered canary (anyone holding a canary can append custom caveats) shares one bucket, so invented conditions cannot multiply alerts. At most one `--alert-command` process runs at a time, and only the newest pending alert waits. The command gets SIGTERM after 10 s and SIGKILL after 12 s, sent to its whole process group on POSIX, so a command that ignores SIGTERM delays the next alert by at most 12 s. Canaries are re-read from the registry every 60 s and at every reconnect: a canary baked while watch runs is guarded within 60 s, by registering again (not counted as a reconnect). Priority output lines are capped at four times the normal output limit. The summary reports `canaryUses` (every denied use) and `canaryAlerts` (alerts raised).

Usage is aggregated per (node, credential ID, root key ID, method) as `{calls, errors, firstSeen, lastSeen}` and written to `<registry>.usage.json` (owner-only, atomic replacement) at exit and while running at most every 5 s, spaced by the file's size so that on average at most 64 KiB/s reach the disk. At most 20,000 records are kept: at capacity the least recently seen record is evicted, and the file records the number of evictions and the time of the last one (`evictions`, `lastEviction`). Calls watch could not attribute under overload are recorded as `droppedAttributions` and `lastAttributionDrop`. Serializing a full store takes about 10 ms. `recommend` prints no narrowing command when any record was evicted or any call went unattributed: either can belong to any credential, including one whose remaining records were all first seen later. To get a complete observation, stop watch, move the usage file aside and run watch again. **Usage file format, version 1** (`schema: 1`): an object with `schema`, `dropped` and `entries` (required) and the optional `evictions`, `lastEviction`, `droppedAttributions`, `lastAttributionDrop`, `canaryUses` and `coverage` (both from 1.0.1) and `coverageSpans` (from 1.1.0); optional fields are validated when present and fields this version does not know are ignored, so files from older and newer writers are read. Every timestamp in the file (`firstSeen`, `lastSeen`, `lastEviction`, `lastAttributionDrop`, `firstUse`, `lastUse`, `firstStart`, `lastEnd`, span start and end) must be a real UTC instant `YYYY-MM-DDThh:mm:ss[.fraction]Z`: a month 1 to 12, a day that exists in that month, hours 0 to 23, minutes and seconds 0 to 59 (`2026-99-09T12:00:00Z`, 30 February and `24:00:00` are refused, though they have the shape). Each pair must be in order, compared as instants: `firstSeen` ≤ `lastSeen`, `firstUse` ≤ `lastUse`, `firstStart` ≤ `lastEnd`, span start ≤ end. A file that breaks either rule is invalid (`invalid usage file`; inventory warns `usage-unreadable`, recommend exits 3 at R4), never partly used. watch keeps the order when the clock steps back: a later call never moves a `last…` time before the time already recorded. Registry timestamps (`createdAt`, `revokedAt`) follow the same instant rule. A change that older readers must understand to stay safe (for example a new reason to distrust the records) takes a new schema number, which this version refuses. The usage file and `<registry>.canary.json` are read only as regular files whose path and resolved target carry no protected name (SAFE-02), checked before they are opened, and only up to a size derived from their formats: 22,077,440 bytes for the usage file (1 KiB per usage record, 512 bytes per canary use or coverage record, 64 bytes per coverage span, 4 KiB for the rest) and 4 KiB for the canary configuration. A sidecar that fails these checks is unreadable (inventory warns `usage-unreadable`; recommend exits 3 at R4; watch exits 3 at W4 or W6) and its content is never parsed. Lock owner records (`<registry>.lock`, `<registry>.watch.lock`) are read only when the path itself is a regular file, not a symlink, of at most 64 KiB, and only through one descriptor whose file is that checked regular file (same device and inode; no-follow where the platform supports it), reading at most 64 KiB + 1 bytes; a record replaced after the check is not read, and one that grew past 64 KiB is refused like a larger record. This holds for the first owner read and for the stale-lock recovery, quarantine and release reads. The summary counts at most 10,000 distinct credential IDs. Only valid identities are recorded (a credential ID, a canonical root key ID up to 2^64−1; a usage or canary record in the file with any other root key ID makes the file invalid); a call without a decodable macaroon is counted in the events but never written. Writes run one at a time from a snapshot, and a record that arrives during a write stays pending for the next one. `canaryUses` holds, per node and registered canary root key ID, `{nodePubkey, rootKeyId, uses, firstUse, lastUse}` counted from the guard's denied uses (at most 1,000 records, least recently used dropped first); `inventory` shows them. `coverage` holds, per node, `{nodePubkey, firstStart, lastEnd, coveredSeconds, sessions}`: the first registration, the last moment watch was known registered, the whole seconds it was registered and the number of registrations (at most 64 nodes); `recommend` reports it as the observation window. `coverageSpans` holds, per node with a `coverage` record, `{nodePubkey, spans}`: the most recent registered spans `[start, end]`, oldest first (at most 256 per node, oldest dropped first, which only undercounts; overlapping spans in a file are merged, never counted twice). The covered-seconds counter starts where each span starts, so a clock step back cannot count time twice (1.2.1). It is a separate field so that 1.0.1 still reads the `coverage` records. All three are updated while running and at exit.

**Payment journal** (`--payment-journal <path>`; owner addition 2026-10-09, 1.2.0; off by default). Usage records say which credential called a payment method how often; the journal says which credential asked LND to pay which payment hash, so `reconcile` (Commands > 12) can compare that with what LND settled. Without the flag nothing below happens and no payload is read.

- **Methods.** The journaled methods are taken from the bundled ListPermissions snapshot of LND v0.21.4-beta: the payment-initiating `/routerrpc.Router/SendPaymentV2` and `/routerrpc.Router/SendToRouteV2`, and the payment-record deletions `/lnrpc.Lightning/DeletePayment` and `/lnrpc.Lightning/DeleteAllPayments` (a credential that can delete payment records can remove the settlement evidence `reconcile` relies on). Lightning's `SendPayment`, `SendPaymentSync`, `SendToRoute` and `SendToRouteSync` are not methods of v0.21.4-beta (the snapshot has none of them) and are not journaled. On-chain spends (`SendCoins`, `SendMany`, `SendOutputs`, channel opens and closes) carry no payment hash and are not journaled; their calls are still counted in the usage file.
- **What is read.** For a `request` intercept of a journaled method only, the middleware passes the serialized request (RPCMessage `serialized`) on to the journal; for every other method, every response and every stream authentication the payload is skipped as before. A payload above 64 KiB is not copied (the record says `payload-too-large`). From SendPaymentV2 (routerrpc.SendPaymentRequest) only `amt` (2), `payment_hash` (3), `payment_request` (5), `fee_limit_sat` (7), `amt_msat` (12), `fee_limit_msat` (13) and `amp` (22) are read; from SendToRouteV2 only `payment_hash` (1) and, inside `route` (2), `total_amt_msat` (6) and each hop's `amt_to_forward_msat` (6); from DeletePayment `payment_hash` (1) and `failed_htlcs_only` (2); from DeleteAllPayments `failed_payments_only` (1), `failed_htlcs_only` (2) and `all_payments` (3). Every other field is skipped by wire type and never copied, including `dest_custom_records` (which carries a keysend preimage), route hints, first-hop records and hop payloads. Scalars follow protobuf's last-one-wins; a field with an unexpected wire type is skipped; a truncated message, a varint over 10 bytes, a group or invalid UTF-8 in `payment_request` makes the record `malformed` (no hash). Parsing is one pass, linear in the payload.
- **Payment hash.** From `payment_request` when present: the BOLT11 text (at most 8,192 characters, else `invoice-too-long`) is decoded as bech32 without the 90-character limit (one case, valid characters, valid checksum, an `ln` prefix and an optional amount `<digits>[m|u|n|p]` with a whole number of millisatoshi), and the first `p` field of 52 groups with zero padding is the hash; anything else is `invoice-invalid`. The signature is not checked (LND does, and refuses the payment otherwise). Otherwise `payment_hash` when it is 32 bytes (other lengths: `malformed`); neither: `no-hash`. With `amp` set the hash is not recorded (`amp`): LND chooses an AMP payment's identifier itself. The invoice text is never stored; the copied payload is zeroed once decoded.
- **Amounts.** `amountMsat` is the invoice amount when the invoice carries one (`amountSource: "invoice"`), otherwise `amt_msat`, or `amt` × 1,000 (`request`); for SendToRouteV2 the last hop's `amt_to_forward_msat`, the amount that attempt delivers (`route`). `feeLimitMsat` is `fee_limit_msat`, or `fee_limit_sat` × 1,000, or `0` when neither is set (SendPaymentV2 then considers only zero-fee routes); for SendToRouteV2 the route's fee, `total_amt_msat` minus the delivered amount. A negative value gives `null`. Amounts are decimal strings.
- **Identity.** Each record names the caller by its **credential ID** (`id:` + 16 hex of SHA-256 over the macaroon identifier packet, as for usage) and its root key ID, decoded from the intercepted macaroon, which is then dropped. The credential ID groups every copy of one baked credential, including copies a client attenuated with further caveats (lncli adds a timeout caveat per call); the exact-token fingerprint (`fp:`) is deliberately not used, because it changes with every added caveat. A call without a decodable macaroon is journaled as `id:none` or `id:undecodable` with root key ID `none`. Two different credentials on one root key ID (for example two macaroons baked on root key 0) have different credential IDs.
- **Off the intercept path.** The observer answers first, as always. A journaled request is captured synchronously (a copy of its payload of at most 64 KiB and of the caller's macaroon) into its own bounded intake (1,024 calls or 8 MiB), separate from the attribution queue, so a flood of other calls cannot push payments out. Decoding and attribution run on later event-loop turns, at most 64 calls per turn and, like attribution, within a time budget of 20 % of wall time (a token bucket banking at most 5 ms; a turn always decodes at least one call, and when the budget is spent the next turn waits 5 ms), so a holder of a pay credential sending 64 KiB payloads at any rate cannot keep the loop busy (1.2.1: without the budget a flood blocked it 93 to 98 % of the time). Every record is checked with the reader's own rules before it is queued; one the reader would refuse is written as `malformed` with no facts, so watch never writes a line that makes the journal unreadable (1.2.1). A reader validates lines as it reads them and refuses a journal with more than 64 consecutive unreadable lines anywhere, tail included (1.2.1; a crash leaves one partial line and at most one partial repair). Record lines wait for the disk in a queue of at most 1 MiB; one append (`write` in append mode, then `fsync`) runs at a time. When the intake or the line queue is full, the payment is not journaled and is counted; before the next record a `drop` record states how many were lost and the first and last time, so the loss is recorded where it happened. Journal writes never delay an intercept answer.
- **Gaps are recorded, never implied.** A `registered` record is written when the observer's registration is confirmed, an `unregistered` record when its session ends (`stream-lost`, `refresh` when watch re-registers for changed canaries, `stopping`), a `run-start` and `run-end` around each run, and an `alive` record while registered whenever nothing was written for 5 minutes. Coverage is only the time between `registered` and what ends it; a run without `run-end` (killed, crashed, or still running) is covered only up to its last record. Coverage markers carry the time of the event they describe, never the time the queue wrote them (1.2.1).
- **File rules.** The path and its resolved target must carry no protected name (SAFE-02); a name Windows would change, a symlink or anything but a regular file is refused. The file is created owner-only: `0600` on POSIX; on Windows through the same owner-only creation as `--out` files (a protected DACL granting only this user; 1.2.1). An existing file that is not owner-only or belongs to another user is refused: on POSIX by mode and owner, on Windows when any allowing entry names an account other than this user, SYSTEM or Administrators (the message says how to fix it with `icacls`); on a volume that stores no permissions (FAT, exFAT) warning `acl-best-effort` is raised instead. The lock path must not be a symbolic link: an exclusive create that followed one (Windows) removes the file it made and exits 3 (1.2.1). An existing file must start with a journal record. One watch writes a journal at a time: `<journal>.lock` is taken with the same owner-record and stale-owner rules as `<registry>.watch.lock`. The run's `run-start` is appended and synced before watch registers. Any of these failing → exit 3 at W6, nothing registered. A file whose last line is incomplete or invalid (a crash cut a write short) is ended with a newline, and the new run's `run-start` carries `repairedTail: true`.
- **Bounded size.** A journal holds at most 64 MiB (about 150,000 payment records). watch refuses to start on a file with less than 64 KiB of room left (exit 3); when the limit is reached while running, a `full` record ends coverage and nothing more is written. The records that did not fit are recorded where they were lost, in room kept for this so the file still never exceeds 64 MiB (1.2.1; before, the `full` record took the time it was written, so coverage ran on over the payments it had just discarded): a `drop` record counts the calls lost (payment and deletion records that did not fit, the counts of `drop` records that did not fit, and calls dropped earlier and not yet reported) from the capture time of the first line that did not fit, marker or call, to the last, and the `full` record follows at that last time. Coverage therefore ends where the loss began: the window starts at the first lost line even when it is a marker, because a lost `unregistered` would otherwise leave the time after it looking covered. When only markers did not fit, there is no `drop` record and the `full` record takes the time of the first of them. There is no automatic rotation: stop watch, move the file aside, start watch again.
- **Failures.** A failed write or a disk that does not take markers (more than 1 MiB of them waiting) stops journaling for the run: nothing more is written, so coverage ends at the last written record. Each stop (`full`, `write-failed`, `stalled`) is reported once by the status event `payment-journal-stopped` (`PAYMENT JOURNAL STOPPED (<reason>)`), never dropped, and by warning `payment-journal-stopped`; calls not journaled raise warning `payment-journal-dropped`. watch itself keeps running: the canary guard and usage do not depend on the journal.
- The summary gains `paymentJournal: {path, payments, deletions, dropped, stopped}` (`stopped`: `full`, `write-failed`, `stalled` or `null`).

Stop: SIGINT/SIGTERM/SIGHUP or `--until` closes both streams (LND unregisters them), writes the usage file and releases the lock, then gives alerting one deadline of at most 13 s: from then on no alert command starts (an alert raised by the final flush, such as a window summary, starts only when no command is running; one that would wait behind a running command is discarded and reported as `alert-failed`, though its event line is still printed), the running command may finish within 12 s and is then cancelled (its process group or, on Windows, its process tree is killed), and the process-tree kills get the rest of the 13 s; then it kills what alert commands left running (POSIX process groups), and exits 0 with the summary `{node, startedAt, endedAt, calls, errors, credentials, canaryAlerts, canaryUses, alertFailures, reconnects, canaries, usageFile, droppedUsageRecords, evictedUsageRecords, droppedAttributions, droppedEvents}`, plus `paymentJournal` with `--payment-journal` (the journal is closed with its `run-end` before the watch lock is released). **Operational risk:** while registered, LND waits for the watcher's answer on every RPC, up to `rpcmiddleware.intercepttimeout` (default 2 s), and fails the RPC when it times out. A watcher that is suspended (not stopped) or whose host stalls therefore delays and then fails the node's RPCs until its connection drops. Run it as a supervised service and stop it with a signal, never by suspending it.

Output that cannot be delivered never keeps watch alive: after its final drain (at most 5 s) it drops and counts the event lines still queued and stops retrying, writes the summary off the event loop for at most 2 s, and exits. A write that the operating system has already accepted cannot be cancelled (on Windows every write to an inherited pipe is synchronous), so if the process is still alive 3 s after watch finished it is terminated (that deadline starts only once every alert process-tree kill has finished, each bounded to 10 s, so it never cuts one short): exit 1 on Windows, SIGKILL on POSIX, reporting that output was not delivered. With a reader that reads, watch exits on its own with its real status.

Alert command leftovers: on POSIX every alert command runs in its own process group; the group gets SIGKILL 1 s after the command exits, and every group still alive is killed when watch stops, so background jobs an alert command starts cannot accumulate (an attacker holding a canary sets how often alerts run). A child that calls `setsid()` leaves the group and is out of reach. On Windows a timed-out or cancelled command's process tree is killed with System32 `taskkill /T /F`; children of a command that has already exited cannot be found by tree, so alert commands on Windows must not leave background processes.

### 9. `recommend` (online, read-only)

`macwarden recommend (<label> | <root-key-id> | id:<16 hex> | --target-file <file>) [--accept-short-observation] [--json]` + online flags (`--registry`) — needs `info:read` (GetInfo, ListPermissions).

Reads the usage that `watch` recorded for the selected credential: a label or non-zero root key ID selects every credential ID observed on that root key ID; `id:…` or `--target-file` (credential ID computed from the file's identifier; the bytes are not kept) selects one credential. Root key ID 0 alone is refused (exit 2, R6): the default macaroons share it. A selector of digits that is not a canonical uint64 (`007`, `18446744073709551616`) is neither a root key ID nor a label: exit 2 at R1. Each observed method is mapped to the permissions LND requires for it (ListPermissions). Result `{node, selector, label, rootKeyId, credentials, observed:[{method, calls, lastUsed, permissions}], unmapped, recommended, recommendedUris, current, unneeded, observation, commands}`: `recommended` is the union of entity permissions, `recommendedUris` the exact methods (the tightest), `unneeded` the entity permissions the registry entry holds that no observed method needed, and `commands` the narrowing steps (`macwarden bake --label <label>-narrow --uri <methods> --out <file> …`, then `macwarden revoke <label> …` after the app switched). Methods missing from ListPermissions are listed in `unmapped` and suppress the commands. It changes nothing; usage covers only calls seen while a watcher ran, so a method used rarely may be missing — watch through a full business cycle before narrowing.

Narrowing commands are printed only from complete, consistent evidence. With warning `usage-incomplete` none is printed when any usage record was evicted or any call went unattributed (`droppedAttributions`): some of the credential's methods may be missing, and following the command would break the app. With warning `recommendation-broader` none is printed when an observed method is not covered by the registry entry's recorded permissions, or, with `--target-file`, by the file's own decoded permissions (poisoned usage data or a wrong registry; the command would widen the credential). The guard applies to every selector alike: a credential ID (`id:…` or `--target-file`) is resolved through the root key ID its usage was recorded with (and, for `--target-file`, the file's own) to the single active registry entry with that non-zero root key ID. With warning `recommendation-unverified` none is printed when there are observations but no permissions to check them against: the root key ID is unregistered or 0 (except through `--target-file`), more than one active entry has it, or one credential ID was recorded under several root key IDs. The `revoke` step is suggested only for a label or root key ID selector, which covers every credential observed on that root key ID; a credential ID selector prints the `bake` step alone, because revoking deletes the whole root key ID.

Observation window: `observation` is `{seconds, since, until, sessions, short, accepted}`, how long `watch` was registered with this node according to the usage file's coverage record (gaps between runs are not counted). Only coverage after the credential was created counts, as a provable lower bound: its creation is the registry entry's `createdAt` or, without an entry, its first recorded use. `seconds` is the larger of the recorded spans' time after creation and the covered total minus all time from the first registration to the creation, and never more than the time from creation to `until`. Coverage before creation can therefore never satisfy the 7-day rule: with a usage file without `coverageSpans` (1.0.1), coverage that began before creation counts only as far as it cannot have lain before it. The text output prints `observed for <duration> (<n> watch sessions since <time>)`. Below **7 days** (`short: true`; one weekly cycle, so weekly jobs and rarely used methods such as payments have had a chance to appear) the warning `short-observation` says rarely used methods may be missing and no narrowing command is printed unless `--accept-short-observation` is given (`accepted: true`; the warning stays). A usage file without a coverage record (written before 1.0.1) gives `seconds: null` and counts as short. A window that cannot be computed (any step of the calculation is not a finite number, or `until` is before `since`; the usage reader already refuses such files, so this is defence in depth) gives `seconds: null`, `short: true`, `accepted: false` and warning `observation-invalid` instead of `short-observation`, and no narrowing command is printed even with `--accept-short-observation`: that flag accepts a short window, not evidence that cannot be placed on the clock. A computed window that is negative (the credential was created after `until`) is 0 seconds, short.

### 10. `respond` (online, mutating through `rotate`)

`macwarden respond --out-dir <directory> [--allow-admin] [--yes] [--break-lock] [--dry-run] [--json]` + online flags; `macwarden respond --finish [--yes] [--break-lock] [--dry-run] [--json]` + online flags. Needs `info:read` and `macaroon:read` to plan; staging and finishing need what `rotate` needs.

Incident response after credentials may have leaked (for example the BTCPay Server 2.4.2 advisory of 2026-08-07, where unauthenticated attackers downloaded LND macaroon files). It rotates every registered credential in two batches through the `rotate` steps, so every SAFE rule and step of `rotate` applies unchanged, and it reports proof afterwards. All state lives in the registry (pending replacements), so an interrupted run is resumed by running the same command again.

Steps (P1–P9):

1. **P1** Parse arguments → exit 2. Staging without `--dry-run` needs `--out-dir`; `--finish` takes neither `--out-dir` nor `--allow-admin`. Errors name the flag.
2. **P2** ENV → exit 2. OWN (`info:read` for GetInfo and ListPermissions, `macaroon:read` for ListMacaroonIDs and CheckMacaroonPermissions, or their `uri:` permissions) → exit 4.
3. **P3** Open the registry read-only → exit 3.
4. **P4** GetInfo; ListPermissions (`snapshot-drift`); ListMacaroonIDs → exit 4/5.
5. **P5** Classify, sorted by root key ID: each active registry entry for this node that is not itself a staged replacement gets action `stage` (no replacement staged), `finish` (replacement staged, also when the old root key ID is already absent from LND: an earlier finish deleted it and stopped before saving the registry, and `rotate --finish` repairs that through F6 after proving the replacement accepted; a staging rerun reports it `staged-earlier` and says so), `repair` (absent from LND with no replacement staged: `macwarden revoke <label>` records it; or a replacement an earlier stage allocated but never completed, `verified: false` or without `outPath` or fingerprint: status `failed` with `error` exit 7 at P5, listed under `unproven`, never reported `staged-earlier` and never retried, because LND may hold or still create its ID; the message says whether LND lists it and gives the recovery `macwarden revoke <replacement root key ID>` and a fresh stage) or `manual` (root key ID 0, macwarden's own root key ID, no label, or an `lnd-custom` caveat: a canary is never rotated into an ordinary credential; the note says to revoke it, bake a new canary and restart `watch`). Before classifying, every active entry naming another active entry in `replaces` must be a believable staged replacement (same node and label, different root key ID, created no earlier, with the S3 exception for a link a 1.1.0 stage wrote under a clock behind O); otherwise exit 3 "registry tampering", because a forged link would hide a credential from the batch. Likewise, an active entry whose `outPath` file matches its fingerprint and carries an `lnd-custom` caveat the entry does not record → exit 3 "registry tampering" before any mutation: the decoded file, not the editable caveat list, decides whether a credential is a canary. The same check covers every link on the node: a replacement whose target is itself a staged replacement (a chain or a cycle), or a second entry claiming the same original, is tampering too. Advice names a credential by its label only when that label resolves to exactly one active entry on the node (as `revoke` requires), otherwise by its root key ID. Each staged replacement's fingerprint is shown (`replacementFingerprint`) for the operator to compare with the file the app uses. Root key IDs in LND not covered by an active entry, other than 0 and the own ID, are listed: under `revokedButPresent` when the registry records them as revoked (an earlier revoke did not complete, or a credential that can bake re-created them; treat them as live and revoke each), otherwise as unknown and never touched (Lightning Terminal, Loop, Pool, Faraday or another operator may own them). Active credentials other than the own one that can bake (by their recorded permissions, assessed as for `verify`'s `canBake`; a recorded grade of `UNASSESSED` also counts, and the `ADMIN` grade alone does not) are listed under `bakingRisk` with guidance: a leaked one can create credentials on any root key ID, including the staged replacements, so `--finish` handles them first and only regenerating all root keys removes everything it could have baked. Warnings `revoked-but-present` and `baking-credential-in-scope` accompany these lists. Root key ID 0 always gets the manual guidance: LND refuses to delete it, so invalidating it means the operator runs `lncli changepassword --new_mac_root_key` on the node (macwarden never calls it, SAFE-02). That regenerates **every** root key, not only ID 0 (LND v0.21.4 `macaroons/store.go`, `GenerateNewRootKey`): every macaroon on the node stops working, including per-app macaroons, macwarden's own and any replacement `respond` has staged. When credentials on root key ID 0 may have leaked, the guidance therefore says to regenerate first, in a maintenance window, and bake fresh per-app macaroons afterwards, not to stage replacements before it.macaroon`, `readonly.macaroon`, `invoice.macaroon` and macwarden's own credential if it is on 0, then stops working; `--stateless_init` keeps new default macaroons off disk. `--dry-run`, or nothing to do, prints this plan and exits 0 with no change.
6. **P6** Staging: create `--out-dir` with mode `0700` when it does not exist; a protected path, or a path that is not a directory → exit 3. On Windows, `--out-dir` and every `<label>.macaroon` it would receive are checked against B4's name rule before anything is created; a refused name (a label such as `CON` names a device) → exit 3 with nothing staged.
7. **P7** One typed confirmation for the batch (SAFE-05), unless `--yes`: the prompt lists every credential and the operator types `stage N` or `finish N`. Wrong text, EOF, or no TTY without `--yes` → exit 6, nothing changed.
8. **P8** For each selected credential in order: staging runs `rotate <label> --out <out-dir>/<label>.macaroon` (with `--allow-admin` when given); finishing runs `rotate <label> --finish --yes` (the batch confirmation replaces the per-credential one). A credential that fails is recorded with its exit code, step and message, and the batch continues. An interrupt stops before the next credential; the rest are `not-run`.
9. **P9** `--finish` proof, after the batch: ListMacaroonIDs again, then for each finished credential CheckMacaroonPermissions with the old file (when it still exists and matches its fingerprint) and with the replacement file. A credential is **proven** when its old root key ID is absent, the replacement is accepted, and the old credential is rejected (`credential-rejected`) or no old file is left to test (`root-key-id-absent`). Every proof has `scope: "this-credential"`: it shows that this credential's old root key ID is gone and its replacement accepted, not that no other credential exists. Every finished-but-unproven and every failed credential is listed under `unproven` with the reason.

Exit: 0 when no incomplete replacement is outstanding, every selected credential succeeded and, after `--finish`, every finished credential is proven; otherwise the batch code by severity 7, 8, 4, 5, 3, 6, 2 (a possible LND change outranks everything). A finished credential that is not proven (old root key ID still listed, LND unreadable after the deletions, replacement not accepted) is an LND change that could not be confirmed → 7; so is an incomplete replacement found at P5 (except with `--dry-run`, which exits 0). An interrupt after any credential was staged or finished exits 7, before any exits 6.

`result`: `{"mode":"stage"|"finish","dryRun","node":{"pubkey","alias","network"},"rootKey0":{"present","ownOnRootKey0","guidance":[…]},"own":{"rootKeyId"},"unknown":{"rootKeyIds":[…],"guidance"},"revokedButPresent":{"rootKeyIds":[…],"guidance"},"bakingRisk":{"rootKeyIds":[…],"guidance":[…]},"outDir"|null,"items":[{"label","rootKeyId","grade","action","status","replacementRootKeyId","replacementFingerprint","outPath","note","error":{"code","step","message"}|null,"proof":{"evidence","oldRootKeyIdAbsent","oldCredential","newCredential","proven","strength","scope"}|null}],"unproven":[{"label","rootKeyId","reason"}]}`. Item status: `planned`, `staged`, `finished`, `failed`, `staged-earlier`, `not-staged`, `finished-earlier` (with `--finish`: the credential already replaced a now-revoked one, so there is nothing to finish), `not-run` or `manual`. No credential bytes appear in the result or output (SAFE-01); replacement bytes are only in the `--out-dir` files.

Acceptance: against the pinned regtest, two labelled credentials are staged (each replacement accepted by LND), then `--finish` deletes both old root key IDs, proves each old credential rejected and each replacement accepted, and leaves unknown IDs and root key ID 0 in LND.

### 11. `verify` (online, read-only)

`macwarden verify <file | -> [--json]` + online flags (`--registry`); `macwarden verify <hex | base64 | lndconnect://...> --unsafe-arg [--json]` + online flags. Needs `info:read` (GetInfo, ListPermissions) and `macaroon:read` (CheckMacaroonPermissions); ListMacaroonIDs is called only when the own credential holds `macaroon:read` or its `uri:`.

Asks the node whether one credential file is still accepted. After a leak such as the BTCPay Server 2.4.2 advisory (2026-08-07), patching closes the hole but does not invalidate stolen copies, and LND regenerates `admin.macaroon` from the same root key, so an operator checks each old file. The credential is read and decoded exactly as `inspect` reads it (Global conventions; a literal needs `--unsafe-arg`); a Nostr Wallet Connect URI → exit 3, step `input-form` ("not an LND credential"). The credential is never printed and never written (SAFE-01); it is sent only to the configured node, inside CheckMacaroonPermissions. Owner addition 2026-10-08 (1.1.0).

Steps (C1–C7):

1. **C1** Parse: exactly one input (`--` ends flags), known flags, connection flags as for every online command → exit 2, `error.step` `null`.
2. **C2** ENV → exit 2.
3. **C3** Read and decode the credential → exit 2 or 3 with the input or decoding stage, as `inspect`. A credential with no permissions → exit 3, step `C3` (an empty permission list is never sent; Global conventions).
4. **C4** OWN (`info:read` for GetInfo and ListPermissions, `macaroon:read` for CheckMacaroonPermissions) → exit 4, zero LND calls.
5. **C5** Open the registry read-only (no lock) → exit 3.
6. **C6** GetInfo; ListPermissions (`snapshot-drift`); ListMacaroonIDs when allowed → exit 4/5 on failure.
7. **C7** CheckMacaroonPermissions with the credential and its own decoded permissions (as in **Verify accepted**) → exit 4/5 when the call itself fails (transport, TLS, authentication of macwarden's own credential, unclassified LND error).

`status` is `accepted` when LND returns `valid: true`, otherwise `rejected` with `rejection`: `root-key-missing` or `signature-mismatch` (**Verify rejected**: the root key ID is gone, or the signature does not match the root key: after a root key regeneration, or for an altered copy), `expired` (LND itself reported that a `time-before` caveat of this credential has passed, by the node's clock), or `other`. Expiry is node-side evidence only: LND v0.21.4 answers CheckMacaroonPermissions with gRPC `InvalidArgument` (HTTP 400 through REST) carrying the error of `macaroons/service.go` `CheckMacAuth`, whose bakery (macaroon-bakery v2.0.1) checks the first-party caveats in order and reports the first that fails as `caveat "<caveat>" not satisfied: <reason>`; an expired `time-before` gives exactly `caveat "time-before <value>" not satisfied: macaroon has expired`. `rejection` is `expired` only when the whole message has that form and `<value>` equals the value of one of the credential's decoded `time-before` caveats; anything else that is not `root-key-missing` or `signature-mismatch` is `other`. The operator machine's clock never decides the verdict (audit 1.1.0, MW110-02): a skewed clock could otherwise turn a caller-dependent rejection into false clearance. When the local clock says a `time-before` caveat has passed (`expired: true` in `caveats`) but LND did not report expiry, the verdict stays `other` and the guidance says the local reading is no proof; LND may also have refused an earlier caveat, such as an IP lock, first. LND quotes the text of the caveat it refused in its message (Go `%q`), and whoever holds a macaroon can append a caveat with any text, so every quoted span is blanked before a message is classified (1.2.1): `caveat "root key with id 5 doesn't exist" not satisfied: caveat not recognized` is `other`, never `root-key-missing`. A `root-key-missing` answer while ListMacaroonIDs still lists the root key ID contradicts the listing and counts as `other`, not conclusive, with guidance saying so (1.2.1). A rejection is **conclusive** for `root-key-missing` and `expired`, and whenever ListMacaroonIDs no longer lists the root key ID. A `signature-mismatch` is conclusive in that last case, and when the file's fingerprint equals the fingerprint the registry recorded for that root key ID on this node (`registry.match: "fingerprint"`): those bytes are known genuine (the fingerprint covers the canonical bytes including the signature, and macwarden recorded them after LND accepted them), so the mismatch can only come from a changed root key, and the guidance says the root key was regenerated (review RT-01). Otherwise it is not conclusive: LND gives the same answer after `changepassword --new_mac_root_key` and for any altered copy of a live credential, and a regeneration keeps every root key ID listed, so while the ID is listed (or could not be listed) the original may still be accepted. That macwarden's own credential authenticated is no such evidence: it shows only that its own bytes are valid now. The guidance says so, says how to get a conclusive answer (verify the exact file the registry recorded, or compare the file's fingerprint with one recorded before the incident, such as an `inventory --report` export or a backup), says to treat the original as live and gives the revoke command (for root key ID 0: regenerate every root key unless that was already done). An `other` rejection is not conclusive either: CheckMacaroonPermissions evaluates caveats in the context of macwarden's own call, so an IP-locked credential, or one with a custom caveat (a canary is accepted only while `watch` runs), can be refused here and accepted for another caller; the guidance says to treat it as live until its root key ID is revoked.

`registry` is the registry entry for this node with the same fingerprint (`match: "fingerprint"`), else one with the same root key ID (`match: "root-key-id"`: another credential on that root key ID, such as an attenuated copy), preferring an active entry; `null` when there is none. `ownCredential` is true when the root key ID is that of macwarden's own credential; `canBake` when the permissions include `macaroon:generate` or `uri:/lnrpc.Lightning/BakeMacaroon` (the only permissions LND accepts for BakeMacaroon), or when the authority cannot be fully assessed: grade `UNASSESSED`, an unassessed permission (`unassessed-permission`, `unassessed-uri`) or a decode past its bounds (`identifier-exceeds-bounds`, `caveats-exceed-bounds`). The `ADMIN` grade alone does not imply it: `macaroon:write` is `ADMIN` (it deletes root key IDs) but cannot bake (audit 1.1.0, MW110-06).

`guidance` (printed as `next` lines):

- Accepted on root key ID 0: LND cannot delete root key ID 0; only regenerating every root key invalidates it (`lncli changepassword --new_mac_root_key`, which macwarden never runs, SAFE-02). That also invalidates every other macaroon on the node, including macwarden's own and any replacement staged with `respond`, so the regeneration comes first, in a maintenance window, followed by fresh per-app macaroons (the same order as `respond`'s root key ID 0 guidance). No revoke command is printed for ID 0 (SAFE-03).
- Accepted on another root key ID: `macwarden revoke <id>` when a registry entry matches (by root key ID, since a label is ambiguous while a rotation is staged; an active entry's label is named with the `rotate` alternative), otherwise `macwarden revoke <id> --unregistered`; revoking the ID invalidates every macaroon baked on it. For macwarden's own root key ID no revoke command is printed (revoke refuses it). When `canBake`: its holder may have baked credentials on other root key IDs that revoking this one does not remove, so `respond` replaces and revokes every registered credential and, if it may have been used, every root key is regenerated.
- Rejected, conclusive: LND rejects it now, and why; for `expired` with the root key ID still listed, other macaroons on that ID keep working until it is revoked.
- Rejected, not conclusive: treat it as live; the revoke command as above, never one macwarden would refuse (review RL-06): for macwarden's own root key ID, how to invalidate it instead (bake a new session credential, switch to it, then revoke the old root key ID from the new session); for root key ID 0, that only regenerating every root key invalidates it. When this machine's clock says a `time-before` caveat has passed, a note that LND did not report the expiry and that the local reading is no proof.

Text output is the `inspect` text followed by `node`, `status`, `root key` (listed, not listed, or not checked), `registry` and one `next` line per guidance line.

`result`: the `inspect` result fields plus `{"node":{"pubkey","alias","network"},"status":"accepted"|"rejected","rejection":"root-key-missing"|"signature-mismatch"|"expired"|"other"|null,"conclusive","rootKeyListed":true|false|null,"ownCredential","canBake","registry":{"label","status","match"}|null,"guidance":[…]}`. Warnings: `unsafe-arg`, `own-root-key-0`, `snapshot-drift`.

Exit: 1 when the credential is accepted or the rejection is not conclusive (`ok: true`, `error: null`; a live credential is a finding, as with `scan --fail-on`); 0 when LND conclusively rejects it; 2, 3, 4, 5 or 6 as in the steps above (6 on SIGINT, SIGTERM or SIGHUP; nothing is changed).

Acceptance: against the pinned regtest, a credential baked on its own root key ID verifies `accepted` (exit 1) with its registry label; after `macwarden revoke` it verifies `rejected` with `root-key-missing` (exit 0); the fixture's `admin.macaroon` verifies `accepted` on root key ID 0 with the regeneration guidance and no revoke command. `--json` output validates against `schemas/output/verify.schema.json`, and no credential appears in any output.

### 12. `reconcile` (online, read-only)

`macwarden reconcile --payment-journal <path> [--since <time|n(m|h|d)>] [--until <time|n(m|h|d)>] [--json]` + online flags (`--registry`, for labels). Needs `info:read` (GetInfo, ListPermissions) and `offchain:read` (ListPayments, TrackPaymentV2), or exactly the four method URIs: a credential baked with `info:read uri:/lnrpc.Lightning/ListPayments uri:/routerrpc.Router/TrackPaymentV2` is enough. `offchain:read` also lets its holder read channels, payments and their preimages, so give this credential to no app. Owner addition 2026-10-09 (1.2.0).

Joins two kinds of evidence and keeps them apart: **observation** (the payment journal `watch --payment-journal` wrote: which credential asked LND to pay which payment hash, and when watch was or was not registered) and **settlement** (what LND reports for each payment now). A journaled request is never counted as a payment LND made; a payment missing from the journal or from LND is never counted as proof that none was made. Nothing is changed in LND, the registry or the journal.

Steps (Q1–Q7):

1. **Q1** Flags → exit 2, `error.step` `Q1`: `--payment-journal` is required; `--since` and `--until` take a UTC instant (`YYYY-MM-DDThh:mm:ss[.fraction]Z`, a real instant) or `<n>(m|h|d)` before now (`n` 1–999999); `--since` after `--until` is refused, checked after `--until` defaults to now, so a `--since` in the future is refused too (1.2.1); connection flags as for every online command.
2. **Q2** ENV → exit 2.
3. **Q3** OWN: TLS certificate and own macaroon readable and decodable, holding `info:read` (or the GetInfo and ListPermissions URIs) and `offchain:read` (or the ListPayments and TrackPaymentV2 URIs) → exit 4, zero LND calls.
4. **Q4** Read the journal (Payment journal format: bounded, validated, never partly used) and the registry (read-only, no lock) → exit 3.
5. **Q5** GetInfo; ListPermissions (`snapshot-drift`) → exit 4/5.
6. **Q6** ListPayments (`GET /v1/payments`, `include_incomplete=true`, `creation_date_start`/`creation_date_end` the window widened by 60 s on each side), 100 payments per page, at most 100,000 → exit 4/5 on failure; LND amounts summed past 2^63−1 msat, for one payment's attempts or one credential's payments, are not LND's records (no real sum reaches it: 21 million bitcoin is 2.1e18 msat) → exit 5, `invalid LND response` (1.2.1).
7. **Q7** For each journaled payment hash in the window that the listing does not hold (its payment may have been created earlier, for example a retry of an old payment), one TrackPaymentV2 lookup (`GET /v2/router/track/{hash}`, the first update only), at most 1,000 → a transport, TLS or authentication failure exits 4; any other failure of one lookup leaves that payment `unknown`. SIGINT, SIGTERM or SIGHUP at any step → exit 6, nothing changed.

The **window** is `--since` to `--until`; by default from the journal's first record for this node to now. Only records of runs whose `run-start` names the connected node are used (others are counted in `journal.otherNodeRecords`, warning `journal-other-node`).

- **Payments** (`payments`): one item per payment hash journaled in the window, sorted by first observation. `observation` holds the journal evidence: first and last time, number of requests, `requestedMsat` (the latest SendPaymentV2 request's amount), `routeAttemptsMsat` (the sum of SendToRouteV2 amounts; a retried shard is counted each time it was requested), `feeLimitMsat` (the latest SendPaymentV2 limit) and the last 100 observations with credential ID, root key ID, label (from the registry, by non-zero root key ID), method and request ID. `settlement` holds LND's evidence: `status` `succeeded`, `failed`, `in-flight` (LND `IN_FLIGHT` or `INITIATED`), `not-found` (LND has no payment with this hash: it refused the request before creating one, or the record was deleted) or `unknown` (LND reports `UNKNOWN`, the lookup failed, or the lookup limit was reached); `source` (`list-payments`, `track-payment`, or `null` without a record); `createdAt`; `settledMsat` and `feesMsat`, the delivered amount and route fees summed over the HTLC attempts LND reports as succeeded (LND's payment summary only when it lists none for a succeeded payment); `inFlightMsat` over in-flight attempts; `attempts`, the number of HTLC attempts; `failureReason` (LND's reason without `FAILURE_REASON_`, lower case with dashes: `timeout`, `no-route`, `error`, `incorrect-payment-details`, `insufficient-balance`, `canceled`); and `predatesObservation`, true when LND created the payment more than 60 s before the first journaled request for it (its outcome may belong to an earlier attempt by any credential). `attribution` is `single` when one credential ID requested the hash, `ambiguous` when several did, and `historical` when one did but LND's record predates its first journaled request (`predatesObservation`): the outcome may belong to an attempt the journal never saw, by any credential (1.2.1). A hash journaled in the window is attributed from every request for it the journal holds, before the window included, so an earlier request by another credential makes it `ambiguous` (1.2.1). Per-credential totals count `single` payments only; `ambiguous` and `historical` are counted (`ambiguous`, `historical`) without amounts, and either keeps the run from exit 0. Each LND record is reduced to its attempt count and amounts by status while it is read (any number of attempts within the 8 MiB response bound, since LND keeps every failed attempt of a retried payment; amounts and times outside LND's own types, or attempt sums above 2^63−1 msat → exit 5), and the listing and lookups stop after a 10 minute budget, reported like the count limits; the `lookups-limited` warning names which one ended the listing: the 100,000 count, the budget, or both (1.2.1). `deletedBy` lists credentials that journaled a DeletePayment for this hash or any DeleteAllPayments in the window.
- **Per credential** (`credentials`): for each credential ID, its root key IDs, label, number of payments it alone requested and how LND reports them (`succeeded`, `failed`, `inFlight`, `notFound`, `unknown`), and the sums over those payments of `requestedMsat` (the request, or the route attempts), `settledMsat`, `feesMsat` and `inFlightMsat`. A sum of journaled requests above 2^63−1 msat (a credential can ask for any amount; LND refuses it) is reported as 2^63−1 with the warning `requested-amounts-capped`, as is such a `routeAttemptsMsat`; a sum of LND's amounts above it exits 5 (Q6) (1.2.1). Hashes requested by several credentials are counted in each one's `ambiguous`, never in its sums. `unmatched` counts its requests without a hash, `deletions` its journaled payment-record deletions.
- **Requests without a hash** (`unmatched`): journaled payment requests in the window whose hash could not be read (AMP, malformed, oversized, invalid invoice); they cannot be matched to LND's records.
- **Unattributed payments** (`unattributed`): payments LND lists as created in the window whose hash the journal never recorded for this node, with LND's evidence and `coverage`: `gap` (created while the journal shows watch not registered), `covered` (created at least 60 s inside a covered period: a payment watch did not see while registered, such as one made through a path the middleware does not intercept, or recorded in another journal), or `boundary` (within 60 s of a coverage edge, where the clocks of the two hosts decide). Payments whose hash the journal recorded outside the window are counted in `lookups.attributedOutsideWindow`.
- **Coverage** (`coverage`): window and covered seconds, `complete`, and the gaps (at most 1,000 listed; `gapCount` and `gapSeconds` are exact), each `{from, to, reason, dropped}` with reason `before-journal`, `not-running` (between runs), `not-registered` (a run not registered: before its first registration, after a lost stream or during re-registration), `unconfirmed` (after the last record of a run that has no `run-end`: watch still running, killed or crashed), `journal-full` or `dropped` (payment calls watch could not journal under overload, from the first to the last; `dropped` counts them; listed even when it lasted no measurable time).
- **Deletions** (`deletions`): every journaled DeletePayment and DeleteAllPayments in the window with its credential, scope (`payment`, `failed-htlcs`, `all-payments`, `failed-payments`, or `none`, which LND refuses) and hash.
- `journal`: path, size, runs, records for this node, first and last record time, `otherNodeRecords`, `tornTail` (the file ends with an incomplete line: watch is writing it, or stopped while writing it; it is ignored) and `repairedLines`. `lookups`: `listed`, `listTruncated`, `tracked`, `trackFailed`, `trackLimited`, `attributedOutsideWindow`.

Warnings: `journal-gaps`, `unattributed-payments`, `payments-uncertain` (a journaled payment without a final outcome: in flight, not found or unknown), `journal-unmatched`, `attribution-ambiguous`, `payment-deletions`, `lookups-limited`, `requested-amounts-capped`, `journal-torn-tail`, `journal-other-node`, `own-root-key-0`, `snapshot-drift`.

Text output: `node`, `journal`, `window` (covered of window, number of gaps), up to 20 `gap` lines, one `credential` line per credential, one `payment` line per hash (observation, then `|  LND:` and the settlement), then `unmatched`, `unattributed` and `deletion` lines, and an `evidence` line stating that the two kinds of evidence are separate.

Exit: 0 when the window is fully covered, every journaled payment in it has a final outcome from LND (`succeeded` or `failed`), every request carried a hash, no hash is ambiguous, no deletion was journaled, no lookup was limited and LND lists no unattributed payment; otherwise 1 (`ok: true`, `error: null`: the reconciliation is incomplete, a finding as with `scan --fail-on`). 2, 3, 4, 5 or 6 as in the steps above.

Acceptance: against the pinned regtest node and a second regtest LND it pays through a direct channel, with `watch --payment-journal` running, payments made with baked credentials reconcile to their credentials: an invoice paid with a `pay-only` credential is `succeeded` with its amount, a keysend to an unreachable node made with a second credential is `failed` with LND's failure reason, a hold invoice still held is `in-flight`; a payment made with `admin.macaroon` after watch stopped is `unattributed` with `coverage: "gap"`, and the gap is listed. `--json` output validates against `schemas/output/reconcile.schema.json`, every journal line against `schemas/output/payment-journal-record.schema.json`, and no credential, invoice text or preimage appears in the journal or any output.

## Registry format

One JSON file, mode `0600` in a directory with mode `0700` (SAFE-06), written atomically (temp file + rename; the rename is retried on Windows `EPERM`/`EBUSY`) under the lock described above. On Windows the temp file is created with an owner-only protected DACL through the same helper as `--out` files, and the rename keeps it, so a saved registry never inherits a permissive folder's entries (1.2.1); the usage file and `<registry>.canary.json` are written the same way. It is read as a regular file of at most 64 MiB (1.2.1). It contains no credential material (SAFE-06).

```json
{
  "schema": 1,
  "entries": [
    {
      "nodePubkey": "02ab…c4",
      "label": "btcpay",
      "rootKeyId": "4831990234117",
      "permissions": ["info:read", "invoices:read", "invoices:write"],
      "caveats": [{ "type": "time-before", "value": "2027-01-01T00:00:00Z", "requested": "90d" }],
      "grade": "RECEIVE",
      "fingerprint": "fp:3f9a1c0e5b7d2a44",
      "outPath": "/home/op/btcpay.macaroon",
      "createdAt": "2026-10-02T09:00:00Z",
      "verified": true,
      "status": "active",
      "revokedAt": null,
      "revokeEvidence": null,
      "replaces": null,
      "replacedBy": null
    }
  ]
}
```

Rules: entries are keyed by (`nodePubkey`, `rootKeyId`); `status` is `active` or `revoked`; at most one active entry per label per node, except a pending replacement (`replaces` set) during a staged rotation; exactly one of the two may name the other (two entries naming each other form a cycle and make the registry invalid, exit 3). `label` is `null` only for an ID revoked with `--unregistered`. Root key IDs are never reused, including revoked ones. LND is the authority on which IDs exist; the registry only adds who/why, and macwarden never changes LND to match it. An unknown `schema` value → exit 3. Every field is validated when the registry is read, before any LND call (1.1.1, RL-03): `caveats[].requested` appears only on a `time-before` caveat and is a duration as `bake --expires` accepts it (`^[1-9][0-9]{0,4}[mhd]$`), and `createdAt` and `revokedAt` are real calendar instants (`2026-02-30T00:00:00Z` or `T24:00:00Z` is invalid rather than rolled over); anything else → exit 3. Before 1.1.1 a malformed `requested` was parsed only after BakeMacaroon, so `rotate` exited 7 at S11 with a root key it had to leave behind.

## Payment journal format

Version 1 (owner addition 2026-10-09, 1.2.0). Written only by `watch --payment-journal` (Commands > 8), read by `reconcile` (Commands > 12). Each record is one line of JSON (UTF-8, at most 2,048 bytes; watch writes at most about 500) ending in `\n`, appended in order. Every record has exactly the keys listed for its type, plus `v` (`1`), `type`, `time` (`YYYY-MM-DDThh:mm:ss.sssZ`, a real instant; within a run, times never decrease: a clock that steps back does not move a record before its predecessor) and `run` (a random UUID per watch run). A reader refuses a file holding a record with another `v`, an unknown type or key, or a value outside its form; fields are never added to version 1. The JSON Schema is `schemas/output/payment-journal-record.schema.json`.

| `type` | Further keys | Meaning |
|---|---|---|
| `run-start` | `node` (pubkey), `version` (macwarden's), `repairedTail` | A watch run begins; it is not registered yet. `repairedTail: true` when the file ended with an incomplete or invalid line (a crash), which this run ended with a newline. |
| `registered` | `session` (1, 2, … per run) | The observer's registration was confirmed: coverage begins. |
| `unregistered` | `session`, `reason` (`stream-lost`, `refresh`, `stopping`) | That session ended: coverage ends. |
| `alive` | — | Still registered (written when nothing else was written for 5 minutes). |
| `payment` | `requestId`, `method`, `credential`, `rootKeyId`, `paymentHash`, `amountMsat`, `amountSource`, `feeLimitMsat`, `amp`, `extraction` | One payment request (Commands > 8, Payment journal). `requestId` is LND's middleware request ID (decimal), `credential` `id:<16 hex>`, `id:none` or `id:undecodable`, `rootKeyId` a canonical root key ID or `none`. `paymentHash` is 64 lower-case hex, or `null` unless `extraction` is `complete`; other extraction values: `no-hash`, `amp`, `payload-too-large`, `malformed`, `invoice-invalid`, `invoice-too-long`. `amountMsat` and `feeLimitMsat` are decimal strings up to 2^63−1 or `null` (a request or invoice amount above that is recorded as `null`; 1.2.1); `amountSource` (`request`, `invoice`, `route`) is `null` exactly when `amountMsat` is. |
| `deletion` | `requestId`, `method`, `credential`, `rootKeyId`, `paymentHash`, `scope`, `extraction` | One DeletePayment or DeleteAllPayments request; `scope` `payment`, `failed-htlcs`, `all-payments`, `failed-payments` or `none`; `extraction` `complete`, `payload-too-large` or `malformed`. |
| `drop` | `count`, `first`, `last`, `reason` (`overload`) | `count` journaled calls between `first` and `last` (capture times, `first` ≤ `last` ≤ `time`) were not journaled. Directly before a `full` record it covers what did not fit into the file, from the first line lost (marker or call) to the last (1.2.1). |
| `full` | — | The file reached 64 MiB: coverage ends and nothing more is written. Its time is that of the last line lost (the `drop` record's `last`), or of the first lost marker when no call was lost, never the time it was written (1.2.1); `reconcile` lists that `drop` as a `dropped` gap with its count, and the gap from where coverage ended keeps the reason `journal-full`. |
| `run-end` | `payments`, `deletions`, `dropped` | The run ended cleanly (after its `unregistered`), with its counts. |

Reading rules (`reconcile`): the path and its resolved target carry no protected name (SAFE-02) and must be a regular file of at most 64 MiB, checked before it is opened; the opened file must be that file; only the bytes present when it was opened are read (watch may be appending), in 1 MiB blocks, one line at a time. The first valid record must be a `run-start`; every other record must belong to the current run (the latest `run-start`), come before its `full` or `run-end`, and not go back in time; `registered` and `unregistered` must alternate with matching sessions. Invalid lines are accepted only where a crash leaves them: directly before a `run-start` with `repairedTail: true` (counted in `repairedLines`), or at the end of the file, together with an unterminated last line (ignored, `tornTail`). Anything else makes the whole file invalid (exit 3 at Q4), never partly used.

Coverage rules: watch was registered with a node only between a `registered` record of a run for that node and the `unregistered`, `full` or `run-end` that follows it; a run that has none of these is covered only up to its last record. A `drop` record removes `[first, last]` from coverage. All other time is a gap; `reconcile` reports each with its reason. Listed gaps may overlap: a drop inside time that is uncovered for another reason is listed with its count beside that gap, and a drop that reaches the end of a covered span leaves the gap after the span with the reason that ended the span. `gapSeconds` is the window less the covered time, never a sum of the listed gaps (1.2.1).

## Acceptance criteria

The behaviour each command must show, beyond the step-by-step definitions above. Each item is covered by unit tests, by tests against the pinned regtest LND node (`npm run test:oracle`), or both.

### Acceptance: general

- `macwarden --version` prints the `package.json` version; `--help` exits 0 on stdout; an unknown command or flag exits 2 with a usage message; `--json` with no command prints the envelope with `command: null` and code 2; an unknown "command" that looks like a credential is echoed nowhere.
- An exception thrown inside `main` (or uncaught anywhere) exits 8 with `error.step` `internal` and no argv or stack in the output.
- A leak test plants a sentinel macaroon and checks every output for it (SAFE-01).

### Acceptance: inspect

- Reads a file (binary, hex text, base64 text, UTF-8 with BOM, UTF-16LE with BOM, CRLF) and stdin; all give identical output for one macaroon. Literal hex, base64 and `lndconnect://` arguments give the same output with `--unsafe-arg` and are refused with exit 2 without it; the refusal never echoes the argument.
- The `readCredential` edge cases above each give their stated result: empty file, empty stdin, `-` on a TTY, a directory, an unreadable file, odd-length hex, `0x` prefix, unpadded base64, padded base64url, line-wrapped base64 in a file, upper-case scheme, percent-encoded and duplicate `macaroon` parameters, an argument outside every alphabet.
- For each test vector, root key ID, permissions and caveats match `lncli printmacaroon` under the caveat matching rule above; the fingerprint equals the vector manifest's independently computed one.
- Each negative vector fails at the stage its manifest names (v1 binary and base64, unknown packet type, over-long varint, header without identifier, missing final end-of-section, caveat with vid but no id, `storageId` errors, protobuf wire types, op with zero actions).
- LND's default `admin`, `readonly` and `invoice` macaroons grade `ADMIN`, `READ` and `RECEIVE`; the `pay-only` preset's method names exist in the permission snapshot.
- Every row of the grade table has a unit test, including `UNASSESSED` with its `unassessed` list, malformed strings, `grade([])`, duplicates and sorted outputs; the snapshot equals live `lncli listpermissions` on the pinned node.
- `expired` is correct at the boundary (now = instant) and independent of the local timezone; `inspect` prints the snapshot's LND version.
- Malformed input exits 3 with an error that contains no input bytes.
- `--json` output validates against `schemas/output/inspect.schema.json`.
- L402 input: the Authorization value (`L402` and `LSAT`, with and without the header name), the pair, stdin and the `--unsafe-arg` literal give one fingerprint; several macaroons and every challenge variant are read; a literal without `--unsafe-arg` exits 2 and is echoed nowhere; services, capabilities, `valid-until` expiry at the boundary (now = instant is expired) with an injected clock, unknown and third-party caveats, withheld caveats, the preimage check (`matches`, `mismatch`, `unverifiable`, `absent`), paid and pending token files, and each malformed form exiting 3 at its stage; the preimage and macaroon appear in no output.

### Acceptance: scan

- A fixture tree with at least three `*.macaroon` files and each text kind (hex, base64, `lndconnect://`, `nostr+walletconnect://…secret=`) in each of `.env`, YAML and JSON: every planted item is found with path, line and column; each macaroon is graded. Fixture manifests state the literal expected numbers (findings, distinct, dropped, ignored, skipped by reason); fingerprints and grades in them are copied from `test/vectors/manifest.json`, never computed with `src/`.
- Fail closed: a line-wrapped or otherwise undecodable hex/base64 match is reported as `undecodable-candidate` and counts as `ADMIN`; an `lndconnect://` URI without a decodable macaroon is counted in `dropped`.
- Encodings and positions: UTF-8 with and without BOM, UTF-16 LE/BE with BOM, CRLF, LF and CR-only; non-ASCII text before a match gives the right code-point column.
- Boundaries: `*.macaroon` 65,536 vs 65,537 bytes; files of 5,242,880 vs 5,242,881 bytes; NUL at offset 8,191 vs 8,192; a file that grows during the scan.
- A look-alike fixture produces no findings.
- `--fail-on` exits 1 when any finding counts at or above the threshold and 0 otherwise, for each ladder grade; an OPERATE-only tree and a READ/RECEIVE tree exit 0 under `--fail-on SPEND`; lower-case, repeated, missing and `UNASSESSED` values exit 2.
- A path argument that does not exist or cannot be read exits 3; files failing during the walk are listed in `skipped` with their reason.
- Symlinks (including a loop) are not followed; a root argument that is a symlink is followed once; FIFOs and devices are skipped; overlapping path arguments scan each file once; a permission-denied directory is skipped as `unreadable` (proven with an injected file system everywhere and with a real-filesystem test as an unprivileged Linux user).
- SAFE-02 names, in any case and as directory names, are never opened (fs spy); files are opened read-only and left unchanged (SAFE-07).
- `.macwardenignore` and `--ignore-file` suppress exactly the listed fingerprints (with and without a path glob), count them in `ignored`, and keep them out of `--fail-on`; a malformed line exits 3.
- `--json` output validates against `schemas/output/scan.schema.json`; text and JSON both pass the leak test.
- gitleaks `v8.30.1` (pinned Docker image), run with `--redact` and `rules/gitleaks.toml` on the same tree, finds every text item its manifest marks as expected for gitleaks.
- L402 (synthetic tokens built independently of `src/` with a fixed root key): Authorization values with both schemes and with several macaroons, pairs (also as `KEY=<pair>`), `WWW-Authenticate` challenges (`macaroon` or `token`, either order, quoted or bare, both schemes on one line), paid gRPC macaroons and token store files in `.env`, HTTP logs, HAR, curl commands, YAML, code, MCP agent configurations (tagged `mcp-config`), client token directories and git history are each found once with independent fingerprints; look-alikes, digests, short or long preimages and undecodable pairs are not reported as Authorization credentials; `--fail-on READ` exits 1 for a token with a usable preimage and 0 for higher thresholds and for unpaid or mismatched tokens; text, JSON, SARIF and github output and error output carry no preimage or macaroon in any encoding (leak check with the preimages and macaroons as sentinels, with a positive control); hostile lines of open L402 shapes scan in time linear in their length; malformed base64, truncated macaroons, huge inputs and many caveats never exit 8 and stay within the stated bounds.

### Acceptance: online commands and inventory

- The test fixture refuses to run unless the node is on regtest and `getinfo` `version` starts with `0.21.4-beta` (SAFE-10).
- Online conventions: flag/env precedence; `--macaroon` credential text exits 2; the OWN check exits 4 with zero LND calls; `own-root-key-0` warning; `snapshot-drift` warning when ListPermissions differs from the bundled snapshot; `NODE_DEBUG`/`NODE_OPTIONS` refusal exits 2; a crash forced mid-request leaks nothing.
- On a fresh node, `inventory` shows root key ID 0 with the "cannot be individually revoked" note and flags macwarden's own ID.
- A root key ID baked with `lncli` is reported as "unknown — not in this registry (another tool or operator may own it)".
- A registry entry whose root key ID LND no longer has is reported as a difference; LND and the registry are not changed.
- `inventory --verify` reports `accepted` for a live entry and `rejected` after the test regenerates the root keys on the fixture; it never prints the credential.
- Registry and lock: file `0600`, directory `0700`; a held lock exits 3 with nothing sent; a stale lock is removed by `--break-lock` only when its owner provably no longer runs on this host.
- Wrong TLS cert or unreachable host: exit 4, no credential in output.
- The LND facts suite checks the assumptions listed in [architecture.md](architecture.md#assumptions-to-confirm) on the fixture (including empty-list CheckMacaroonPermissions, preimage exposure, the address REST clients appear from, streams surviving a revoke, and root key regeneration replacing every key), and the documents are corrected where reality differs.

### Acceptance: bake

- Request checks with zero LND calls: `UNASSESSED`, `ADMIN` without `--allow-admin`, preset mixed with `--permissions`/`--uri`, missing `--label`/`--out`, empty permissions, invalid or all-digit label → 2; existing `--out` → 3; lock held → 3. When several apply, the lowest-numbered step wins.
- `--out` is created exclusively and owner-only before any LND call and removed on every failure before the bytes are written.
- Two consecutive bakes get two different, new root key IDs, neither 0; two concurrent bakes on one registry: one succeeds, the other exits 3.
- Each preset's macaroon is accepted for an RPC it should allow and rejected for one it should not (checked with `lncli` against LND); `pay-only` cannot call `HtlcInterceptor` or `UpdateChannelPolicy`.
- The final bytes, including the `time-before` caveat, are verified before `--out` is written; `--expires` appears in `inspect` output; an expired macaroon is rejected by LND.
- Every failure branch of B10–B16 gives its exit code (4, 5 or 7) and the observed state, with at most one ListMacaroonIDs call after the failure. B10 and B11 with the chosen ID confirmed absent report no change and need no compensating mutation. B11 with the ID present prescribes `macwarden revoke <id> --unregistered`; unreadable state prescribes `macwarden inventory`. B12–B15 first record an active, unverified entry with no output path when writable and prescribe `macwarden revoke <label>`; a failed registry write prescribes `macwarden revoke <id> --unregistered`. B16 retains the valid file and prints the credential-free entry for recovery.
- A registry entry is written with label, root key ID, permissions, caveats, grade, fingerprint, path, status `active`; the file's fingerprint equals the registry's.
- `--dry-run` prints the plan; LND root key IDs, the registry and the `--out` path are unchanged (SAFE-05).

### Acceptance: revoke

- After `revoke <label>`, LND rejects the macaroon, the registry shows `revoked` with `revokedAt`, other macaroons still work, and the output ends with the revocation-scope sentence.
- Without a usable macaroon file (absent, fingerprint mismatch, expired), `revoke` confirms the ID is absent from ListMacaroonIDs and reports "by ID only".
- Refused before any LND call (V1–V4): `revoke 0`, malformed IDs (`-1`, `+5`, `0x10`, `007`, `18446744073709551616`), ENV or OWN failures, a `--target-file` on root key ID 0 or differing from a numeric target, and a numeric target equal to macwarden's own root key ID (SAFE-03). An unreadable or undecodable explicit target file exits 3 at V3.
- Refused after GetInfo, with zero mutating calls (V6): an unknown or ambiguous active label, another node's entry, an unregistered ID without `--unregistered`, a label resolving to macwarden's own root key ID, or an explicit target file differing from the resolved ID. An invalid registry or a default `outPath` decoding to a different root key ID exits 3. All V1–V6 refusals make zero mutating calls.
- A run killed after DeleteMacaroonID is repaired by rerunning `revoke` (registry marked revoked, LND not called again), including with `--dry-run` and with a declined confirmation.
- `deleted:false` with the ID absent continues; an error with the ID still present exits 5.
- Confirmation shows label, root key ID and grade and needs the typed label (or the ID for unregistered); wrong text, no TTY without `--yes`, or decline change nothing; the lock is taken only after confirmation (SAFE-05).

### Acceptance: rotate

- Stage: the replacement has the old macaroon's permissions (from the decoded old file when its fingerprint matches; a mismatch with the registry exits 3), the same `--expires` duration and a new root key ID; it is verified accepted; the old one is untouched; `inventory` shows the pending replacement. Stage applies every `bake` refusal before any LND call. A second stage while one is pending exits 2 listing both IDs and both ways out.
- Finish: shows old and new ID, grade, permissions and new path; needs the typed label unless `--yes`; revokes the old ID; old rejected, new still accepted; registry shows old `revoked` with `replacedBy`, new `active`.
- Abandoning: `revoke <new id>` removes the staged replacement and leaves the old credential in use.
- `--dry-run` of stage and of finish changes nothing.

#### Rotation failure injection

Each case runs as a unit test with faulty dependencies and as an integration test against the regtest fixture; production code has no test-only hooks. For every case the test asserts the exit code, a message naming the failed step, and, with the `lncli` acceptance probe, that **the old macaroon is still accepted** unless the finish's DeleteMacaroonID had completed.

1. Stage: the bake of the replacement fails, or its response is lost → old untouched; a root key created before a lost response is reported for `revoke <id> --unregistered`.
2. Stage: the staged macaroon is rejected, or the verify call times out → old untouched; the new one is reported for `revoke`.
3. The operator never finishes (the process ends after stage) → both valid; `inventory` shows the pending replacement.
4. Finish: DeleteMacaroonID fails and the single reconciliation shows the old ID still present → old still valid; registry unchanged; exit 5. If the response was lost after completed deletion and reconciliation proves absence, continue only with the prescribed read-only verification; never retry deletion. Unknown state or an insufficient proof exits 7 without marking the registry revoked.
5. Finish: DeleteMacaroonID reports success but the old macaroon is still accepted → exit 7; registry not marked revoked.
6. LND unreachable between any two calls of stage or finish → stop with the matching exit code; at most one ListMacaroonIDs afterwards.
7. Registry write fails after an LND change → LND state is reported with the follow-up command; the registry is not left claiming the opposite.
8. Process killed during stage or during finish (integration: killed between the two invocations, and mid-finish via a paused container; unit: faulty dependencies) → `inventory` shows the actual state; a rerun of finish repairs the registry; old valid unless the delete completed.

### Acceptance: replacing the default macaroons

- The guide [Replacing the default macaroons](replacing-default-macaroons.md) orders the steps as: plan a maintenance window → the operator rotates the root keys by hand (macwarden never does) → bake macwarden's own session macaroon → `macwarden bake` one macaroon per app → distribute → `inventory --verify` → `scan` confirms no root-key-0 credential remains in app configs. It states that rotating the root keys invalidates every macaroon ever baked, and never suggests moving apps first and rotating afterwards.
- Following the guide end to end on the regtest fixture leaves every app on its own root key ID.
- The guide never asks macwarden to call `changepassword` or touch `macaroons.db` (SAFE-02).
- The BTCPay Server preset has an integration test showing BTCPay Server's required calls succeed and a call outside its needs is rejected.

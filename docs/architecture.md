# macwarden — architecture

Behaviour is defined in [spec.md](spec.md); safety rules (SAFE-nn) in [security-model.md](security-model.md). LND facts below were checked against LND `master` source on 2026-10-02, and some were observed on a regtest `lightninglabs/lnd:v0.21.4-beta` node the same day (marked "observed"). Anything not checked, including claims reported by reviewers from source but not re-read here, is in "Assumptions to confirm" at the end.

## Stack

TypeScript (strict), Node.js `^22.23.2 || ^24.18.1 || >=26.5.1` (the July 2026 security releases, which fix the HTTP/2 flaws CVE-2026-56846 and CVE-2026-56848 in `node:http2`, used by `watch`; vitest 5 / vite 8 need ≥ 22.12), ESM, published to npm. Node built-ins only at runtime: `node:util` (`isDeepStrictEqual`, `types`), `node:https`, `node:http2` (only `src/lnd/grpc.ts`, for the `watch` middleware stream), `node:crypto`, `node:fs`, `node:path`, `node:os`, and `node:child_process` — always with an argument array and no shell, in exactly four places: `src/commands/bake/write-out.ts` (`execFile`) to run System32 `whoami /user` (the current user SID) and then `icacls` on Windows, `src/registry/process-domain.ts` (`execFile`) to run the fixed system PowerShell process-domain query on Windows (see Lock process-domain proof), and `src/scan/git-history.ts` (`spawn`, minimal environment, no network transport, no optional locks, repository config keys that could start a program or change the listing pinned on the command line, 120 s idle timeout) to stream local `git rev-parse`, `git log` and `git cat-file` output for `scan --git-history`, and `src/watch/alert.ts` (`spawn`, no shell, no arguments, minimal environment; its own process group on POSIX, SIGTERM at 10 s and SIGKILL at 12 s, and the group is killed 1 s after the command exits; on Windows a timed-out command's tree is killed with System32 `taskkill /T /F`) to run the operator's `watch --alert-command` with the canary event on stdin. The audited config-key list is the header comment of `src/scan/git-history.ts`.

```ts
}

                                                                     // or InputError('input-read' | 'input-form') (exit 3) — never includes input
                                                                     // file/stdin reads stop after at most 1,048,577 raw bytes;
                                                                     // overflow above 1,048,576 fails at input-read before decoding

```

`readCredential` follows the order in spec.md (Global conventions), including the `--unsafe-arg` rule. `literal: true` tells the caller the argument itself was the credential, so it emits warning `unsafe-arg`.

## Redaction and leak paths

Tested by the leak tests, which plant registered sentinel credentials and check every output, temporary file and retained report for them in raw, hex, base64 and base64url forms ([CONTRIBUTING.md](../CONTRIBUTING.md#tests)):

1. **`Secret` type.** Credential bytes only ever live inside `class Secret`. It is a generic byte container that also holds malformed inputs. For `inspect` only, it may hold a verbatim NIP-47 `nostr+walletconnect://` URI; `decodeNwc` in `src/decode/index.ts` parses it, derives the client public key with a load-time capture of `createECDH`, and returns facts only after refusing (exit 3) any reported field that carries a recognisable encoding of the connection secret (spec.md, NWC input). Its public fingerprint and its `toString`, `toJSON` and `[util.inspect.custom]` markers use the canonical bytes of a valid macaroon, ending at its signature packet. Trailing bytes preserve that identity. Malformed or nonmacaroon containers safely hash their exact stored bytes and retain the decoder's specified failure. Credential bytes are stored in a native private field in `src/secret-capability.ts`; a `Secret` instance and its prototype expose no byte-access method. Public `src/secret.ts` exports only `Secret`. The internal `revealSecret` import capability is permitted only in `src/decode/index.ts`, `src/lnd/index.ts`, and `src/commands/bake/write-out.ts`; consumers cannot re-export it. The build checks the closed production import graph and exported authority, then keeps internal module storage and reveal authority lexical in the shipped runtime. Public module facades expose individual ESM value bindings; the shipped credential facade exports only `Secret`, so native dynamic imports do not expose raw reveal authority. Internal export objects are neither public nor passed to replaceable global export-definition or freezing functions. Lint enforces the declared import, dynamic-code, network-global and builtin boundaries. Ordinary JSON property access remains permitted. These mechanisms enforce the shipped credential boundary without claiming isolation from arbitrary hostile code sharing the Node process. `Buffer.from`, `createHash` and the hash methods are captured at load, so later replacements do not observe stored bytes; code that replaces `Buffer.prototype.subarray` before input or decode runs can still observe bytes under this credential boundary. Spread copies of decoded facts retain an opaque canonical `Secret` under an enumerable symbol, allowing re-encoding without facts-object identity.

2. **`output` choke point.** All stdout/stderr goes through `output.render`/`output.error`. Before writing, bounded shared credential recognition redacts confirmed structured credentials in contiguous, wrapped and encoded text without repeated prefix decoding; grouped base64 runs (groups joined by `-`, `_` or another separator) are found by a single linear pass (`src/grouped-runs.ts`, mirrored in the leak check) rather than backtracking regular expressions, so recognition time grows linearly with the text; scan and output use the same recognition boundary. Raw bytes are recognised as latin1 and as UTF-8: a UTF-8 rendering replaces ill-formed bytes with U+FFFD and so loses a binary credential's lengths, and it is recognised by the framing that survives (U+0002 and a header packet kind at the start, an end-of-section U+0000 and the signature packet header before the last 32 bytes), redacted from its start to the furthest end its signature can reach (`src/credential-recognition.ts`). The renderer rejects non-plain values before serialization and escapes control characters in paths and LND-supplied strings.
3. **Process level.** `cli.ts` installs `uncaughtException` and `unhandledRejection` handlers that mark an internal failure without printing input, stack or request objects. A failure during a command remains sticky through completion: the command emits only its internal-error result, `error.step: "internal"`, and exits 8 even if its work otherwise succeeds. A harmless Node `warning` is suppressed without changing the command result or exit code. A failure outside an active command reports a stage-only error through `output.error`. If a mutating LND call may have been sent, the internal-error message adds "run `macwarden inventory`". Online commands refuse to run when `NODE_DEBUG` names `http`, `https`, `tls` or `net`, or any `NODE_OPTIONS` value is nonempty (spec.md ENV check). The leak test includes a crash forced mid-request.

Errors carry a stage name (`input-form`, `v2-header`, `identifier-root-key-id`, …) and never the input.

## LND REST adapter

```ts
interface LndAdapter {
  getInfo(): Promise<{ pubkey: string; alias: string; network: string; version: string }>;
  listMacaroonIds(): Promise<bigint[]>;
  listPermissions(): Promise<Record<string, string[]>>;
  bakeMacaroon(perms: string[], rootKeyId: bigint): Promise<Secret>;   // refuses rootKeyId 0n
  deleteMacaroonId(rootKeyId: bigint): Promise<{ deleted: boolean }>;  // refuses 0n (SAFE-03, second layer)
  checkMacaroon(mac: Secret, perms: string[]): Promise<{ valid: true } | { valid: false; reason: 'root-key-missing' | 'signature-mismatch' | 'other'; message: string }>;
                                                                       // refuses an empty perms list
}
```

Implementation: `node:https` with `ca` = the `--tls-cert` file and normal hostname verification (SAFE-08); no option to disable verification. Header `Grpc-Metadata-macaroon: <hex>` ([docs/macaroons.md](https://github.com/lightningnetwork/lnd/blob/master/docs/macaroons.md)). 10 s timeout per call. No automatic retries: after a failure a command makes at most one `listMacaroonIds` call (spec.md). The adapter exposes no other endpoint; a test asserts the list (SAFE-02). `node:https` is used instead of `fetch` because global `fetch` cannot take a per-request CA without the undici package; it has no SOCKS support, so Tor-only nodes need an SSH tunnel to localhost.

| Method | REST | Request / response | LND permission required |
|---|---|---|---|
| GetInfo | `GET /v1/getinfo` | `identity_pubkey`, `alias`, `version`, `chains[].network` | `info:read` |
| ListMacaroonIDs | `GET /v1/macaroon/ids` | → `root_key_ids` (uint64[]) | `macaroon:read` |
| ListPermissions | `GET /v1/macaroon/permissions` | → `method_permissions: {uri: {permissions: [{entity, action}]}}` | `info:read` |
| BakeMacaroon | `POST /v1/macaroon` | `permissions: [{entity, action}]`, `root_key_id` (uint64 as string); `allow_external_permissions` is never sent as `true` → `macaroon` (hex) | `macaroon:generate` |
| DeleteMacaroonID | `DELETE /v1/macaroon/{root_key_id}` | → `deleted` (bool) | `macaroon:write` |
| CheckMacaroonPermissions | `POST /v1/macaroon/checkpermissions` | `macaroon` (bytes → base64 in JSON), `permissions` (the macaroon's own decoded permissions; `uri:` ones as `{entity: "uri", action: <method>}`); `fullMethod` and `check_default_perms_from_full_method` are never set → `valid` | `macaroon:read` |

"Verify accepted" and "verify rejected" are defined in spec.md. An empty permission list is not a validity proof; its behaviour is pinned by the LND facts suite (assumption 9). In tests, the oracle for accepted/rejected is an `lncli` call made with the macaroon in the pinned container, never macwarden's own check.

Sources: REST mappings in [lnrpc/lightning.yaml](https://github.com/lightningnetwork/lnd/blob/master/lnrpc/lightning.yaml); messages in [lnrpc/lightning.proto](https://github.com/lightningnetwork/lnd/blob/master/lnrpc/lightning.proto); permissions in `MainRPCServerPermissions` in [rpcserver.go](https://github.com/lightningnetwork/lnd/blob/master/rpcserver.go) and `macPermissions` in [routerrpc/router_server.go](https://github.com/lightningnetwork/lnd/blob/master/lnrpc/routerrpc/router_server.go); REST field types at [lightning.engineering/api-docs](https://lightning.engineering/api-docs/api/lnd/).

### Verified LND behaviour the commands rely on

- BakeMacaroon validates entities against `onchain, offchain, address, message, peers, info, invoices, signer, macaroon, uri` and actions against `read, write, generate`; a `uri` action must be an existing `/package.Service/Method`. Observed: `remotesigner` and unknown `uri:` methods bake only with `allow_external_permissions`, and ListPermissions never lists `remotesigner`. An empty permission list is rejected. It adds **no caveats** ("this can be done offline"), so macwarden adds `time-before` itself (rpcserver.go).
- The BakeMacaroon handler does not compare requested permissions with the caller's own, so `macaroon:generate` is admin-equivalent (rpcserver.go; SAFE-09).
- Root key IDs are uint64 in the API and stored as the decimal string bytes (`strconv.FormatUint(id, 10)`); the default is `"0"` (rpcserver.go, [macaroons/store.go](https://github.com/lightningnetwork/lnd/blob/master/macaroons/store.go)).
- Baking with an ID that already exists **reuses that root key**; an unknown ID creates a new 32-byte key (`RootKey()` in store.go).
- DeleteMacaroonID refuses the default ID and the internal `enckey` (`ErrDeletionForbidden`); an unknown ID returns `deleted:false` without error (store.go, rpcserver.go).
- Verifying a macaroon whose root key is gone fails in `Get()` with `root key with id <id> doesn't exist` (store.go; the docs quote it as `cannot get macaroon: root key with id 0 doesn't exist`).
- After deletion, CheckMacaroonPermissions returned HTTP 400 with JSON code `3` and message `root key with id <id> doesn't exist`; it did not return `valid:false`. The next `lncli` request using that key was rejected. These are pinned fixture observations, not a guarantee of a particular gRPC code ([CP-015 observations](test/oracle/facts/observations.json)).
- `GenerateNewRootKey` (store.go, used by `changepassword --new_mac_root_key`) regenerates the default root key **and every other root key ID** ("Now iterate over all the other root keys that may exist and re-generate each of them"). In the isolated fixture, the equivalent REST ChangePassword request with `new_macaroon_root_key` rejected both a root-key-zero and a nonzero credential on later ordinary RPCs. The `lncli changepassword` probe required a TTY and did not complete, so there is no CLI-success claim. macwarden never invokes either API (SAFE-02; [CP-015 observations](test/oracle/facts/observations.json)).
- `MacaroonStreamServerInterceptor` ([rpcperms/interceptor.go](https://github.com/lightningnetwork/lnd/blob/master/rpcperms/interceptor.go)) checks the macaroon once, when a stream opens. In the pinned fixture, a `SubscribeInvoices` stream opened before deletion delivered the next invoice after deletion, while a new request was rejected ([CP-015 observations](test/oracle/facts/observations.json)).
- Method permissions used by the `pay-only` preset (`macPermissions` in routerrpc/router_server.go; rpcserver.go): `/routerrpc.Router/SendPaymentV2` needs `offchain:write`, `/routerrpc.Router/TrackPaymentV2` `offchain:read`, `/lnrpc.Lightning/DecodePayReq` `offchain:read`. `offchain:write` also covers `/routerrpc.Router/HtlcInterceptor`, `/routerrpc.Router/UpdateChanStatus` and `/lnrpc.Lightning/UpdateChannelPolicy`. `/lnrpc.Lightning/ListInvoices` and `SubscribeInvoices` need `invoices:read`. Generating the test vectors re-checks these names against the committed snapshot.
- gRPC codes are not reliable: BakeMacaroon errors were observed as code `Unknown`, not `InvalidArgument`. The adapter classifies errors by HTTP status and message text, never by assuming a code: root-key-missing text → `root-key-missing`; the independently observed HTTP 400 target signature mismatch → `signature-mismatch`; authentication, transport and unknown errors remain distinct and are never evidence that an ID was deleted.
- Observed: `lncli printmacaroon` prints `{version, location, root_key_id (string), permissions (serialized operation/action order, with duplicates), caveats (null when empty)}`. Its [pinned implementation](https://github.com/lightningnetwork/lnd/blob/390b2d2b7bdcc335c183962e483f5daeceb8f0e7/cmd/commands/cmd_macaroon.go#L449-L456) iterates the decoded operations and actions without sorting; a hand-made reversed-order macaroon printed that order ([CP-015 observations](test/oracle/facts/observations.json)). Root key ID 18446744073709551615 baked and decoded; go-macaroon ignores bytes after the signature; `lncli` 0.21.4 has no `--ip_range` flag; ListPermissions listed 164 methods, including nonempty requirements such as GetInfo's `info:read`.
- On the pinned fixture, CheckMacaroonPermissions with an empty requested permission list returned `valid:true` for both an expired macaroon and one with a corrupted signature; an ordinary RPC rejected the corrupted one. Product verification never uses an empty permission list. A host REST request and a container REST request both accepted an `ipaddr 127.0.0.1` caveat, consistent with the REST proxy being the address LND checks ([CP-015 observations](test/oracle/facts/observations.json)).
- An invoice with a known preimage exposed its nonzero `r_preimage` via ListInvoices to `invoices:read`. The pinned fixture's `offchain:read` ListPayments call was permitted but returned no outgoing payments, leaving preimage exposure through that permission unresolved. The combined `preimage-exposure` warning remains conditional ([CP-015 observations](test/oracle/facts/observations.json)).
- Root key 0 can be invalidated by `changepassword --new_mac_root_key` (which, per `GenerateNewRootKey` above, replaces every root key) or, per LND's docs, by deleting `macaroons.db` (docs/macaroons.md). macwarden does neither (SAFE-02). Three setups change what macwarden can see or prove:
  - `--no-macaroons`: LND checks no macaroons at all; macwarden's verification is meaningless there.
  - `--mac_root_key` / stateless init: macaroons can be baked offline from the root key and never appear in ListMacaroonIDs or `inventory`.
  - Remote signer: the signer node has its own macaroon store and must be inventoried separately.

## Macaroon decoding

Hand-written (~250 lines), no dependency. Format, from [go-macaroon](https://github.com/go-macaroon/macaroon/blob/v2/marshal-v2.go) (which LND uses):

- **v2 binary:** byte `0x02`; then packets `type(varint) len(varint) data`, where type 1 = location, 2 = identifier, 4 = verification ID, 6 = signature, and 0 = end-of-section (a single byte). Layout: header section `[location] identifier EOS`; per caveat `[location] identifier [vid] EOS`; a final `EOS`; then the signature packet (32 bytes). Fields within a section must be in increasing type order. A nonempty caveat location without a verification-ID packet is rejected; a present empty verification ID parses and is classified as first-party because its length is zero, even if a location packet is present ([go-macaroon v2.0.0 marshal](https://github.com/go-macaroon/macaroon/blob/bed2a428da6e56d950bed5b41fcbae3141e5b0d0/marshal-v2.go#L151-L196), [verification](https://github.com/go-macaroon/macaroon/blob/bed2a428da6e56d950bed5b41fcbae3141e5b0d0/macaroon.go#L50-L56)). go-macaroon ignores bytes after the signature packet; the decoder does too, adds warning `trailing-bytes`, and fingerprints and re-encodes only the canonical bytes. For valid macaroons, the decoded identity equals the public `Secret` fingerprint and debug marker; malformed or nonmacaroon containers safely hash their exact stored bytes and retain the specified decoding failure (Redaction and leak paths item 1). v1 macaroons are refused at stage `v2-header` ("macaroon v1 format is not supported"). Failure stages are listed in spec.md.
- **Signature chain:** `sig₀ = HMAC-SHA256(derive(rootKey), id)`, then for each first-party caveat `sig = HMAC-SHA256(sig, caveatId)` ([macaroon.go](https://github.com/go-macaroon/macaroon/blob/v2/macaroon.go), [crypto.go](https://github.com/go-macaroon/macaroon/blob/v2/crypto.go)). `addFirstPartyCaveat` needs only the current signature, which is how `lncli` adds `--timeout` client-side.
- **LND identifier:** byte `0x03` (bakery version 3), then protobuf `MacaroonId { bytes nonce = 1; bytes storageId = 2; repeated Op ops = 3 }`, `Op { string entity = 1; repeated string actions = 2 }` (lightning.proto; `printmacaroon` in the [pinned cmd_macaroon.go](https://github.com/lightningnetwork/lnd/blob/390b2d2b7bdcc335c183962e483f5daeceb8f0e7/cmd/commands/cmd_macaroon.go#L449-L456) decodes it the same way). `storageId` is the root key ID as canonical decimal ASCII (else stage `identifier-root-key-id`); permissions are `entity:action` for every action of every op, preserving order and duplicates. The protobuf reader accepts field numbers 1 through 536870911, rejects malformed UTF-8 in protobuf `string` fields at `identifier-proto`, and skips unknown fields with wire types 1 and 5. Raw macaroon location bytes retain go-macaroon's permissive UTF-8 replacement behavior. See the [protobuf field-number limit](https://protobuf.dev/programming-guides/proto3/#assigning-field-numbers) and [CP-015 references](test/oracle/facts/sources.json).
- **Caveat conditions** are `name arg` strings: `time-before <RFC3339Nano UTC>` (bakery `checkers`), `ipaddr <ip>`, `iprange <cidr>`, `lnd-custom <name> [<condition>]` ([macaroons/constraints.go](https://github.com/lightningnetwork/lnd/blob/master/macaroons/constraints.go)). Go `time.Parse` accepts more than nine fractional digits and truncates beyond nanoseconds ([Go 1.26.8 time parser](https://github.com/golang/go/blob/go1.26.8/src/time/format.go)); inspect compares at nanosecond precision and keeps the caveat value verbatim. A third-party caveat's reported value is its location, not the raw caveat id `printmacaroon` prints.
- **lndconnect:** `lndconnect://<host>:<port>?[cert=<base64url DER>&]macaroon=<base64url>` ([lndconnect spec](https://github.com/LN-Zap/lndconnect/blob/master/lnd_connect_uri.md)). A shared parser percent-decodes the one macaroon query value exactly once and accepts only canonical base64url, either unpadded or with exactly its required trailing padding. It rejects standard-base64 plus or slash, whitespace, malformed or remaining percent escapes, misplaced or excess padding, and noncanonical unused bits. Inspect fails at `input-form`; scan drops the candidate. Used only as `inspect`/`scan` input; its host and port are never contacted.

The spec's example macaroon begins `AgEDbG5k…` = `02 01 03 'lnd' 02 …`: version 2, location `lnd`, identifier starting `0x03`. The scan prefixes in spec.md come from this, so text detectors only match macaroons with location `lnd`.

**Test vectors.** `scripts/make-vectors.mjs` runs against the pinned regtest fixture (the container exec command is injectable through env `MACWARDEN_LNCLI`): it bakes one macaroon per grade-table row (external permissions with `allow_external_permissions`) and per preset, adds `time-before` and `ipaddr` caveats with `lncli constrainmacaroon`, and copies LND's default three files. Structural vectors (third-party caveat, unknown condition, `iprange`, `lnd-custom`, nanosecond `time-before`, duplicate ops, no location, trailing bytes) are produced by the script offline and labelled `hand-made`, meaning "no LND-acceptance claim"; `lncli printmacaroon` JSON is still captured for them as the decode oracle. The manifest records each vector's fingerprint computed with `sha256sum`/`openssl` (independent of `src/`) and a hand-assigned expected grade. These are throwaway regtest credentials, regenerated on LND upgrades. Negative vectors (one per decoder stage) are hand-made. Tests: decode equals oracle; decode→encode is byte-identical to the canonical bytes; a macaroon with a past `time-before` added by `addFirstPartyCaveat` is rejected by LND (integration). A library would be reconsidered only if the hand-written decoder cannot pass the vectors.

## Root key ID allocation (`bake`)

Because LND reuses an existing root key for an existing ID, reusing an ID would silently make two macaroons share a key. So: draw a random uint64 in [2³², 2⁶³−1] with `crypto.randomBytes`; reject it if it is in ListMacaroonIDs (fetched immediately before) or anywhere in the registry (including revoked entries); repeat, at most 16 draws (then exit 5). Runs sharing a registry are serialised by the registry lock; the large random range makes a collision with small hand-picked IDs or with a run on another registry negligible. A collision could not be detected afterwards, which is why both measures exist. After baking, the decoded `storageId` must equal the chosen ID (spec.md B12).

## Registry, lock and the `--out` file

- Registry file `0600`, directory `0700`; on Windows best effort (SAFE-06). Saved as temp file + rename; the rename is retried on Windows `EPERM`/`EBUSY` (up to 10 tries over about one second). On POSIX the directory is then synced so the rename survives a power loss (best effort where a file system refuses directory sync). Acquiring the lock removes this registry's own leftover `<registry>.<uuid>.tmp` files from interrupted saves; only the lock holder saves, so none can belong to a live writer. A failure after the lock file is created (closing it, or removing the `.lock.claim` guard, which is retried briefly on `EBUSY` and on Windows `EPERM`/`EACCES`) releases the lock before reporting, so a failed acquisition never leaves a stale lock.
- Lock file `<registry>.lock`, created exclusively, holding `{pid, hostname, startedAt}`. `--break-lock` recovers it only when `hostname` is this host and `process.kill(pid, 0)` reports the pid not alive, regular-file dev/ino identity is established, and the uniquely quarantined inode and owner still match. Changed locks are preserved without overwriting another writer. The lock is never held while a prompt waits for input.
- `--out` (`src/commands/bake/write-out.ts`, shared by `bake`, `rotate`, the offline `attenuate` and `inventory --report --out`): opened with flags `wx` and mode `0600` before any LND call and kept open; on any failure before the bytes are written the empty file is removed. On Windows it then runs System32 `whoami /user /fo csv /nh` (no shell, 10 s timeout) and, when that returns a valid SID (`S-1-` followed by numeric parts), runs System32 `icacls <file> /inheritance:r /grant:r *<SID>:F`. Without a valid SID it grants `<USERDOMAIN>\<user>:F` from `os.userInfo()` and `USERDOMAIN` instead. Both run through `execFile` with an argument array and no shell; if the grant fails, warning `acl-best-effort`. A handle opened by another process before the grant keeps its access, so the creation handle is closed and the file reopened with libuv's `UV_FS_O_EXLOCK` (share mode 0): the reopen fails while any other handle exists, and no handle can be opened until the bytes are written and it is closed. A failed reopen removes the empty file and fails the reservation; a reopened file with a different device/file index is neither written nor removed. Only the exclusive handle receives bytes.

### CP-038 online lifecycle and pending recovery

The adapter reports a request that reached LND (TLS established) but got no complete response, such as a timeout, reset, cancellation or oversized response, as `LndUncertainError`. For BakeMacaroon and DeleteMacaroonID such an outcome is unknown: an immediate ListMacaroonIDs cannot prove "nothing changed" or "still valid", because LND finishes a request after the client disconnects. Commands keep the pending entry or leave the registry unchanged and exit 7 with an executable recovery command. `src/online.ts` consumes only normalized `LndAdapter` methods and values. It owns endpoint validation, identity normalization, snapshot comparison, ID listing, typed LND failure mapping and bounded certificate reads. Commands preserve their numbered step order and pass failures to this boundary without interpreting raw transport objects. Registry reload/update/revocation/replacement methods require the owned lock.

A pending allocation is persisted before issue, without credential bytes or a fabricated fingerprint. `fingerprint:null` requires `verified:false` and `outPath:null`; known credentials use their canonical fingerprint. Final verification and file write finalize the pending entry. Cooperative cancellation is scoped to one invocation, interrupts adapter/prompt waits and executes cleanup without replacing the primary outcome. Unknown mutation state retains pending recovery. SIGKILL remains outside cooperative cleanup. Normal and recovery lock acquisition share an exclusive short-lived <registry>.lock.claim guard, preventing entry during quarantine verification; an abandoned or changed claim requires offline recovery. Stale-lock recovery requires matching producing/recovering process-domain metadata before same-host dead-process ownership and the regular-file inode before and after a unique quarantine rename. Ambiguous or changed ownership is preserved for offline recovery. Missing old-credential rotation authority requires typed informed approval showing the grade and permissions before lock/output reservation. An absent unregistered ID has nothing to revoke (SPEC V7, exit 5); if the record save fails after deleting an unregistered ID, exit 7 says no further action is needed and prints no rerun. Cleanup failure is appended to the primary error; successful possible mutation plus failed cleanup reports exit 7. Pre-mutation cancellation reports cancelled/interrupted with exit 6.

### Credential boundary limitations and bounds

Protected-path refusal checks supplied and resolved path component names. A differently named hardlink to a protected file cannot be identified by this policy; inode or size heuristics are not used. Keep scan inputs limited to directories intended for credential inspection.

Ignore input is limited to 5 MiB (5,242,880 raw bytes) and 1,024 entries; the bounded reader reads at most 5,242,881 raw bytes and rejects overflow with exit 3, and the parser accepts at most 5,242,880 code units. Each path glob is limited to 1,024 characters and 256 tokens. The matcher uses bounded dynamic programming rather than backtracking. Ignored credentials remain visible only when findings are suppressed, as sorted unique canonical `fp:<16 lowercase hex>` fingerprints in optional `result.ignoredFingerprints` and a separate `ignored-fingerprints` text line, without credential bytes or suppressed finding details; `summary.ignored` counts suppressed findings, which are excluded from `findings`, `failOn` and `byGrade`, while `skipped` contains only actual skipped files with the existing reason enum and `filesSkipped` equals `skipped.length`. In CI, select an operator-controlled file with `--ignore-file` from a trusted path, because a repository's `.macwardenignore` can suppress its own findings.

Peer GetInfo pubkeys must be compressed public keys (02/03 followed by 64 hexadecimal digits), normalized to lowercase. Alias and version are at most 256 characters with control characters refused. A timer is created only after request construction and cleared on every settled request. The command cancellation signal aborts pending requests, removes its listener, clears the timer and destroys the request. ListMacaroonIDs accepts exactly one `root_key_ids` field and canonical uint64 tokens, without duplicate keys or trailing input. HTTP 500 own-credential authentication failures map to exit 4. Only independently observed HTTP 400 target missing-root-key or signature-mismatch reasons prove rejection.

Windows credential output invokes the absolute `SystemRoot/System32/icacls.exe` executable with an argument array and `shell:false`.

#### Lock process-domain proof

Linux lock records bind the producing process to the trusted kernel boot ID and the device/inode identity of its PID namespace (`/proc/self/ns/pid`). Recovery requires exact equality with the recovering process before interpreting ESRCH. Missing, legacy, malformed and mismatched records require offline recovery. Trusted own-process metadata paths are fixed and never derived from credential or registry input. Platforms without a supported process-domain query record null and refuse automatic stale-owner recovery; ordinary lock acquisition and owned release still work. Windows uses a fixed bounded system PowerShell helper inheriting the owning process domain. The native RtlGetCurrentServiceSessionId export reports the effective service-session identity: a successful zero identifies the host domain, and nonzero identifies a service/silo domain. Missing exports and failed queries remain unverifiable. This native API is not a published stable Win32 contract; independent review must assess its domain semantics and helper inheritance. NtQuerySystemInformation class 90 supplies the kernel boot identifier; status zero, the complete 32-byte structure and a nonzero GUID are required. Windows domain records bind this boot identifier to the effective service-session identity, without relying on editable registry machine identifiers. Query errors or unsupported identity refuse recovery; hostname, filesystem identity and uptime are insufficient. Only src/registry/process-domain.ts may invoke this trusted ownership query, with no profile, shell interpolation, caller script, network or credential inputs.

Old-credential baseline verification preserves completed normalized negative acceptance as by-id-only. Transport/authentication/protocol failures stop at V8/F7 before DELETE or any further RPC; unexpected baseline errors retain internal failure classification.


## Watch (owner addition 2026-10-07)

`src/lnd/grpc.ts` is a single bidirectional gRPC call over `node:http2` (pinned CA, hostname verification, gRPC framing, compressed messages refused, 200 MiB message limit like LND, TCP keepalive and an HTTP/2 PING every 30 s that must be answered within 20 s, each received frame zeroed after use). `src/lnd/middleware-proto.ts` decodes RPCMiddlewareRequest and encodes RPCMiddlewareResponse by hand (lnrpc/lightning.proto v0.21.4-beta field numbers), skipping unknown fields and never copying the serialized RPC payloads. `registerMiddleware` in `src/lnd/index.ts` reveals the own macaroon only for the request metadata, wraps each intercepted macaroon in a `Secret` before any other module sees it, and sends the caller's verdict before doing anything else. `src/commands/watch.ts` runs the read-only observer and, when canaries exist, the canary guard; attribution, usage recording and alerts happen after the verdict (microtasks), so LND is answered within its intercept timeout. `src/watch/usage.ts` and `src/watch/canary.ts` own the sidecar files next to the registry (`.usage.json`, `.canary.json`, `.watch.lock`). REST was not used for the stream: LND's WebSocket proxy caps a message at 4 MiB, so a large intercepted response would end the stream and fail that RPC.

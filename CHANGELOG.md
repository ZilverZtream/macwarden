# Changelog

## Unreleased

Fixes from an external audit of every source file of 1.3.1, each claim verified with a probe before it was fixed; every fix has a test that fails on 1.3.1. Claims that were refuted, or that describe behaviour the specification prescribes, are not changed.

### Security

- `scan` paths and decoded facts: encoded macaroons were redacted before L402 values, so a `<macaroon>:<preimage>` pair or L402 header in a path or caveat lost its macaroon and kept its preimage, in every output format. Structured forms are now redacted first, as in the output.
- Rune facts: the long-token scrub ran before macaroon redaction and cut a macaroon held in a rune restriction (hex in groups, wrapped base64), so its signature tail was printed. Known NWC secrets and L402 preimages inside rune restrictions were not redacted in `scan --json`, and NWC secrets there were not collected.
- NWC: a wallet secret after an HTML-escaped separator (`&amp;secret=`) or `;secret=` was not collected, so it was printed where it appeared elsewhere; JSON-escaped, percent-encoded and `+`-as-space NWC URIs were not redacted in output. A known secret inside a longer base64 run is now redacted at any byte alignment.
- Output redaction: a grouped base64 macaroon joined to a key or suffix by a separator (`mac:AgED:bG5k:…`) was read as irregular groups and printed in full. An lndconnect URI followed by punctuation, or with its macaroon in standard base64, kept its host and certificate around a redacted macaroon; it is now replaced whole.
- `scan --json`: `summary.agentConfigs` paths were not redacted against known secrets.

- `scan --git-history`: git opened the scanned repository's `diff.orderFile` (on Windows a network path made an SMB connection; a protected file was read). The history read now pins the order file.
- Output redaction: an escape-like prefix (`%2`, `\x2`, `\u000`) before a base64, base64url or base32 macaroon was decoded together with its leading `A` and hid the whole macaroon, which was then printed in full (for example in a scanned file's path). Every form is now also recognised in the literal text.
- `scan`: an L402 value holding both an L402 and an LND macaroon is reported as its LND macaroon, but its preimage was not redacted, so it appeared in a path or in the other macaroon's caveat (SAFE-01).
- `inventory --report`: the report redacted encoded macaroons only, and before anything else, so an L402 value's preimage, an NWC secret or a rune in key context in an alias, version or caveat was written as is (to the `--out` file; the preimage also to stdout and `--json`). The report now uses the output's whole redaction.
- `verify`: a signature mismatch was conclusive on a registry fingerprint match even for a row recorded with `verified: false` (for example the bytes of an altered copy given to `revoke --unregistered --target-file`), so verify could call a live credential dead. Only bytes LND accepted count.
- `inventory --verify`: a row whose root key ID was edited while it kept another credential's file and fingerprint was checked with that file and reported `accepted`. The file's root key ID must now be the row's.

### Fixed

- `watch`: an oversized macaroon whose header was re-framed as go-macaroon still accepts it (non-minimal varints of 5 to 10 bytes, or v1 framing) lost its identifier and was journaled `id:undecodable`; the header is now found in every framing.
- `watch` lock: a lock refused because the path no longer named the file this watch created removed the file a link resolved to without checking it was its own, so another watch's lock could be deleted. A watch reading a lock another watch had created but not yet written called it ownerless; it now waits briefly for the owner record.
- `scan --git-history sub .`: a work-tree file whose finding `sub/.macwardenignore` ignored was reported again from the history of `.` as a commit finding.
- `scan`: a rune key whose value is too short to be a rune (`rune=a/b/cln_rune="…"`) moved the key search past the rune key inside it, and that rune was neither found nor redacted.
- `recommend`: the printed `bake` command was refused by bake when the observed methods graded ADMIN (now with `--allow-admin`) or included a method LND lists but the bundled permission table does not (now withheld, warning `recommendation-unassessed`).
- `inventory --report --out`: an existing file was refused only after every LND request; it is now refused at N7 before any, and the report is written to the path that was checked.
- `inventory --verify`: an interrupt during the checks was recorded as a row error and the remaining rows were checked; it now stops the command (exit 6).
- `bake`: an unexpected failure after the bake request was sent no longer omits the allocated root key ID and its recovery command.
- `respond`: warnings from the rotations it runs (`acl-best-effort`) were dropped.
- Usage file: records over a bound were ordered as text, so a newer record with a fraction of a second could be dropped before an older one; a duplicate key beyond a bound was accepted.
- A repeated `--json` is refused (exit 2) like every other repeated flag.
- `reconcile`: `--since` after now (no `--until`) dropped the warnings collected before the window was checked.
- Payment journal: a BOLT11 invoice with a multiplier letter but no digits (`lnbcm1…`), which LND refuses, was read as an amountless invoice and its hash journaled.
- `watch`: every intercepted macaroon's fingerprint (a parse of every caveat and a hash of up to 64 KiB) was computed while answering LND, outside the attribution budget, although only its identifier is needed; it is now computed when first read.
- `watch`: `macwarden --json watch` skipped the alert cleanup and the exit deadline that `macwarden watch --json` has. An alert command whose process group is already empty when it exits is no longer killed by group a second later (its group ID could have been reused). A write that reports no progress backs off instead of being retried at once.
- `bake --canary`, `watch`: a failed write of `<registry>.canary.json` left an empty file that made every later run fail; the configuration is now written to a temporary file and linked into place.
- `scan --agent-configs --git-history`: history was read for the discovered agent locations, which are usually outside a git work tree, so the scan failed (exit 3). History is read for path arguments only; without one the combination is a usage error.
- `scan`: a repeated `--format` said "takes one of …"; it now says the flag was given more than once. The unsafe `NODE_OPTIONS` check also runs when a programmatic caller passes no environment.
- `--version` reads the installed version without failing.

### Payment lab

- Payer: an HTLC attempt or creation time learnt from a superseded submission's own SendPaymentV2 stream was recorded under the live submission, so a tracker's FAILED for the live submission, read before that submission reached LND, could fail it, release its budget and admit a replacement while it might still pay. A SendPaymentV2 update now records under its own submission.
- Payer: `payer pay` on a payment still in intent ignored a different `--budget`, `--fee-limit-msat` or `--max-parts`, and could submit with no reservation held; such a request is now refused.
- Payer: the payment hash LND's DecodePayReq returned was not checked against the payment request; a different one is refused, as the receiver already refuses one. AddInvoice's hash is checked the same way.
- Outbox: a row edited in the database was signed with its edited operation, order, subject, value or fee; the worker now checks each against the row's ledger entry.
- `ledger-verify`: an order fulfilled twice, or fulfilled from an invoice not settled in full, passed; both are now named. A late settlement now keeps LND's amount, so it is checked without LND too. A deleted entry no longer distorts which payment counts as first, and LND's totals include payments whose posted lines cannot be read.
- REST: a stream dropped by a fault after the server's end arrived resolved instead of failing; an error answer to a stream had no time or size limit.
- `explain`: a long line starting with `::` was cut by three characters; a failed submission's HTLC attempts are shown at its failure, before the retry; `--refresh` names a late invoice's LND state and when it still has to be canceled, and fingerprints the subject's own ID instead of redacting it.
- `outbox-status` reads one snapshot. `:memory:` stores and an empty database file left by an interrupted first open are handled. The CLI removes its signal listeners after each command, and the lab removes Node diagnostic variables from macwarden's environment in any case.

## 1.3.1 (2026-10-11)

Fixes from a section-by-section audit of 1.3.0 and a second external audit. No new features.

### Security

- `inspect` and `scan` graded an L402 value that carried an admin LND macaroon among several macaroons as L402 `READ`, so `scan --fail-on` did not count it. Such a value is now graded as its LND macaroon (the highest grade when there are several), and `scan` reports every LND macaroon in it at its own column.
- `inspect` did not check `NODE_OPTIONS` and `NODE_DEBUG` when run from the command line, as the 1.2.1 release described; it now does.
- Node diagnostic flags written with underscores (`--tls_keylog`, `--cpu_prof`, `--heap_prof`, `--track_heap_objects` and the like), and V8's `--log`, were accepted; they are now refused with exit 2 like their dashed spellings.
- An `lndconnect://` URI with a second, percent-encoded `macaroon` parameter (`%6Dacaroon=`) was read with one of the two macaroons; it is now refused.
- `recommend` printed a narrowing command that dropped the credential's expiry or IP lock; a recorded expiry duration is now carried as `--expires`, and any caveat `bake` cannot reproduce withholds the command with warning `recommendation-caveats`.
- `recommend` suggested narrowing or revoking a canary; it now warns `canary-not-narrowed` instead.
- `recommend` could print a narrowing command whose credential outlived the original; `--expires` is now capped by the original's remaining lifetime, an expired original gets warning `recommendation-expired` with rotate or revoke advice instead of a command, and an expiry that cannot be parsed withholds the command.
- `rotate` silently dropped every caveat of the old credential other than the expiry it re-applies from the recorded duration, so the replacement of an IP-locked credential was unlocked and the registry recorded the narrower caveat list as fact. Such a credential, by its registry entry or its decoded file, is now refused before any LND call (exit 3 at S5, naming the caveat types: bake a new credential, attenuate it, then revoke the old one); `respond` skips such entries with a note and `inventory` no longer advises rotating them. Re-applying IP locks is planned.
- On Windows, `NODE_OPTIONS` and `NODE_DEBUG` written in another letter case (`node_options`, `Node_Debug`), which Node applies there, were not checked, so every command ran with them; they are now refused with exit 2 like the upper-case names.
- `scan --git-history` refuses a link in the git directory or a location file whose target is a Windows 8.3 short name (or another file system alias) of a protected file.
- `scan --git-history` accepted a symlink or junction inside the git directory whose target was a directory (`refs/heads/ext` → a folder holding `wallet.db`, outside or inside the work tree), and git then read every file in it to resolve the refs. A directory reached through such a link is now listed and a protected file or directory name in it is refused (exit 3) before git starts; a branch named `seed` in git's own directory still passes. On Windows, a gitfile, `commondir` or alternates entry written as a rooted path without a drive (`gitdir: /x`) was resolved on the drive macwarden ran from, so a scan from another drive failed with "path is not inside a git work tree"; it now resolves on the work tree's drive, as git does.
- `reconcile` attributed a payment to a single credential when a request for it came from a caller watch could not identify (`id:none` or `id:undecodable`). Such a payment is now reported with attribution `unidentified`, counted in no credential's totals, and keeps the run from exit 0.
- `reconcile` did not list in `deletedBy` a payment-record deletion that watch could not read in full (oversized or malformed request), although LND may have carried it out; it now associates such a deletion with every journaled payment.
- `watch --alert-command`: when several canaries alerted while an alert command was running, only the newest waiting alert ran and the others were dropped without notice; each canary now keeps its own waiting alert, run in order.
- `watch` did not check the node behind the endpoint again on reconnect; a different node now ends the run with exit 4 instead of recording its calls under the first node.
- `watch`: attribution still queued from a lost session could take over a request ID that LND reused in the next session, hiding the new call and recording its error under the old method and credential; request IDs are now matched only within their own session.
- A Core Lightning rune limited to `listconfigs`, which returns bitcoind's RPC password, was graded `READ`; it is now `UNASSESSED`.
- `scan --git-history` followed a symlink in the repository's git directory or location files to a network path; every location is now resolved link by link, and a UNC or device target is refused before it is touched.
- `scan --git-history` read include paths in `.git/config` differently from git, so quoting, comments without spaces and line continuations could hide a protected or network include from the location check; include values are now read as git reads them, and a nested include is resolved from the including file's path, not from its link target.
- `scan --git-history` refuses a repository whose refs or other git-directory files link to a protected file or a network path, refuses `~user/` include paths, and expands `~/` from the same home directory git is given.
- `scan --git-history` could run git from a relative `PATH` entry such as the scanned directory; git is now found once in absolute `PATH` entries and run by its absolute path.
- `scan` reported only the lndconnect credential when an lndconnect URI also held a different macaroon in another query parameter; the other credential is now reported.
- `scan` skipped a raw binary macaroon or Aperture token file stored under a name other than `*.macaroon` (such as `admin.macaroon.bak`) as binary; it is now read as a credential file.
- `scan` missed or only flagged as undecodable a percent-encoded standard base64 macaroon (`%2B`, `%2F`, `%3D`); it is now decoded and graded.
- `scan` missed a Core Lightning rune given as `"--rune", "<rune>"` in an MCP or JSON args array, a TOML array or a YAML flow list, and in JSON held inside a JSON string.
- `scan node_modules` or `scan .git` given as a path argument scanned nothing and exited 0; the argument is now scanned.
- `inventory --report` did not escape bidirectional, invisible and Unicode whitespace characters or the `##[` marker; they are now escaped in every format, and on stdout.
- On Windows, a dangling symbolic link at the registry lock or claim path was followed when the lock was taken; the lock is now refused and the file created through the link removed.
- On POSIX, a registry directory owned by another user was accepted; it is now refused unless owned by the current user or root.
- The registry was read by path after its size was checked, so a file replaced or grown in between was read whole; it is now read through the checked file's descriptor and at most 64 MiB.
- `watch --payment-journal` followed a symbolic link at the journal path or its `.lock` path and journaled to its target; it now refuses such a path (exit 3 at W6), as specified.
- The release workflow now publishes the exact tarball that its tests verified, only for a tagged commit on main, from a separate job that runs no dependency scripts while it holds the publishing token.

### Fixed

- `scan --git-history` refused a repository whose `.git` is a symlink to a gitfile ("path is not inside a git work tree", exit 3), although git accepts the layout and a `.git` symlink to a directory was already followed. The entry is now resolved link by link and classified by what is there; a relative `gitdir:` still resolves against the directory holding `.git`, as git does.
- `recommend --target-file -` read the credential from the process's own standard input (hanging on a pipe nobody wrote to) and a literal credential given as the target reached the file reader; both are now refused at parse with exit 2, as `revoke` refuses them.
- `watch`: the payment journal's keep-alive gate ran on the system clock, so a backward clock step of X delayed the next `alive` record by X and a run killed meanwhile looked unconfirmed from X earlier than necessary; the gate follows the monotonic clock now, as record times do.
- CLI: `macwarden --json` alone was reported as "unknown flag", and `macwarden --json <command> …` and `macwarden --version --json` were refused. The first is now "missing command", the second runs the command with `--json`, and the third prints the version as one JSON document.
- CLI: a second SIGINT, SIGTERM or SIGHUP while a command was blocked in a call that does not observe the interrupt did nothing; it now prints the interrupt result (exit 6, or 7 once a change may have reached LND) and ends the process. `watch` is not affected.
- CLI: an unexpected exception in a command that then never resumed ended the process with exit 8 and no output; the internal error is now printed once (one JSON document with `--json`).
- CLI: waiting for output to be flushed before an interrupt exit could exceed its 2-second limit when the system clock was set back; the limit now uses a monotonic clock.
- `inspect` narrowed L402 text holding a character above U+007F to bytes (U+013A was read as `:`); such text is now refused.
- `inspect` read the hex or base64 encoding of a rune, an NWC URI or an L402 value as that credential kind; hex, base64 and lndconnect input is now read as a macaroon only, and such an encoding exits 3.
- `inspect`: an L402 macaroon whose preimage is in a third-party caveat ID is checked against that preimage, as Aperture does, and that caveat is withheld from output; a `_valid_until` value with leading zeros is read as Aperture reads it instead of being reported as unparseable.
- Output redaction of nested macaroon-shaped data in a caveat or scanned file took tens of seconds for crafted inputs of a few hundred kilobytes; it now takes time linear in its size.
- `scan` stops at the findings limit as soon as findings of files scanned out of order exceed it, instead of first scanning every file already queued.
- `scan`: an ignore file with many long failing globs could make a scan take minutes; glob matching work is now bounded, and findings beyond the bound are kept.
- `scan --agent-configs` failed with exit 3 when a well-known location was a link to a missing file, and treated a location it could not examine as absent; the first is now absent, the second fails the scan.
- `scan` read an explicit symlink argument that points to a `*.macaroon` file as text, and could skip a distinct file as a duplicate on file systems whose file IDs are truncated (ReFS, Dev Drive).
- `scan`: SARIF and GitHub output now name every file not opened because its name looks like a wallet secret; the unknown-flag message lists `--agent-configs` and `--format`.
- `scan --git-history` with a file argument spelled in another case now scans that file's history on Windows and macOS, and scans files in trees and blobs that a tag names directly, and older stash entries.
- `scan --git-history` bounds the memory a history listing uses for commits and path names, failing as too large to scan instead of exhausting memory; history paths that are not valid UTF-8 stay distinct; a `.git` file is read only in git's own `gitdir: <path>` format.
- `scan --git-history` on Windows reports committed names containing `\` or `..` below the scanned path, and `\` counts as a separator for the `.git`/`node_modules` rule.
- Bounded file reads compare file identities exactly on Windows, and a failed close no longer hides the read's own error.
- `inventory` warns `usage-incomplete` when the usage file is incomplete, and the access review marks usage as incomplete or unreadable instead of "not observed".
- `inventory --report` writes the expiry as a UTC instant, and `--json` `result.report.review` matches the escaped report; `inventory` reports no `expires` for an expiry outside the years 0000 to 9999, so its JSON matches the published schema.
- `inventory` text output for very large node inventories renders in linear time; `inventory` and `recommend` take the latest last use by time, not by text, when timestamps have different precision.
- `recommend` warns `usage-incomplete` when usage records were evicted or calls went unattributed, even when no record remains for the selected credential.
- `recommend` prints a revoke step that names the root key ID when the label is shared (for example while a rotation is staged), and never suggests a label equal to the original or to another active label.
- `recommend` left methods that were only ever refused in the recommendation and then withheld it as broader; they are now left out, and warning `recommendation-denied` names them.
- `recommend` for a credential without a registry label (`--target-file`, `id:…`) always suggested the label `narrowed`, which `bake --label` refuses once a credential with that label is active on the node; it now suggests `narrowed2`, `narrowed3`, … past the active ones.
- `bake --canary --dry-run --json` printed a `canary` field that `schemas/output/bake.schema.json` did not allow; the schema now accepts it on a plan.
- `rotate --finish` deleted the old root key even when the replacement file had been removed or overwritten while the confirmation prompt was open, leaving the app without a valid credential. The replacement file is now read again after confirmation and must still hold the same credential; otherwise the run exits 3 at F7 with nothing changed.
- `attenuate` exited 8 "internal" for an input whose caveats, with the requested ones, exceeded 4,096; it now refuses such an input with exit 3 at A4 before writing anything.
- `respond`: an interrupted batch that left a file system call pending (an `--out` check on a stalled mount) printed its result and then kept the process alive; it now exits with its code (6 or 7) as soon as the result is written.
- `respond` lists a root key ID only once when LND returns it twice; `respond` and `verify` read the TLS certificate from the resolved path they checked.
- A ListMacaroonIDs answer that lists a root key ID twice is refused as an invalid LND response (exit 5).
- `watch`: a wall clock stepping forward (NTP on a host without a real-time clock, a restored VM snapshot) was counted as observed coverage, which could let `recommend` treat minutes of observation as days; coverage is now measured on a monotonic clock.
- `watch`: a wall clock stepping back paused the periodic usage-file writes, the reconnect registry re-read and the stable-session backoff reset for the length of the step; these timers now use a monotonic clock.
- `watch`: after a reconnect, or after many distinct calls, every further message of a live stream could be counted as a new call; request IDs are now kept after their response and forgotten least recently seen first, and a message of a stream whose opening the session never saw is recognised by LND's stream flag (`stream_rpc`) and not counted again.
- `watch`: two watches starting at once against a stale lock could both exit. When the one acting on its stale read moved the other's fresh lock aside and put it back, the new owner found the path briefly absent and refused its own lock as "watch lock path is a symbolic link". It now waits up to 0.5 s for the same file to return.
- `watch`: once output was closed (EPIPE), every drop notice counted itself as a new drop, so `droppedEvents` grew every 5 s for the rest of the run.
- `watch`: responses were charged their macaroon size in the attribution queue although nothing is copied for them, so heavy traffic with large macaroons dropped attribution earlier than needed.
- `watch`: a stream's error response still queued for attribution when its session was lost was discarded at the reconnect, uncounted (two errors became one, and `recommend` saw the evidence as complete); the queued attribution of the lost session now runs before its request IDs are forgotten.
- `watch --until`: a run whose `--until` ran out before LND confirmed the registration reported that it could not register and to check that LND is running; it now says that `--until` expired first.
- `watch`: the final error of a stream opened before an interceptor-only reconnect (LND kept running) was dropped uncounted, because request IDs were assumed to restart with every middleware session; LND numbers them per process, so such a stream keeps its ID and is now attributed to the credential that opened it. IDs restart only with LND, when every earlier stream is gone.
- `watch`: the final error of an idle server stream (SubscribeInvoices, SubscribeChannelEvents) was lost once 50,000 unary calls had been answered after it opened, because every answered call kept its request ID in the 50,000-entry remembered set and aged the stream out of it. Answered calls are now forgotten before any open stream or unanswered call, and a stream forgotten at the limit counts as a dropped attribution when usage would have recorded its error, so `recommend` sees the evidence as incomplete.
- `reconcile`: an authentication failure on TrackPaymentV2, which LND reports inside a stream error body, exits 4 instead of 5; a payment or HTLC status named after a JavaScript object member (`constructor`, `__proto__`, `toString`) is reported as `unknown` instead of breaking the output.
- `reconcile` compared LND's payment record with the first journaled request in the file, so a payment requested again after a clock was set back between watch runs was reported as `historical` and left out of its credential's totals; it now uses the earliest request, and `observation.first` and `last` are the earliest and latest request times.
- `reconcile` classified an unattributed payment near `--since` or `--until` as `boundary`; it now classifies it against the coverage around it, so one inside covered time is `covered`.
- `reconcile` reported a window of no width (`--since` equal to `--until`) at an uncovered instant as complete; it now refuses it with exit 2 at Q1.
- `reconcile`: the 10 minute budget now runs on a monotonic clock, so a system clock step no longer ends it early (reported as `lookups-limited`) or extends it.
- Payment journal: record times were pinned to a system clock that stepped forward and was then corrected; within a run they now follow the system clock only while it moves with a monotonic clock, so a real gap after the correction is reported instead of read as covered.
- Payment journal: coverage reported the time between a watch run's start and its registration with the reason of the gap before the run (or `before-journal` for the first run); it is now `not-registered`.
- Payment journal: records were counted as dropped when the fsync after a complete write failed; the records are in the file, and journaling still stops with `write-failed`.
- watch, the payment journal and recommend give a v1-encoded macaroon the same credential identity as its v2 form.
- `watch` and the payment journal attributed a call whose macaroon was padded past 64 KiB, or whose unsigned location field was padded past 4 KiB, to `id:undecodable`; the macaroon's header is now kept (its first 4 KiB, or up to 64 KiB when the header ends later), so the call is attributed to the credential named in it.
- `reconcile` reports `journal.firstRecord` and `lastRecord` (and the text output's journal span) as the earliest and latest record times; after a clock was set back between watch runs the span was shown backwards.
- `reconcile` text output named a payment requested by an unidentified caller `ambiguous`; it now says `unidentified` and lists the journal credentials.
- `reconcile` text output says on the `window` line how many payments in the window were attributed by requests before it (`lookups.attributedOutsideWindow`): they are reported by the window of their request, so they are neither listed nor unattributed in this one.
- `inventory --verify` marked a credential `rejected` when LND reported its root key missing while still listing the root key ID; it now reports `error`, as `verify` does.
- Loading a usage file holding more records than the limit could keep an older record over a newer one when their times were written with different precision; records are now ordered by time.
- Registry: a lock that could not be released after a failed acquisition was forgotten by the process; it is now kept, retried and reported as still held.
- Registry: a lock whose owner record could not be written was left behind when a virus scanner briefly held it, blocking every later run including `--break-lock`; its removal is now retried and, if it stays, the file is named.
- Registry: `--break-lock` could link a verified stale lock back to the lock path when deleting it failed once, leaving a lock that every later `--break-lock` refused; the delete is now retried and the stale lock is never linked back.
- Registry: `--break-lock` that could not examine the stale lock it had just moved (a virus scanner briefly holding it) put the lock back under two names, which every later `--break-lock` refused as ambiguous; examining the moved lock is now retried, and a lock put back keeps its one name.
- Registry: on NTFS, the lock's identity checks compared file identifiers as 53-bit numbers, so two different files could pass as the same one when a claim was cleaned up or a stale lock recovered; identifiers are now compared in full.
- Registry: on Windows, taking the lock failed at once when the previous holder's lock file was still being deleted; that is now waited for, up to 300 ms, as a claim held briefly by another command is.
- Registry: a lock file left empty by a writer killed while creating it was reported as "invalid registry lock" with no file name or remedy; the message now names the file, says no owner record was found, and advises stopping all writers and deleting it offline (`--break-lock` still refuses it, as there is no owner to prove gone).
- Registry: two commands starting at the same moment could fail with advice to delete the `.lock.claim` file; a claim held briefly by another command is now waited for (up to 300 ms), and permission, read-only, disk-full and missing-directory errors say so instead of advising deletion.
- Registry: on Windows, saving failed after about one second when another program held `registry.json` open; the save now waits about ten seconds and says the file is open in another program.
- On Windows, a file holding data could be deleted when another program had it open while macwarden was creating it; only an empty file is now removed.

### Changed

- `reconcile`: payment attribution has a new value, `unidentified`, with warning `attribution-unidentified`; such a payment is counted in no credential's totals, an identified credential that also requested its hash counts it under `ambiguous`, and it keeps the run from exit 0.
- `reconcile` refuses `--since` equal to `--until` (exit 2 at Q1).
- `recommend` has new warnings `recommendation-caveats`, `recommendation-expired`, `canary-not-narrowed` and `recommendation-denied`, and its `bake` step carries a recorded expiry as `--expires`, capped by the original's remaining lifetime.
- `inspect` and `scan` grade a rune limited to `listconfigs` `UNASSESSED`, and an L402 value carrying an LND macaroon as that macaroon.
- `watch` exits 4 at `W5` when a different node answers after a reconnect, and at `W7` when `--until` runs out before the first registration.
- `inventory` adds warning `usage-incomplete`; the access review shows "not observed (usage incomplete)" or "usage unreadable" where it showed "not observed".
- `macwarden --version` reports 1.3.1 (read from `package.json`).

## 1.2.1 (2026-10-10)

Security and robustness release from an external audit of 1.2.0 and a second audit round by five reviewers (payments, watch, scan, online commands, supply chain). No new features.

### Security

- `verify` could be made to say a credential was revoked while it was live: LND quotes the text of the caveat it refuses, and a caveat whose text reads `root key with id N doesn't exist` (or `signature mismatch`) matched the adapter's classification. Every quoted span in an LND message is now blanked before classification, and a `root-key-missing` answer while ListMacaroonIDs still lists the root key ID is treated as a contradiction: inconclusive, exit 1, with guidance.
- The payment journal could be poisoned by one request: a satoshi amount or fee limit times 1,000, or an invoice amount, above 2^63−1 millisatoshi was written as a record the reader refuses, which made every later `reconcile` exit 3 for the whole file. Such amounts are recorded as `null`, and the writer now checks every record with the reader's rules before writing it (one that fails is written as `malformed` with no facts).
- `reconcile` could credit an earlier payment to a later credential that reused the hash: attribution now uses every journaled request for a hash, before the window included (an earlier request by another credential makes it `ambiguous`), and a payment whose LND record predates every journaled request is `historical`, counted for no credential. The output schema gains `historical` in `attribution` and per credential.
- On Windows the registry, the usage file, `<registry>.canary.json` and the payment journal relied on mode 0600, which Windows does not implement: in a folder with permissive inherited permissions another account could read or change them. They are now created through the same owner-only helper as `--out` files (a protected DACL granting only this user), the rename of an atomic replacement keeps it, and an existing journal that any other account can read is refused with the `icacls` command that fixes it.
- As a consequence, on Windows creating the registry temp file, the usage file, the canary configuration and a new payment journal now runs the same fixed System32 PowerShell helper that `--out` files already used. Where it cannot run (PowerShell unavailable or in Constrained Language Mode), those writes fail as `--out` already did: `watch` reports `usage-write-failed` and refuses a new journal (exit 3), and a registry save fails through the command's existing recovery path.
- A bake response carrying caveats (an injected `lnd-custom` caveat made the new credential depend on a middleware, a pseudo-canary) is refused at B12/S11: BakeMacaroon never returns one.
- Diagnostic Node flags on the command line (`node --inspect …`, `--cpu-prof`, `--heapsnapshot-signal`, `--report-*`, `--trace-*`, `--tls-keylog`) are refused like `NODE_OPTIONS`; `inspect` and `scan` now apply the diagnostic-settings check too; `watch` warns (`unsupported-node`) on a Node version outside `engines`.
- `\\?\` paths that do not name a drive or UNC root (`\\?\GLOBALROOT\Device\…`) are refused as device namespace paths on Windows.
- The pre-commit hook declared `types: [text]`, so a staged `.macaroon` file (binary) never reached the scan; it is now `types_or: [text, binary]`.
- The example LND clients (`examples/agent-payments`, `examples/payment-lab`) set `rejectUnauthorized: true` explicitly, so an inherited `NODE_TLS_REJECT_UNAUTHORIZED=0` cannot turn their pinned certificate off; the demo strips that variable from child environments.
- `examples/agent-payments` sent its paid-API request without `rejectUnauthorized`, so under an inherited `NODE_TLS_REJECT_UNAUTHORIZED=0` the `Authorization: L402 <macaroon>:<preimage>` bearer token went to any certificate an HTTPS service presented (in a probe, a self-signed server outside the trust store received it). That request now sets `rejectUnauthorized: true` like the LND client and is refused (`DEPTH_ZERO_SELF_SIGNED_CERT`); the payment lab's client already did, and no other HTTPS or TLS request in either example lacked it.

### Fixed

- Denial of service with attacker-controlled input, each measured and bounded: the trailing-punctuation strip behind the `lndconnect` scan retry was quadratic (35 s for one 262 KB line); the LND error classifier's wildcard regex was quadratic (a hostile 1 MiB error body stalled every call 65 s; now a 4 KiB prefix and fixed phrases); payment journal decoding had no time budget (a 64 KiB payload flood kept watch's event loop 93 to 98 % busy; now the same 20 % budget as attribution); `journalCoverage` was quadratic in drop records and overflowed the call stack at 150,000 (now sorted sweeps, no argument spreads); the journal reader held every line of a 64 MiB file before validating (491 s, 2.4 GB for a file of empty lines; now streamed, with a cap of 64 consecutive unreadable lines); `reconcile` kept every HTLC attempt of every listed payment (about 10 GiB at the listing limit; now sums per payment) and scanned every coverage span per payment and every deletion per hash (now binary search and an index); `inventory` scanned the whole usage file per root key ID (now an index); `macaroonId` parsed every caveat for `watch` (a macaroon padded with 1,900 caveats exhausted the attribution budget at 450 calls per second; now header only).
- `reconcile` has an overall 10 minute budget besides the per-request timeout, reported like the count limits; LND values outside their types (negative amounts, a creation time beyond the year 9999, an index above 2^64−1) are an invalid response (exit 5) instead of reaching the output outside its schema or an internal error (each field here; the sums are bounded by the N1 fix below).
- Journal writes count the bytes each `write` call reports and loop until every byte landed; a write that makes no progress stops the run like a failed one.
- An explicitly empty `payment_request` with a valid `payment_hash` is journaled with the hash (LND pays the hash); it was recorded as `invoice-invalid`.
- `watch`: a repeated registration confirmation from LND no longer starts another coverage session; an exclusive lock create that followed a dangling symbolic link (Windows) removes the file it made and refuses the lock; an interrupt after the lock but before the first registration exits 6 (interrupted) instead of 4 (unreachable); at shutdown no alert command starts from the first shutdown step on, before the usage write; a delayed process-group kill probes the group first; the summary waits for the event write still in flight after a timed-out drain. The registry is read as a bounded regular file (64 MiB) like every other sidecar.
- `reconcile` coverage: two drop records that overlap in time were listed as two overlapping `dropped` gaps, in record order; they are now one gap with the summed count. A registration whose end was never recorded now makes the time after it `unconfirmed` even when it lasted no measurable time (it was reported with the previous span's end reason). Checked against the 1.2.0 implementation over 50,000 random journals: covered spans, covered seconds, every other gap and every drop count are identical.
- When the payment journal reached its 64 MiB limit, the payment records that no longer fit were discarded without a trace and the `full` record took the time it was written, so `reconcile` counted the time over those payments as covered: payments captured at seconds 10 and 20 vanished and `reconcile` reported 30 seconds covered, no gaps, no payments and exit 0. ### Added

- L402 (formerly LSAT) tokens. `inspect` reads an `Authorization: L402 …` or `LSAT …` value (one or several macaroons), a `WWW-Authenticate` challenge, a `macaroon:preimage` pair, a bare L402 macaroon in any encoding, or an Aperture token store file (`l402.token`, `l402.token.pending`, legacy `lsat.token`, as written by lnget, Loop and Pool). - An L402 token is reported as `access: "service-access"`, never with an ADMIN to READ grade: it pays for access to a service and gives no control of a node. `countedAs` is `READ` when a preimage is present that matches the payment hash (or cannot be checked because the identifier is not Aperture's), and `null` for a challenge, a pending token or a wrong preimage, which grant nothing alone.
- `scan` finds L402 Authorization values, challenges, `macaroon:preimage` pairs (also as `KEY=<pair>`), L402 macaroons in hex and base64 (including Aperture's gRPC `Macaroon` header form with a preimage caveat) and token store files, in code, configuration, `.env`, HTTP logs, HAR files, MCP agent configurations, base64-encoded Kubernetes data and git history. SARIF rules `macwarden/l402/paid|unpaid` and `macwarden/l402-file/paid|unpaid` (level note).
- Rule packs: gitleaks and TruffleHog rules `macwarden-l402`, `macwarden-l402-macaroon-hex` and `macwarden-l402-macaroon-base64`.

- Core Lightning runes, offline ([spec](docs/spec.md#core-lightning-runes-120)). `lightning-cli decode` already decodes a rune; macwarden adds safe scanning and a conservative assessment. Nothing is sent to a node: `checkrune` is never called, and whether a node would accept a rune (authenticity, issuing node, blacklist, rate-limit state) is reported as unchecked.
  - Parsing reproduces Core Lightning v26.06.8 byte for byte: its URL-safe base64 decoder (padding, unused bits, refused characters), restriction parsing with `\` escapes, the AND of OR-alternatives structure, all eleven conditions (`!` `=` `/` `^` ` `~` `<` `>` `{` `}` `#`), and the unique ID and version in the initial empty-field restriction, kept as strings and separate from the `id` (peer) field. Bounds of 8,192 characters, 256 restrictions and 1,024 alternatives fail closed: a rune beyond them is never assessed from a part.
  - `inspect` accepts a rune from a file, stdin or, with `--unsafe-arg`, a literal (a literal without it is refused like a literal macaroon), and reports `kind: "rune"` with recognition, assessment and verification apart. The grade comes from a method table pinned to Core Lightning v26.06.8 (every built-in command, with reviewed classes): a capability is excluded only when the whole restriction structure proves no request for it can pass. `method^list` is `UNASSESSED` with a broad-access warning (and `listdatastore`, `listconfigs` named as sensitive), `method/withdraw` is `ADMIN`, `commando` is `ADMIN` (a commando rune lets a peer run commands on the node), contradictory method conditions match no method, and peer, parameter, rate and time conditions are listed separately. A deadline is reported as passed according to the local clock only when every request is closed by time conditions.
  - `scan` finds runes in rune context: rune keys in env files, shell, JSON, YAML, TOML, code and agent configurations (`RUNE=`, `CLN_RUNE=`, `"rune":`, `clnRune`, `--rune=`), clnrest's `Rune` header, the base64 of a rune in a Kubernetes Secret, and checkable runes passed to `lightning-cli commando`, `checkrune` and `showrunes`. Findings have kind `rune`; a value in rune key context that does not parse, exceeds the bounds, or parses without a unique ID that `checkrune` accepts as a number (as arbitrary base64, digests and node IDs often do), is a `rune-invalid` finding graded `UNASSESSED`, never dropped. A value that may be cut (an unclosed quote, a folded line) is never graded below `UNASSESSED` unless `ADMIN`. Text, JSON, SARIF (rules `macwarden/rune/<grade>`, `macwarden/rune-invalid`) and GitHub annotations report the unique ID and assessment, never the rune, its authenticator or Core Lightning's decoded string; restriction values are redacted and bounded, and rune-context values in scanned paths and other output are redacted. Fingerprints cover the whole decoded credential.

  - Tests: the upstream ccan rune vectors (vendored), every condition, escapes, malformed encodings, ID and version placement, limits, the assessment table, expiry alternatives, scanning contexts and non-contexts, leak checks across text, JSON, SARIF, GitHub annotations and errors with freshly registered sentinel runes, and linear work on adversarial input. ## 1.1.1 (2026-10-09)

Security release. It fixes every finding of the independent audit of 1.1.0 ([report](docs/reviews/2026-10-09-audit-1.1.0.md)) and of four further internal reviews (threat model, lifecycle logic, scan robustness, output files and environment): 38 issues, each proven by a test that failed on 1.1.0. The most important: a long or punctuation-terminated `lndconnect://` URI could be missed by `scan`; `verify` could report a live credential as conclusively rejected (clock skew, an altered copy); a FIFO could hang `scan`; a new `--out` file was briefly readable under the folder's inherited Windows permissions.

Behaviour changes to note: Windows `--out` writes need the System32 PowerShell; POSIX `--out` is refused on file systems that cannot keep mode `0600` (for example WSL `/mnt/c`); connection settings must come all from flags or all from the environment.

### Fixed

- `recommend` no longer prints narrowing commands from a usage file whose timestamps are not real instants. The usage reader checked only the shape of each time, so a value such as `2026-99-09T12:00:00Z` was accepted, the observation window became NaN, and the 7-day short-observation guard was skipped. The usage file now requires real UTC instants (valid month, day of that month, hour 0 to 23) and ordered pairs (`firstSeen` ≤ `lastSeen`, `firstUse` ≤ `lastUse`, `firstStart` ≤ `lastEnd`, span start ≤ end); a file that breaks either is refused as `invalid usage file`. Independently, `recommend` treats an observation window it cannot compute as invalid: warning `observation-invalid`, and no narrowing command even with `--accept-short-observation`. Registry `createdAt` and `revokedAt` follow the same instant rule, and `watch` keeps each `last…` time from moving backwards when the clock steps back. A usage file written by an earlier `watch` across a backward clock step may now be refused; move it aside and run `watch` again (MW110-05).
- The usage file reader accepted root key IDs above the uint64 maximum (any 20-digit value, such as `99999999999999999999`), unlike the registry and the usage writer. One canonical uint64 rule (digits only, no leading zero, at most 18446744073709551615) is now shared by the registry, usage and canary records, the canary recorder and the `recommend`, `revoke` and `watch` root key ID checks; a `recommend` selector above the maximum is refused at R1 (MW110-07).
- `scan --git-history` no longer opens protected files named by repository locations. A `.git` gitfile, `commondir`, alternates entry or config `include`/`includeIf` path whose supplied path or resolved target has a protected file or directory component (such as an include of `../wallet.db`) now fails with exit 3 "git history would open a protected file" before the file is opened and before git starts; location files are read through one checked descriptor with a bounded read (MW110-03).
- Lock owner records (`<registry>.lock`, `<registry>.watch.lock`) are read through one descriptor bound to the checked regular file and never more than 64 KiB + 1 bytes, in the first owner read and in stale-lock recovery, quarantine and release. Previously a lock changed after its check was read whole by pathname (MW110-04).
- Releasing the registry lock no longer removes a lock another process created in its place. The release compared only device and inode, which Linux can hand to the next file as soon as the lock is removed; the owner record now carries a random per-acquisition `token`, and release also requires the same birth time and the exact record this acquisition wrote. Lock records without a token, written by earlier versions, are still read.
- `verify` reports a rejection as conclusive only on evidence from the node: a missing root key ID, a signature mismatch, or LND's own expiry error naming one of the credential's `time-before` caveats (`caveat "time-before <value>" not satisfied: macaroon has expired`, judged by the node's clock). Before, an unspecific rejection became `expired`, `conclusive: true` and exit 0 whenever the operator machine's clock said a `time-before` caveat had passed, so a skewed clock turned a caller-dependent rejection such as an IP lock into false clearance. Such a rejection now stays `other`, `conclusive: false`, exit 1, with a note that the local expiry reading is no proof (MW110-02).
- `verify` no longer clears a credential on a signature mismatch while its root key ID is still listed. LND answers `signature mismatch` after a root key regeneration, which keeps every root key ID listed, but equally for any altered copy (a flipped byte, a mangled paste, a decoy) of a credential that is still accepted; before, such a copy was reported `conclusive: true`, "its root key was regenerated", exit 0. The mismatch is now conclusive only once ListMacaroonIDs no longer lists the root key ID; otherwise it is `conclusive: false`, exit 1, with guidance that the original may still work and the revoke command (on root key ID 0: regenerate every root key unless already done). After a regeneration you carried out, old files therefore exit 1 with `signature-mismatch`; the incident playbook says so (RT-01).
- After a real root key regeneration, `verify` answers conclusively again for the exact credential macwarden recorded: a signature mismatch is conclusive (exit 0, "its root key was regenerated") when the file's fingerprint equals the one the registry recorded for that root key ID on this node, because those bytes are known genuine. Altered and unregistered copies stay inconclusive, and the guidance says how to settle them: compare the fingerprint with one recorded before the incident, such as an `inventory --report` export or a backup (RT-01).
- `verify`'s `canBake` and `respond`'s `bakingRisk` reflect baking authority, not the `ADMIN` grade: `macaroon:generate` or `uri:/lnrpc.Lightning/BakeMacaroon`, or a credential whose permissions could not be fully assessed (grade `UNASSESSED`, unassessed permissions, or a decode past its bounds), which counts as possibly able to bake. Before, a credential holding only `macaroon:write` was reported as able to bake although LND refuses BakeMacaroon with it. Grades are unchanged (MW110-06).
- `respond` checks ListPermissions for snapshot drift itself while planning, as every online command does, and warns `snapshot-drift`; its own credential therefore needs `info:read` (or the ListPermissions URI) for it. Before, a dry run, or a run with nothing to rotate, never made the check and reported no drift (MW110-09).
- `<command> --help --json` prints one JSON document, `{"schema":1,"command":"<name>","ok":true,"warnings":[],"result":{"usage":[…]},"error":null}`, carrying the command's synopsis lines, and every command's output schema accepts it. Before, it printed plain usage text although `--json` promises a single JSON document (MW110-10).
- `macwarden --help --json` prints one JSON document too (`command: null`, `result.usage` with the general usage lines and `result.commands` with every command and its summary). Before, it was refused as an unknown flag. A new schema, `schemas/output/macwarden.schema.json`, covers it and the usage errors printed before any command is known (MW110-10).
- The README now states `verify`'s exit codes as SPEC defines them: exit 1 while LND accepts the credential or rejects it inconclusively, exit 0 only for a conclusive rejection. It said exit 0 once LND rejects the file (MW110-11).
- `verify` no longer suggests `macwarden revoke <id>` for macwarden's own root key ID when a rejection is inconclusive (revoke refuses it). It says to bake a new session credential, switch to it and revoke the old root key ID from there; on root key ID 0 it says that only regenerating every root key invalidates the credential (RL-06).
- `revoke`, `rotate` and `rotate --finish` (and `respond --finish`) no longer dead-end when the old credential's recorded file path now holds another credential, for example after baking or staging the replacement where the app reads its file. Such a file is not the old credential, so the revocation is proven by root key ID only (ListMacaroonIDs no longer lists it) and the stage asks the informed approval used for a missing file. A file carrying the entry's own fingerprint on another root key ID still exits 3, because only an edited registry entry produces it. Before, every revoke, rotate and finish of the old credential exited 3 (RL-01).
- `rotate` records a replacement as created no earlier than the credential it replaces (the later of now and the original's `createdAt`). With the clock behind the original's recorded creation time (an NTP step back, a resumed VM), rotate wrote a link that `rotate --finish`, `respond` and `inventory` then rejected as registry tampering (exit 3), and respond refused every credential on the node. A link 1.1.0 already wrote this way is accepted when it has exactly the shape rotate writes (the original's permissions and grade, at most a `time-before` caveat) and is at most 24 hours behind; any other backwards link is still tampering, and the message now names `macwarden revoke <replacement id>` to abandon it (RL-02).
- A malformed recorded expiry duration (`caveats[].requested`, for example `1y` from a hand edit) is refused when the registry is read (exit 3) and checked again at rotate S5, before any lock or LND call. Before, `rotate` parsed it only after BakeMacaroon and exited 7 at S11, leaving an issued root key and an incomplete replacement that `respond` reported until it was revoked. `requested` is accepted only on a `time-before` caveat, and impossible calendar instants in `createdAt`/`revokedAt` (`2026-02-30`, `24:00:00`) are refused instead of rolled over (RL-03).
- One registry for several nodes works with every command. `revoke <id> --unregistered` revokes this node's ID even when another node's entry (for example an `--unregistered` tombstone) records the same small ID, so the command `verify` prints runs; without `--unregistered` the refusal now says how to proceed. `rotate` and `respond` resolve a label that is active on several nodes against the connected node (a read-only GetInfo) instead of exiting 2 "label is active on several nodes", which failed that credential in every `respond` batch (RL-04).
- Every command `inventory` prints in its text status now runs as printed (with the same connection and `--registry` flags). `revoke with:` names the root key ID when the label is ambiguous, for example while a rotation is staged (before, `macwarden revoke <label>` exited 2), and is not printed for root key ID 0 or macwarden's own credential. `rotate with:` includes the required `--out`, defaulting to `<label>-<YYYY-MM-DD>.macaroon` next to the recorded file, adds `--allow-admin` for an ADMIN credential, and is printed only for credentials `rotate` accepts (not canaries, the own credential, staged replacements or originals that already have one). Before, `macwarden rotate <label>` exited 2 for the missing `--out` (RL-05).
- A credential whose `replaces` names an original that was pruned from the registry can be rotated again. `respond` planned `stage` for it while `rotate` refused it at S3 ("no eligible active entry"), so neither command could ever rotate it. Both now use one definition: only an entry replacing an active entry on the same node is a pending replacement (RL-07).
- An interrupt (SIGINT, SIGTERM, SIGHUP) while `bake` or `rotate` saves the pending allocation, before anything is sent to LND, no longer exits 6 "nothing changed" with an active pending record left in the registry. The record is removed again before exit 6, and likewise before exit 3 when that save fails after its rename. If the registry still holds it, the exit is 7 and the message names the root key ID and `macwarden revoke <id>`. Before, `respond` then reported a false incomplete replacement that "LND may still create" (exit 7), and the bake label stayed blocked (RL-08).
- `scan` no longer silently drops a valid credential longer than its detector window. Before, an `lndconnect` URI carrying a long valid macaroon (about 50 KB, below the 64 KiB bound) was cut at 65,536 code points, counted as dropped and passed `--fail-on` with exit 0. Every match of up to 262,144 code points (the hex of a 64 KiB credential, its base64 or an `lndconnect` URI with certificate) is now matched whole wherever it starts, and a longer match cut by a window, including an `lndconnect` or NWC URI, is reported as `undecodable-candidate` and counts for `--fail-on`. Scanning stays linear in the line length (MW110-01).
- Output redaction recognises a credential's raw bytes rendered as UTF-8, as SAFE-01 promises. Before, only the latin1 rendering was recognised: a caveat embedding the UTF-8 rendering of a binary credential (where ill-formed bytes become U+FFFD) was printed by `inspect --json` unchanged, and a credential whose bytes render as multi-byte characters was missed too. The rendering is recognised by the framing that survives lossy decoding, in linear time (MW110-08).
- `scan` finds an `lndconnect` URI followed by punctuation (a markdown backtick or link `)`, a sentence-final `.`, YAML flow `,` or `}`, a shell `;`) or carrying the standard base64 alphabet. Before, the URI did not parse, was counted as dropped, and the valid credential inside it was hidden, so `--fail-on` passed with exit 0. A URI that does not parse no longer hides the credential it carries: that is reported on its own, decoded or as a candidate (RR-01).
- `scan` finds a base64 macaroon or an `lndconnect` URI whose slashes are JSON-escaped as `\/` (PHP `json_encode` and some Java and Go encoders). Before, the match stopped at the first backslash: about half of all credentials, those with a `/` early in their base64, produced no finding at all (RR-03).
- `scan` finds credentials stored as the base64 of their text, as in Kubernetes Secret `data:` values and Helm values (`kubectl create secret generic --from-literal=LND_MACAROON=<hex>`). Before, the base64 of a hex, base64 or `lndconnect` credential produced no finding. Such text is decoded one level deep, in linear time, and findings are reported at their column in the encoded text (RR-02).
- `scan` decodes hex written with a separator between every byte (colon hex, `xxd -g1`, spaced bytes) and credentials wrapped narrower than 49 columns (joined with their continuation lines), and reports the prefix of an `xxd` default dump as `undecodable-candidate`. Before, all of these produced no finding (RR-10).
- `scan` can no longer be hung by a FIFO. Files were opened without `O_NONBLOCK`, so anyone able to write in a scanned directory could swap a FIFO in between the walk's `lstat` and the open, and `open(2)` waited for a writer forever; SIGINT, SIGTERM and SIGHUP did not end it, because cancellation was only checked between files. Scanned files and the ignore file are now opened non-blocking (and no-follow), the descriptor is checked with `fstat` before anything is read, and an interrupt abandons any file system operation still pending, so the scan exits 6 at once (robustness review 2026-10-09, RR-04).
- `scan` time no longer grows with the cube of directory depth. The walk resolved the full path of every directory and file with realpath, which resolves each component again, so a committed chain of deep directories could stretch a CI scan from seconds to many minutes. Each path argument is now resolved once and resolved paths are carried down the walk; one `lstat` per check keeps the identity guarantees. On Linux 2,000 nested directories now take 1.9 s (25 s before; 0.2 s laid out flat) and 2,000 files at depth 1,000 take 1.9 s (12.7 s before; 0.6 s at the top level) (RR-05).
- `scan` on Linux and macOS reports a file whose name contains `\` under its real name in every format. Every `\` in a path was turned into `/`, so `back\slash.env` was reported as `back/slash.env`, a file that does not exist, and ignore globs were matched against that wrong name. Only Windows treats `\` as a separator now (robustness review 2026-10-09, RR-07).
- `scan` on Linux scans directories named `.GIT`, `Node_Modules` or any other case variant of `.git` and `node_modules`. They were skipped as `excluded-dir` on every platform, so credentials in them were never reported, although on a case-sensitive file system they are ordinary directories. Windows and macOS, whose default file systems ignore case, still exclude them; `--git-history` follows the same rule (RR-08).
- `scan --format github` names the real file in each annotation. The `file` property carried the text-output escape of a control character (`new\x0aline.env`) instead of the path, so GitHub could not attach the annotation to the file. It now carries the path with GitHub's own property escaping only (`%0A`, `%0D`, `%25`, `%3A`, `%2C`) (RR-09).
- Text output escapes invisible characters in file names and other untrusted strings: every Unicode format character (soft hyphen U+00AD, zero-width space and joiners, word joiner U+2060, the tag characters U+E0000 to U+E007F and the rest of category Cf), the Hangul fillers, U+034F and the variation selectors. They were printed raw, so `admin⁠.macaroon` looked like `admin.macaroon`. Characters beyond U+FFFF are written `\u{N}` (RR-11).
- `scan --format sarif` gives correct file URIs for paths outside the working directory. A finding under a relative `../` argument got `file:///../sibling%20dir/x.env`, which names `/sibling dir/x.env`, so code scanning pointed at a file that does not exist. Such a path is now resolved to an absolute `file:` URI (UNC paths as `file://server/share/…`, a `\` in a Linux file name encoded as `%5C`), and the run declares `%SRCROOT%` in `originalUriBaseIds` so every relative URI resolves to its file (RR-06).
- `.macwardenignore` and `--ignore-file` accept a UTF-16 file with a BOM, which is what Windows PowerShell 5.1 writes with `>` and `Out-File`; it failed with exit 3 (`ignore-file`). A glob with a leading `/` (`fp:… /top.env`, as in `.gitignore`) is anchored at the ignore file's directory; it never matched before. Both failed closed (RR-14).
- `scan` exits 3 (`input-read`, "scan path is not a regular file or directory") when a path argument is a FIFO, device or socket. It was skipped as `not-regular` with exit 0, so `scan pipe.env --fail-on READ` passed a CI gate having scanned nothing, against the rule that an unreadable argument fails. Such entries found inside a walked directory are still `not-regular` skips (RR-12).
- `scan` reports every hard-link name of a file with a finding. Within one path argument a second name of the same file was dropped by identity deduplication without a finding or a skip, so an operator who removed `a.env` (most editors write a new file) still had the credential in `b.env` and was never told. The finding at the first name now carries `alsoAt` with the other names (count and up to five paths), shown in text, SARIF and GitHub output; an ignore entry hides it only when every name matches (RR-13).
- Windows `--out` (`bake`, `rotate`, `respond`, `attenuate`, `inventory --report`): the file is created owner-only in the same call that creates it (owner = your SID, a protected DACL with one entry for you, nothing inherited), then its owner and DACL are read back while macwarden holds the exclusive handle, before any byte is written. Before, the file existed under the folder's inherited ACL for about 70 ms until `icacls` ran; an account with inherited change-permissions (WRITE_DAC) could open a handle in that window that the exclusive reopen did not detect, and grant itself read access after the credential was written, while the command reported a restricted ACL. Any other entry, an inherited entry or a different owner now fails the command (exit 3) with nothing written. `acl-best-effort` is given only on a FAT or exFAT volume, which stores no permissions; `icacls` and `whoami` are no longer run (RO-1).
- Windows `--out` and `respond --out-dir` refuse names that Windows normalises or maps to a device or stream before anything is created (exit 3, "output path refused"): a component ending in a dot or a space, a reserved device name (`CON`, `PRN`, `AUX`, `NUL`, `COM0`–`COM9`, `LPT0`–`LPT9`, `CONIN$`, `CONOUT$`, with or without an extension), `:` (alternate data stream) or another character Windows forbids, and `\\.\` paths. Before, Node wrote the literal name while the ACL was applied to the normalised one: `app.macaroon.` next to an existing `app.macaroon` kept the folder's ACL without a warning (and the sibling's ACL was rewritten), and `notes.txt:app.macaroon` wrote the credential into a hidden stream of an existing file instead of refusing (RO-2).
- POSIX `--out` verifies the mode: after the exclusive `0600` create, the mode and owner are read back from the open descriptor, one `chmod 0600` is tried, and a file that is still not private is removed and the command fails (exit 3) with nothing written. Before, on file systems that do not store modes (WSL `/mnt/c`, vfat, exFAT, CIFS) the credential was written world-readable while `bake` printed "(0600)". The text output now reads "(0600, verified)" or "(owner-only Windows ACL, verified)" (RO-3).
- Online commands take the node address, its certificate and their own credential from one source: all from flags, or all from `MACWARDEN_LND_REST`, `MACWARDEN_TLS_CERT` and `MACWARDEN_MACAROON` (`watch` adds `--lnd-grpc`/`MACWARDEN_LND_GRPC`). A flag combined with a set variable for another setting is refused (exit 2, naming the variables, before any request). Before, each setting fell back to its variable on its own, so `--lnd-rest`/`--tls-cert` for node B with a shell-exported `MACWARDEN_MACAROON` for node A presented node A's admin-equivalent credential to node B (RO-4).

## 1.1.0 (2026-10-08)

Security release. It fixes every finding of the independent audit of 1.0.1 ([report](docs/reviews/2026-10-08-audit-1.0.1.md)) and of a differential fuzzing review of the parsers against LND's own macaroon library, and adds `verify` for operators responding to credential exposure such as the BTCPay Server 2.4.2 incident.

### Added

- New command `verify <file | ->`: asks your node whether one credential file is still accepted, for operators checking macaroon files that may have been copied (for example in the BTCPay Server 2.4.2 incident, where patching did not invalidate stolen files). It decodes the file offline as `inspect` does, calls CheckMacaroonPermissions with its own permissions, and reports `status` (`accepted` or `rejected`), why LND rejected it (`root-key-missing`, `signature-mismatch`, `expired` or `other`), whether its root key ID is still listed, and its registry label. Exit 1 while LND accepts it, and also when a rejection may depend on the caller (an IP lock or a custom caveat such as a canary's); exit 0 once LND conclusively rejects it. Guidance names the next step: `macwarden revoke`, `respond` for a credential that can bake, or, on root key 0, regenerating every root key first and baking fresh per-app macaroons afterwards. A Nostr Wallet Connect URI is refused (exit 3). Output schema `schemas/output/verify.schema.json`.
- New [incident playbook](docs/incident-playbook.md) for exposed credentials (BTCPay Server < 2.4.2 and similar): what patching fixes and what it does not, checking each old file with `verify`, replacing and revoking with `respond`, `rotate` and `revoke`, root key ID 0, re-pairing apps and checking for unauthorized activity. Linked from the README.
- Requires Node.js `^22.23.2 || ^24.18.1 || >=26.5.1` (was `>=22.12.0`): the July 2026 Node.js security releases fix HTTP/2 flaws (CVE-2026-56846, CVE-2026-56848) in `node:http2`, which `watch` uses for its gRPC stream to LND. CI tests the new minimum versions.

### Fixed

- `rotate` and `respond` decide whether a credential is a canary from its decoded file, not only from the registry's caveat list. A registry entry whose caveats were cleared while its file still carries an `lnd-custom` caveat is refused as tampering (exit 3 at S4 and P5) before any lock or LND mutation. Before, clearing that metadata let a canary be rotated into an ordinary, accepted credential (MW102-01).
- `respond --finish` resumes a finish that deleted the old root key ID but stopped before saving the registry: the credential is finished through `rotate`'s F6 repair, which proves the replacement accepted, records the revocation and link, and sends no second deletion. Before, it reported exit 0 with a `repair` item and advised `macwarden revoke <label>`, which exits 2 because the old entry and its replacement share the label. Advice in `respond` now names a credential by its root key ID wherever its label is ambiguous (MW102-02).
- `respond` no longer reports a replacement that an earlier stage allocated but never completed (`verified: false`, no output file) as `staged-earlier` with advice to switch the app. It is reported as unresolved: item `repair`/`failed` with exit 7 at P5, listed under `unproven`, with whether LND lists the ID and the recovery `macwarden revoke <replacement root key ID>` followed by a fresh stage. The uncertain mutation is never retried (MW102-10).
- `recommend` applies the `recommendation-broader` widening guard to every selector. Selecting a credential by `id:…` (or `--target-file`) never looked up its registry entry, so usage claiming a method the credential never held (for example SendPaymentV2 on an invoice credential) produced a bake command that widened it. The credential ID is now resolved through its recorded root key ID to the single active registry entry; `--target-file` is also checked against the file's own permissions. When the permissions cannot be established (unregistered, root key 0 by ID, ambiguous), warning `recommendation-unverified` withholds the commands. A credential ID selector no longer suggests revoking the whole root key ID. (MW102-03)
- `recommend` counts only watch coverage after the credential was created toward the 7-day observation rule. It compared the covered total with the time since creation, so eight days watched before a credential existed plus one second afterwards counted as seven days and printed narrowing and revoke commands. `watch` now records the registered spans per node (`coverageSpans` in the usage file, at most 256 per node; `coverage` is unchanged, so 1.0.1 still reads the file), and `recommend` uses a provable lower bound. A file without spans counts coverage that began before creation only as far as it cannot have lain before it; a credential without a registry entry counts from its first recorded use. (MW102-04)
- `watch` shutdown keeps its alert budget (MW102-05). An alert waiting behind a running `--alert-command` is discarded at shutdown (reported as `alert-failed`; its event line is still printed) instead of starting after watch was asked to stop; the running command gets one deadline and is then cancelled with its process group or, on Windows, its process tree; and the CLI's forced-exit deadline starts only after Windows tree kills have finished. Before, a second alert could start 12 s into shutdown and outlive watch.
- `watch --until` honours durations beyond about 24.8 days (MW102-09). Node fires a timer longer than 2^31−1 ms after 1 ms, so `--until 25d` stopped almost at once; the wait now runs in bounded chunks against one monotonic deadline, up to the accepted maximum of 999999d.
- `scan --git-history` bounds the repository-location check. Each include and alternates file is read once, and the check stops with exit 3 ("git history could not be read") when git would follow more than 4,096 include or alternate entries or parse more than 1 MiB of location files in total, or when more than 256 distinct location files are involved; an interrupt is honoured during the check. Before, eight 100-byte configs each including the next eight times were walked 2.4 million times (MW102-06).
- The usage and canary files next to the registry are read through the same bounded reader as TLS certificates: a path or symlink target with a protected name (`seed.json`, `tls.key`, ...) is refused before it is opened, anything but a regular file is refused, and a file larger than its format allows (about 20 MiB for usage, 4 KiB for the canary configuration) fails before it is parsed. Registry and watch lock records are read only from plain files, never through a symlink. Before, a symlinked sidecar was followed into a protected file and read whole (MW102-07).
- Online commands reach a literal IPv6 REST endpoint (`--lnd-rest '[::1]:8080'`). The bracketed host was passed to the TLS connection as a DNS name, so a certificate with the matching IP address SAN failed verification (exit 4). On Node 22, whose own TLS identity check refuses every IPv6 literal, REST and gRPC connections to an IPv6 address use an equally strict check that accepts only a matching IP address SAN. Printed URLs and commands keep the brackets; verification stays on (MW102-08).
- `inventory --report`: the Markdown and CSV reports carry all the evidence of the JSON review. Markdown adds the rotation links (replaces, replaced by), canary uses (count, first and last use), caveats and flag counts. CSV stays one table with one header row and adds caveats, canary uses, the controls naming each root key ID with their observations, and report-level columns repeated on every row (generated time, macwarden version, node pubkey, alias, network and LND version, empty sign-off fields, the limitation statement). The JSON review adds `canary` per credential and `limitations`. Before, Markdown dropped rotation links and CSV dropped the report identity, controls, sign-off and limitation statement (MW102-11).
- `watch` and `recommend` have published JSON schemas: `schemas/output/recommend.schema.json`, `watch.schema.json` for watch's final document and `watch-event.schema.json` for the event lines `watch --json` prints before it (call, error, canary and each status event). They are generated with the others, shipped in the package and checked against real outputs, refusals included. Before, the package had no schema for either command (MW102-12).
- `scan` no longer stalls on a crafted `.json` file. MCP-context tagging rebuilt the whole key path for every string value and compared every finding with every tagged string, so one committed file with deep nesting and many strings (any `.json` file with one candidate finding) held a scan for hours: 19.3 s for 176 KB, about 4 to 5 hours for 5 MB. Tagging is now linear: 75 ms for the 176 KB file, 1.2 s for 5 MB, and it gives up beyond 1,000 levels of nesting. (Parser review 2026-10-08, HIGH-1.)
- A re-framed macaroon is decoded as LND decodes it. go-macaroon reads packet kinds, lengths and end-of-section markers as any varint encoding (non-minimal `0x83 0x00` for 3, `0x80 0x00` for end-of-section), so anyone holding a macaroon can re-frame it without the root key and LND still honours it. `inspect`, `scan`, `revoke` and `rotate` refused such a copy as undecodable, and `watch` attributed its calls to `id:undecodable` instead of the stolen credential. The fingerprint is now defined over the canonical form (what go-macaroon writes), so a re-framed copy has the fingerprint of the original; every macaroon LND or macwarden writes keeps its fingerprint. Output redaction also recognises a re-framed hex copy. (Parser review 2026-10-08, MEDIUM-1.)
- Identifier shapes LND authorizes are no longer refused and ignored. An extra op with an empty entity or no actions, an unknown protobuf group, a non-minimal protobuf tag, more than 256 ops, more than 512 actions in one op and more than 4,096 caveats are decoded as LND decodes them (bakery requires actions only on the first op). Before, `inspect` refused such a macaroon, `scan` reported it as undecodable and `watch` could not attribute its calls, although LND granted it full authority. Expansion stays bounded (an entity over 16 bytes or an action over 256 bytes is left out, as is everything past 1,024 permissions or 64 KiB of permission text, and caveats past 4,096); a macaroon past a bound is still decoded, carries the warning `identifier-exceeds-bounds` or `caveats-exceed-bounds`, and its grade fails closed to `UNASSESSED` unless what was kept is already `ADMIN`. The stage `identifier-limits` is no longer produced. (Parser review 2026-10-08, MEDIUM-2.)
- Output redaction no longer misses a hex macaroon written right after a backslash or a percent sign (for example a Windows path such as `C:\keys\0201…`). Recognition looked only at the text after decoding escapes, so `\020` was read as an octal escape and `%02` as a percent escape, which removed the start of the macaroon. Hex is now also recognised in the literal text. (Parser review 2026-10-08, LOW-1.)
- Output redaction and scan's NWC secret collection use the linear NWC matcher that scan detection already used. They still ran the published `nwc` regex, which backtracks quadratically when the URI prefix repeats without a secret: 1 MB took 4 to 6 s to collect and 10 to 12 s to render, and `inspect` of a 1 MB macaroon with such a caveat took 9.3 s. Now 31 ms, 1.0 s and 1.3 s, with identical matches. (Parser review 2026-10-08, LOW-2.)
- `scan` finds NWC connection strings in common escaped forms: HTML or XML with `&amp;` before `secret=` (the detector matched it, then the hit was dropped without being counted), JSON with escaped slashes, percent-encoded (deep links, form fields) and with `+` decoded to a space. Each grants spend authority. Every detector match is now reported, and each line is matched once more after unescaping these forms. (Parser review 2026-10-08, LOW-3.)
- A `time-before` caveat with a one-digit hour (`2027-10-08T1:00:00Z`), a zone offset hour of 24 (`+24:00`) or an offset minute of 60 is parsed as LND parses it (Go's `time.Parse` falls back to a lenient parser). Before, macwarden reported `bad-time-before` and no expiry, so an expired credential LND refuses was shown with no known expiry, and `revoke`/`rotate` treated it as unusable. (Parser review 2026-10-08, LOW-4.)

## 1.0.0 (2026-10-08)

First production release. It adds runtime visibility (`watch`, canaries, `recommend`), incident response (`respond`), access-review evidence and CI-native scanning to the 1.0.0-rc.1 command set, and closes every finding of the 2026-10-08 deep audit ([report](docs/reviews/2026-10-08-deep-audit.md)). Validated with complete Windows and unprivileged Linux suites, every pinned-regtest LND reference, leak checks and independent reviews. The real-node field check is in [docs/field-check.md](docs/field-check.md).


Audit fixes and hardening (2026-10-08):

- Output is rendered in bounded chunks and written with stdout backpressure, so a very large scan no longer builds one string that can exceed V8's limit. A closed stdout or stderr pipe (`| head`) stops output quietly and keeps the computed exit status instead of reporting an internal error.
- A BakeMacaroon or DeleteMacaroonID request that gets no complete response (timeout, reset, cancellation) is treated as an unknown outcome: exit 7 with the pending record kept and an exact recovery command, never "nothing changed". Recovery commands print absolute paths.
- Registry: a failed lock acquisition no longer leaves a stale lock; saves sync the directory on POSIX; validation is linear in the number of entries; leftover temporary files from killed saves are removed under the lock.
- Windows `--out`: the credential is written only through an exclusive handle opened after the owner-only ACL is applied, so a handle opened before the restriction cannot read it.
- `scan --git-history` refuses repository locations off the local file system (gitfile, commondir, alternates and config includes pointing to network or device paths) before git runs; a shallow clone fails with exit 3 unless `--allow-shallow`; history memory is bounded; SIGINT/SIGTERM stop a scan (exit 6) and kill git.
- Credential recognition finds grouped base64 runs in linear time: a crafted 200 KB caveat took 52 s to `inspect` and now takes 0.15 s.
- `scan` scales: known NWC secret redaction, ignore-file matching, read buffers and per-line work are linear; a 200,000-file tree scans in about 15 s instead of 384 s.
- `--help` lists the commands and `<command> --help` prints its synopsis; refusals name the flag and the rule; `--fail-on` accepts any case.
- `rules/gitleaks.toml` extends gitleaks' default rules (it replaced them before) and adds keyword prefilters; a pre-commit hook definition ships in `.pre-commit-hooks.yaml`.
- `inventory` shows an EXPIRES column with expired and expiring flags; `--expiring-within <n>(m|h|d)` exits 1 for a cron reminder. `scan` text marks expired credentials.
- JSON schemas for every command's `--json` output in `schemas/output/`, shipped in the package and checked against real outputs in the tests.
- The Windows process-domain query passes an explicit temp directory, defaulting to the system Temp folder in service environments without TEMP or TMP.
- Package metadata and the (disabled) release workflow are ready for npm trusted publishing; prereleases publish with the `next` tag.

Features (2026-10-07 and 2026-10-08):

- `scan --format sarif|github` for CI: a SARIF 2.1.0 log for GitHub code scanning and GitHub Actions annotations, both without matched text. `--format json` equals `--json`.
- `scan --agent-configs` scans the configuration locations of AI agents and MCP clients and marks credentials found inside MCP server entries (`context: "mcp-config"`).
- `rules/trufflehog.yaml`: the four detectors as TruffleHog custom detectors, with the same regexes as SPEC and the gitleaks pack.
- `scan --git-history` scans every blob committed on any ref, so a credential that was committed and later deleted is still found. Local git only, offline and read-only.
- `inspect` decodes Nostr Wallet Connect URIs offline: wallet and client public keys, relays, lud16 and fingerprint, counted as SPEND. The secret is never shown; a relay, lud16 or wallet key that embeds it is refused. Legacy `nostrwalletconnect:` schemes are decoded by `inspect` and detected by `scan` and the gitleaks rule.
- New offline `attenuate` command adds expiry or IP caveats to a copy of a macaroon. The copy shares the original root key ID, and the command says so.
- New `watch` command: a read-only LND RPC middleware (gRPC) that attributes every authenticated call to a credential ID, root key ID and registry label, records last use for `inventory`, and guards canary macaroons.
- `bake --canary` bakes a decoy that LND refuses unless `watch` runs; with `watch` running, every use its permissions allow is denied and alerted in the same call.
- `inventory` text output lines its columns up under the headers.
- `watch` canary alerting is rate-limited: every use is still denied, but each canary raises at most one alert per 10 seconds plus a counted summary, and at most one `--alert-command` runs at a time. Previously a flood of canary uses spawned one alert process per use and could exhaust the host.
- Red-team hardening before release, each item reproduced with a probe and covered by a test:
  - `watch`: canary alerts cannot be suppressed by bursts or invented conditions; every bound on the middleware stream (unread feedback, frame size, registration and stall deadlines, method and macaroon field sizes, reconnect backoff) is enforced over real HTTP/2; feedback stays under 100 ms p99 at 100,000 calls/s; output survives a slow or stalled reader on Linux; alert commands and their children are always reaped; the lock survives crashes, container restarts and start races.
  - `recommend` refuses to print a narrowing command when usage may be incomplete or broader than the credential.
  - `respond` leaves canaries alone, lists root key IDs the registry marks revoked but LND still holds, scopes every proof to its own credential, flags credentials that can bake, and refuses tampered replacement links, chains and cycles.
  - `scan` and `inspect` bound macaroon decoding (a crafted 61 KB file took two minutes and 1.3 GB; now milliseconds and refused), report a credential added at many history paths once with a count, enforce a findings limit, and never print a line that GitHub Actions or a terminal could read as a command or reordered text.
  - Printed commands quote safely for POSIX shells and PowerShell, including curly quotes.
- New `recommend` command: least-privilege permissions and exact methods from observed usage, with the narrowing commands.
- `scan` reads files concurrently with a fixed bound and unchanged output order.
- New `respond` command: after a suspected leak, stage replacements for every registered credential in one confirmed batch, then `--finish` revokes the old root key IDs with per-credential proof (old rejected, new accepted). Resumable; unknown IDs and root key ID 0 are reported with guidance, never touched.
- `inventory --report markdown|csv|json [--out <file>]` exports access-review evidence with control observations, last use from `watch` and a reviewer sign-off.
- On Windows, owner-only output files are granted to the current user SID, with the account name as fallback.
